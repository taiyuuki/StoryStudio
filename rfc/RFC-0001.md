# 1. Abstract（摘要）

Story Studio 是一个面向故事（小说、剧本等）创作的 Language Workbench。

Story Studio 不将小说视为一篇不断增长的 Markdown 文档，而是将小说视为一个具有明确结构、可验证、可维护、可演化的软件工程。

AI 在 Story Studio 中不是创作者，而是项目成员（Project Member）。数据流分四层单一职责：**Parser**（理解文本结构）→ **Story IR**（表示故事结构）→ **Knowledge Layer**（表示可推理、可验证的知识，RFC-0015）→ **Compiler**（验证一致性，产出 **Diagnostics**）。AI 的非确定性被隔离在 Extraction 环节，提交后的断言使 Compiler 的确定性承诺真正成立。通过 **Reference Index**（实体间引用）与 **Location Index**（派生的文本块定位）实现实体定位与诊断跳转。

------

# 2. Motivation（为什么做）

随着 LLM 的发展，AI 已经能够生成较高质量的文本。

但是，目前几乎所有 AI 写作产品都存在相同的问题：

> AI 擅长写一段。

> 不擅长维护一本书。

对于几十万字甚至上百万字小说而言，目前主要问题不是文笔，而是：

- 人物设定冲突
- 年龄错误
- 世界观冲突
- 时间线错误
- 道具消失
- 人物复活
- 伏笔遗忘
- 称谓混乱
- 地理位置冲突
- POV 混乱

目前解决方式主要依赖 Prompt。

Prompt 无法成为长期工程管理方案。

Story Studio 希望解决的是：

> **如何让小说像软件一样被维护。**

------

# 3. Philosophy（设计哲学）

Story Studio 遵循以下原则。

------

## 3.1 Project First

Project 永远是第一层。

不是 Chat。

不是 Prompt。

不是 AI。

整个系统围绕一个 Project 展开。

------

## 3.2 Story First

系统维护的是 Story。

不是 Markdown。

Markdown 只是 Story 的一种表现形式。

------

## 3.3 AI is Replaceable

AI 可以替换。

GPT

Claude

Gemini

DeepSeek

Qwen

Ollama

都应该只是不同的 Provider。

Story Studio 不依赖任何特定模型。

------

## 3.4 Compiler First

一致性检查比文本生成更加重要。

任何 AI 都可能犯错。

但"一致性检查"本身是分层的，不能全部压给一个确定性的 Compiler：

- **结构 / 引用检查（确定性）**：实体是否存在、引用是否有效、重名、孤儿节点。**数据源：Story IR。**
- **时序 / 逻辑检查（确定性，依赖显式标注）**：死人复活、时间线倒序、年龄矛盾。**数据源：Knowledge Layer**（RFC-0015）——可验证的命题（断言 + 证据）有专门的存放处，不再悬空为"假设已被标注"。
- **语义 / 文学判断（非确定性，依赖 AI）**：伏笔回收、语气一致、称谓得当。**数据源：Semantic Validator** 对 IR + 文本的 AI 分析。

Compiler 只承担前两类。第三类属于语义判断，确定性 Compiler 根本无法判定（例如无法从纯文本机械地推断一个伏笔是否被"解决"），必须交由独立的 **Semantic Validator（AI）** 处理。

因此 Compiler 永远是**结构安全网**的最终检查者，但不是质量保证的全部。

------

## 3.5 Local First

Project 必须能够完全保存在本地。

离线状态下：

用户依然能够：

- 编辑
- 浏览
- 搜索
- 编译
- 导出

AI 只是增强能力。

------

## 3.6 Plain Files

Project 不依赖数据库。

所有核心数据均采用文本文件保存。

数据库只能作为缓存。

------

## 3.7 Git Friendly

Project 必须适合：

Git

Diff

Merge

Branch

Review

------

## 3.8 Deterministic

相同输入。

Compiler 必须得到相同结果。

Compiler 不依赖 AI。

> **边界声明：** 确定性仅适用于 3.4 中定义的结构与时序检查。语义 / 文学判断本质上是概率性的，不在确定性承诺的范围内——这类判断由 Semantic Validator 产出 Warning / Hint（非阻断），作者拥有最终决定权。

------

# 4. Vision（最终目标）

Story Studio 希望成为：

> 小说领域的 VSCode + Git + Compiler。

而不是：

> ChatGPT 套壳。

------

# 5. Scope（项目范围）

Story Studio 包括：

✓ Novel Project

✓ Story IR

✓ Compiler

✓ Diagnostics

✓ AI Runtime

✓ Plugin

✓ Export

✓ Graph

✓ Version Control

Story Studio 不包括：

✗ 在线小说平台

✗ AI Model

✗ 云存储

✗ 小说社区

✗ 小说推荐

**用户角色（User Role）：**

- **v0.1 为单作者模式（Single-Author）**：一个 Project 归属一位作者，所有编辑、AI 协作、版本控制均在作者本地完成。系统不为多人协同设计锁机制、冲突仲裁或权限模型。
- 协作需求由 **Git 分支 + Merge** 间接满足——作者可在不同分支尝试不同剧情线，通过标准 Git 工作流合并。这是 Local First（3.5）与 Git Friendly（3.7）的自然延伸，而非内置的实时协同。
- 多人实时协同编辑（类似 Google Docs）**明确排除在 v0.1 范围外**，未来是否支持由后续 RFC 决定。

# 6. Core Concepts（核心概念）

| 概念                      | 说明                                                         |
| :------------------------ | :----------------------------------------------------------- |
| **Project**               | 一本小说。Project 是所有数据的根。                           |
| **Story**                 | Project 内真正维护的数据。Story 不等于 Markdown。            |
| **Story IR**              | Story 的标准表示（结构化数据，如 AST 与关系图）。所有模块共享同一个 Story IR。 |
| **Knowledge Layer**       | Story IR 与 Compiler 之间的一层，表示故事中**可被推理和验证的知识**。由 **Knowledge Base**（已提交断言的集合，Source of Truth）构成。引入此层使"哪些事实可被检查"从隐式假设变为显式、可版本化的产物。详见 RFC-0015。 |
| **Assertion**             | Knowledge Layer 的基本记录：一条可验证的命题，形如"主体 在 时间T 具有 属性P = 值V"，带 **Validity Window**（valid_from / valid_until）与 **Evidence**（文本证据）。正式术语用 Assertion；"Fact" 为非正式同义词——提交时刻它只是 claim，是否为真由 Compiler 判定。 |
| **Evidence**              | 一条断言的文本依据，复用 Location Index 的锚点定位指回源文本块并摘录原文。**无 Evidence 的断言不可提交。** |
| **Extraction**            | 从 Story IR（及源文本）生成候选断言的过程，可由 AI 或人工完成。与 Agent Change 共享"生成 → Dry-Run → 提交"模式：候选断言须经 Commit Gate（Compiler Dry-Run）方可合入 Knowledge Base。 |
| **Parser**                | 将原始文本（Markdown / YAML Frontmatter）解析为 Story IR 的模块。Parser 是 Compiler 的前置依赖。 |
| **Reference Index**       | 以 Stable ID 为第一性的实体间引用图谱。记录"角色 A 出现在哪些场景""场景 X 引用了道具 Y"等**实体 ↔ 实体**关系。**取代传统 Source Map**——定位的第一性是 ID 与引用，而非行/列坐标。 |
| **Location Index**        | **派生缓存**（非 Source of Truth）。Parser 扫描源文本中的锚点（如 `<!-- @scene: ch3s2 -->`）构建 `实体 ID → (文件, 块/段落)` 映射。粒度为块/段落而非行，不提交 Git，可随时重建。用于编辑器跳转与诊断定位。 |
| **Compiler**              | 负责**确定性**的一致性检查，读取 **Story IR**（结构）与 **Knowledge Base**（命题）两个输入，并产出 Diagnostics。不处理语义判断（见 Semantic Validator）。 |
| **Semantic Validator**    | 基于 AI 的语义检查层，负责 Compiler 无法判定的文学判断（伏笔回收、语气一致、称谓得当等），产出非阻断的 Hint / Suggestion。**仅消费 Compiler 的 Error / Warning 作为输入上下文，不消费自身输出**——其输出是诊断链的终点，不触发新一轮 Validator 运行，避免循环递归。运行时机由用户手动触发或 Agent 提交 Change 时附带触发，不自动级联。确定性 Compiler 与 Semantic Validator 共同构成完整的 Diagnostics 来源。 |
| **Diagnostics**           | Compiler 与 Semantic Validator 的共同输出，包括 Error（仅来自 Compiler，阻断）, Warning, Hint, Info。 |
| **Change (Patch)**        | 对 Story IR 的原子化变更描述（如 `InsertScene`, `UpdateCharacter`, `MoveChapter`）。所有模块（包括 Agent）**只能**通过提交 Change 来修改 Project，不得直接覆写 IR。 |
| **Agent**                 | 完成某项特定写作或编辑任务的 AI 单元。Agent 不直接修改 Project，只能生成并提交 Change 序列。 |
| **Assertion (Dry-Run)**   | 位于 Agent Runtime 内部的检查层。Agent 生成的 Change 必须经由 Compiler 的轻量级试运行（Dry-Run）验证，仅当无 Error 级别诊断时方可正式提交。注意：Dry-Run 只保证**结构安全**，不保证语义质量。 |

**数据流分层（每一层单一职责）：**

| 层 | 职责 | 确定性 |
|:--|:--|:--|
| **Parser** | 理解文本结构 | 确定 |
| **Story IR** | 表示故事结构 | 确定 |
| **Knowledge Layer** | 表示可推理、可验证的知识（断言 + 证据） | 提交后确定（Extraction 非确定） |
| **Compiler** | 验证知识之间是否一致 | 永远确定 |

**关键依赖流向：**

1. **Parser** 必须先于 Compiler 存在，否则 Compiler 无 IR 可查。
2. **Knowledge Layer** 位于 Story IR 与 Compiler 之间：Extraction 从 IR + 源文本生成候选断言，经 Commit Gate（Dry-Run）后合入 Knowledge Base，供 Compiler 检查时序 / 逻辑一致性。详见 RFC-0015。
3. **Compiler 读取两个输入**：Story IR（结构一致性）+ Knowledge Base（命题一致性）。
4. **Editor** 依赖 Reference Index（实体定位）与 Location Index（跳转到文本块）；Diagnostics 定位到实体 ID + 块，而非行坐标。
5. **Agent** 提交的 Change 必须经过 Compiler 的 Dry-Run 校验（Error = 0），通过后方可合入 Project Storage。Extraction 与 Agent Change 共享同一套"生成 → Dry-Run → 提交"模式。
6. **Diagnostics 有三个去向**：(a) 回流 Editor 展示诊断划线；(b) 反馈 Agent 触发重试/修正；(c) 作为上下文输入给 Semantic Validator。**Semantic Validator 的输出（Hint / Suggestion）是诊断链的终点，不再触发新一轮 Validator 运行**，避免循环递归。
7. **Change 是闭环**：经 Assertion 校验通过后，Change 合入 Project，触发 Parser 增量解析回到 IR，形成完整回路。
8. **Export 只读 IR**，不参与 Change 提交，不修改 Project 状态。
9. **Export 的只读契约**：Export 所需的所有渲染信息（章节编号、页码、目录层级等）均在 Export 管道内计算，**不写回 IR**。若需要缓存渲染中间结果（如 Render Context），存放于 `/.novelstudio/cache/`，不提交 Git。Story IR 的 Core Schema 不为任何特定导出格式（EPUB / PDF）预留渲染专用字段。

# 8. Development Principles（开发原则）

鉴于 Parser 是 Compiler 的必要前置依赖，原开发顺序存在逻辑倒置风险。现修订为以下严格顺序：

| 阶段         | 产出 / 目标                                                  | 关键 RFC           |
| :----------- | :----------------------------------------------------------- | :----------------- |
| **第一阶段** | **Story IR 数据结构 + Project Format**（定义 Schema、文件目录规范） | RFC-0002, RFC-0003 |
| **第二阶段** | **Parser**（将 Markdown / YAML 转化为 IR，建立 Reference Index 与 Location Index 基底） | RFC-0006           |
| **第三阶段** | **Entity Models**（Scene / Character / World / Timeline 的 IR 实体定义）——**必须在 Compiler 之前完成**，否则 Compiler 无实体可查 | RFC-0007, RFC-0008, RFC-0014, RFC-0009 |
| **第四阶段** | **Knowledge Layer**（Assertion / Evidence 模型 + Commit Gate + 手动 Extraction）——**必须在 Compiler 之前完成**，否则 Compiler 无可验证的命题可查 | RFC-0015 |
| **第五阶段** | **Compiler + Diagnostics**（读取 IR + KB，执行结构与时序检查） | RFC-0004, RFC-0005 |
| **第六阶段** | **Editor 核心**（基于 Reference Index + Location Index 实现文本编辑、高亮、诊断划线） | 实现层（消费第三阶段的 Entity Model，无独立 RFC） |
| **第七阶段** | **Agent Runtime + Assertion**（包括上下文构建、Dry-Run、Change 提交；AI Extraction 随此阶段落地） | RFC-0010, RFC-0015 |
| **第八阶段** | **Plugin System**                                            | RFC-0011           |
| **第九阶段** | **Exporter**（输出 EPUB, PDF, Markdown 等）                  | RFC-0013           |

**铁律：** 任何功能模块不得绕过 Story IR 直接操作文本文件。

> **Editor 的边界细化（区分实时缓冲区与已保存状态）：**
> - **实时缓冲区（In-Memory Draft）**：Editor 在内存中维护用户正在编辑的文本，按键仅更新 UI，**不受铁律约束**——实时编辑不经过 Parser / Compiler，否则会卡顿（见 9.1 实时编辑层级）。
> - **已保存状态（Persisted State）**：一旦文本落盘（保存 / AI 提交 Change），**铁律立即生效**——该文本必须经过 Parser 重建为 IR，并经 Compiler 验证，方可视为 Project 的合法状态。
>
> 即：铁律约束的是**持久化边界**，不是每一次按键。未保存的缓冲区允许暂时脱离 IR。

# 9. Critical Clarifications（关键澄清与补充）

## 9.1 关于 Change (Patch) 与 Git 友好性

为了实现 Git Friendly 与 Deterministic，所有对 Project 的修改（无论是用户手动编辑还是 AI 生成）最终在逻辑层均表示为 **原子操作序列（Patch）**。

用户编辑分三个层级，避免与 10.1 / 10.3 的增量解析表述产生歧义：

- **实时编辑（in-memory）**：Editor 在内存中维护当前打开文件的文本缓冲区。用户的每次按键**仅更新 UI 渲染，不触发任何 Parser 或 Compiler**（避免卡顿）。
- **保存时增量（Ctrl+S）**：触发 Parser 的增量解析（仅重算当前修改的文件及其依赖块），生成新的局部 IR，随后触发 Compiler 的增量诊断（仅检查受波及的实体）。增量解析的算法与边界由 RFC-0006 与 RFC-0004 定义。
- **全量重建（手动 / 自动）**：用户可手动触发"重新编译整个项目"，或由系统在检测到缓存失效（如切换分支、合并冲突后）时自动触发。

- **AI 编辑**：Agent 直接生成 Change 序列（不经过 Editor 的实时编辑路径）。
- **存储层**：Change 在保存时可以合并为新的文本文件版本，但 IR 层始终以 Patch 为基础进行状态演化。

此举可确保即使 AI 具有非确定性，最终落盘的文本文件依然具备人类可读的 Diff，且不同分支的 Merge 冲突局限于特定 Scene 或 Block，而非全局 JSON 冲突。

## 9.2 关于 AI 非确定性与系统确定性的调和

系统哲学要求 **Deterministic**（3.8），但 LLM 本质是概率性的。

**解决方案：**
引入 **Assertion (Dry-Run) 层**（见第 7 节架构图）。

1. Agent 生成候选 Change 后，**并不直接写入 Project**。
2. 系统在内存中基于当前 IR 应用该 Change，形成临时 IR（Draft）。
3. Compiler 对 Draft IR 执行全量或增量诊断。
4. 若诊断结果为 **Error = 0**，则允许提交；若存在 Error，则连同 Diagnostics 反馈给 Agent，要求其重试或修正。
5. 最终保证 **任何一次成功的 Commit，其对应的 IR 状态都经过 Compiler 的确定性验证**。

> **Dry-Run 的定位是"必要但不充分"。**
> 它只校验 3.4 定义的结构与时序层（Error 级），**不保证语义质量**。一个逻辑通顺但伏笔全丢、人称错乱、与既有文风冲突的改动可以轻松通过 Dry-Run。语义层的质量保证由 **Semantic Validator** 负责产 Hint / Suggestion，以及 **人工 Review** 最终把关，二者在 RFC-0010（AI Runtime）中单独设计。Error = 0 不等于"这版改得好"，只等于"这版改完后结构没坏"。
>
> **Validator 不自动级联。** Semantic Validator 仅消费 Compiler 产出的 Error / Warning 作为上下文，不消费自身输出；其产出的 Hint / Suggestion 是诊断链的终点，不触发新一轮 Validator 运行，避免循环递归。

## 9.3 关于 Knowledge Layer 与非确定性隔离

3.8 要求 Compiler 永远确定。但如果 Compiler 直接面对非结构化文本，它要么放弃确定性（调用 AI），要么放弃深度（只查结构）。Knowledge Layer 的引入使 Compiler 的确定性承诺第一次**真正成立**：

```text
Extraction（文本 → 断言）：AI 驱动，非确定    ← 关在这里
        ↓ commit（带 Evidence，过 Dry-Run）
Knowledge Base（已提交断言）：确定输入
        ↓
Compiler（验证断言一致性）：确定              ← 永远确定
```

这与 9.2 的 Agent Dry-Run **完全对称**：

| 管线 | 生成（非确定） | 提交门（确定） | 提交后（确定） |
|:--|:--|:--|:--|
| **Agent Change** | AI 生成 Change | Compiler Dry-Run | IR |
| **Extraction** | AI 生成 Assertion | Compiler Dry-Run | Knowledge Base |

两条管线同构：生成的环节允许非确定，但一旦提交，下游验证永远确定。详细设计见 RFC-0015。

## 9.4 关于 Plain Files 的存储边界与缓存

遵循 3.6 Plain Files，所有核心数据以文本形式存储。但 Story IR 中的**派生索引**（如角色出场次数、双向关系索引）若存为文本会导致性能低下。

**存储策略明确如下：**

- **主干数据（Source of Truth）**：
  - `/chapters/`, `/characters/`, `/world/` 等目录下的 Markdown / YAML 文件（含 ID 锚点）。
  - `/knowledge/` 目录下的 **Knowledge Base**（断言 + 证据，详见 RFC-0015）。
  - 二者均提交 Git。
- **派生缓存（Derived Cache）**：由 Compiler 生成的中间索引、Embedding 向量、反向索引、**Location Index（实体 ID → 文本块定位）** 等，存放于 `/.novelstudio/cache/` 目录，**不提交 Git**，可随时由 Compiler 重新构建。

### SQLite 派生查询层（未来扩展）

随着项目复杂度提升（数千 Fragment、数百 Entity、上千 Assertion），BTreeMap 遍历式的关联查询可能成为瓶颈。未来可引入 SQLite 作为**派生查询缓存**：

```text
   TOML 文件（SoT，进 Git）
         │
         ▼ Compiler 解析
   .novelstudio/cache/compiler.db（SQLite，派生缓存，不进 Git）
```

**设计约束：**

- **TOML 永远是 Source of Truth**——SQLite 只是从 TOML 派生的查询优化层，不存储任何原始数据。
- **SQLite 可随时重建**——删除 `compiler.db` 后重新编译即可重建，不丢失任何信息。
- **不替代 TOML**——数据的编辑入口始终是 TOML 文件，SQLite 是只读缓存。
- **触发条件**：当 Fragment > 2000 或 Entity > 500 或 Assertion > 1000 时自动启用，小项目保持 BTreeMap 内存遍历。
- **存放于 `.novelstudio/cache/`**——与其他派生缓存同级，不进 Git。

> **何时实现**：当实际 benchmark 显示 Compiler 单次全量编译 > 5 秒，或 Editor 需要高频查询（每次按键都查数据）时。v0.1 不实现——避免过早优化。在类型接口（IR / Thread / Mechanics）稳定之前不固化 SQLite schema。

### 向量缓存层（未来扩展）

随着 AI 辅助创作的深入，语义检索（RAG）将成为关键能力。未来可引入向量数据库作为**派生语义缓存**：

```text
   TOML 文件（SoT，进 Git）
         │
         ▼ Parser（确定性）
   Story IR（内存）
         │
         ▼ Embedding Model（非确定，AI Runtime 负责）
   .novelstudio/cache/vectors/（向量缓存，派生，不进 Git）
         │
         ▼ 语义检索
   AI Runtime Context Builder（构建 Prompt 时检索相关段落）
   Semantic Validator（伏笔回收检测、矛盾检测）
```

**设计约束：**

- **TOML 永远是 SoT**——向量是从文本派生的语义索引，不存储原始数据。
- **向量可随时重建**——删除后重新跑 Embedding 即可重建。
- **Compiler 不读向量**——Compiler 保持纯确定性（§3.8），不消费任何向量数据。只有 Semantic Validator（AI 驱动、产出非阻断 Hint）消费向量。这条确定性边界不可打破。
- **非确定性隔离**——Embedding 生成属于 AI Runtime 层（§9.2），其非确定性被限制在 AI Runtime 内部，不影响下游确定性检查。
- **存放于 `.novelstudio/cache/vectors/`**——与其他派生缓存同级，不进 Git。

**应用场景：**

| 场景 | 消费方 |
|:--|:--|
| AI 上下文检索（RAG）——从数千 Fragment 中检索最相关段落 | AI Runtime Context Builder |
| 语义搜索——"找到和这段氛围相似的场景" | Editor / Graph |
| 伏笔回收检测——判断伏笔是否在语义层面被回收 | Semantic Validator（Hint 级） |
| 矛盾检测——"这段和前面的描述矛盾" | Semantic Validator（Hint 级） |

> **何时实现**：当 Fragment > 1000 且 AI 上下文需要 RAG 检索时。v0.1 不实现——Embedding 依赖外部模型，应等 AI Runtime 的 Provider 层（RFC-0010）成熟后再接入。

# 10. Performance Consideration（性能考量）

长篇小说（百万字级）的全量编译可能产生数秒延迟。

在本 RFC 阶段，明确以下设计约束：

- 第一阶段 IR 设计必须预留 **Version / Revision** 字段，以便后续（不迟于 RFC-0004）支持 **增量编译（Incremental Compilation）**。
- v0.1 版本（MVP）可仅支持全量编译，但架构上不得阻碍未来引入 Dirty-Tracking 机制。
- Parser 必须支持**流式/分块解析**，以避免大文件 OOM。

## 10.1 放弃 Source Map：改用 Reference Index + 锚点驱动定位

### 动机

传统 Source Map（实体 ↔ 行/列坐标的双向映射）在 Markdown 小说场景下有两个致命问题：

- 作者随意重排段落、软换行，**行号 / 列号极易漂移**。
- AI 生成的文本**不保证保留换行结构**，坐标无法对齐。

维护双向行级 Source Map 的工程成本与脆弱性远超收益，故 **v0.3 起明确放弃该方案**。

### 替代方案：Stable ID + 锚点驱动定位

定位的**第一性是 Stable ID 与实体间引用**，而非文本坐标。具体分三层：

**① Reference Index（实体 ↔ 实体，主干）**

每个实体有稳定 ID（如 `char:linxia`、`scene:ch3s2`）。Parser 解析时构建引用图谱：

```
char:linxia ──appears in──► scene:ch3s2, scene:ch3s3, scene:ch5s1
scene:ch3s2 ──references──► item:umbrella, loc:riverside
```

Reference Index 是 Story IR 的一部分，随主干数据一起演化，**是实体定位的核心**。

**② Location Index（实体 → 文本块，派生缓存）**

Parser 扫描源文本中的锚点，构建 `实体 ID → (文件, 块/段落)` 的映射：

```markdown
## 第三章 雨夜
<!-- @scene: ch3s2 -->

林夏推开门，雨水顺着她的发梢滴落。
```

该映射：
- **粒度为块 / 段落，而非行** → 段内微调不漂移。
- **是派生缓存**（符合 9.3）→ 不提交 Git，可随时重建。
- **不要求 AI 保持行结构** → 只要求保留 ID 锚点。

**③ 诊断定位到块**

Diagnostic 报"角色 X 年龄矛盾 @ `ch3.md @scene:ch3s2`"，跳转到场景块而非行号。精度为段落级，已足够可用。

### 三个关键设计决定

| 决定 | 选择 | 理由 |
|:--|:--|:--|
| **锚点粒度** | 逐块（场景 / 段落开头一个锚点） | 逐句标注污染重、负担大；段落级诊断已够用 |
| **实体识别** | 默认隐式（名字 / 别称匹配）+ 关键节点显式 | 零负担覆盖常规出场；首次出现 / 状态变更 / 死亡等关键点要求显式锚定 |
| **锚点缺失** | 报 Warning | 场景块缺少 `@scene:` 锚点时，由 Compiler 产出非阻断诊断，提示补全 |

### 与原方案的对比

| 维度 | 原 Source Map | 新 Reference Index + Location Index |
|:--|:--|:--|
| 定位第一性 | 行 / 列坐标 | Stable ID |
| 漂移风险 | 高（段内微调即失效） | 低（定位到块） |
| AI 友好性 | 要求保持行结构 | 仅要求保留 ID 锚点 |
| Git | 坐标进 Diff（噪声） | 锚点进 Diff（语义化） |
| 维护成本 | 双向增量更新，脆弱 | 派生缓存，按需重建 |

详细 schema 与锚点语法由 RFC-0006（Parser）与 RFC-0002（Story IR）共同定义。

## 10.2 增量编译的全局依赖风险

代码编译器中"改一个文件只重编依赖项"的假设，在小说一致性场景下**可能失效**：

- 小说的依赖图接近**全连通**——第 3 章改死一个角色，会使第 50 章的相关诊断全部失效。
- Dirty-Tracking 在这种场景下可能退化为全量编译。

v0.1 不强行实现增量编译，但需在 RFC-0004（Compiler）设计时明确**依赖粒度与失效边界**，避免照搬代码编译器策略。

**v0.1 折中策略（两层引用 + Stale 标记）：**

鉴于小说依赖图接近全连通，采用**深度受限的失效传播**而非全量重编：

| 层级 | 范围 | 处理方式 |
|:--|:--|:--|
| **第 0 层** | 发生变更的实体本身（如被编辑的场景 / 角色） | 立即重算诊断 |
| **第 1 层** | 直接引用该实体的实体（同文件内引用 + 跨文件一层引用） | 增量重算诊断 |
| **第 2 层及以上** | 间接依赖（引用的引用……） | **标记为 Stale**，不立即重算，仅在用户保存 / 手动全量编译时才更新 |

- **Stale 标记不阻断编辑**：被标记的实体在 UI 上以灰色 / 虚线诊断提示"可能已过期"，但不阻塞保存或 Change 提交。
- **收益**：将最坏情况从"全连通图全量重编"降为"两层局部重编 + 一批 Stale 标记"，在准确性与响应速度间取得平衡。
- **局限**：存在窗口期——第 2 层以上的诊断可能短暂过时，直到下次全量编译才纠正。这是 v0.1 明确接受的 trade-off。

## 10.3 Editor 实时编辑的增量解析需求

第 8 节铁律已细化（见上）：**实时缓冲区不受铁律约束，仅"已保存状态"强制走 Parser → Compiler**。因此 Editor 的性能压力集中在"保存时增量"这一刻，而非每次按键。

**设计约束：**

- Parser 必须支持**编辑增量解析**（Incremental Parse），仅重算受影响块，服务于 9.1 定义的"保存时增量"层级。
- 10 节已要求的"流式 / 分块解析"同样服务于此目标。
