# 1. Abstract（摘要）

Diagnostics 是 Story Studio 中所有"检查结果"的统一表示。Compiler 产出 Error / Warning，Semantic Validator 产出 Hint / Suggestion，Parser 产出解析错误——它们都汇聚为同一种 Diagnostic 结构。

```text
   Compiler           Semantic Validator       Parser
      │                     │                    │
      │ Error/Warning       │ Hint/Suggestion    │ Error/Warning
      ▼                     ▼                    ▼
   ┌─────────────────────────────────────────────────┐
   │              Diagnostics（统一结构）              │
   └──────────────────────┬──────────────────────────┘
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
          Editor       Agent       Export
        (划线/跳转)   (反馈重试)   (阻断导出)
```

本 RFC 统一定义 Diagnostic 的结构、严重级别、定位模型、生命周期，以及 QuickFix 与抑制机制。

# 2. Severity（严重级别）

## 2.1 四级体系

| 级别 | 含义 | 谁能产出 | 阻断行为 |
|:--|:--|:--|:--|
| **Error** | 必须修复的不一致（结构损坏、时序矛盾） | **仅 Compiler + Parser** | 阻断 Dry-Run、阻断 Export |
| **Warning** | 建议修复的问题（证据失配、孤儿引用） | Compiler + Parser | 不阻断，但 Editor 高亮提示 |
| **Hint** | 建议性提示（风格、约定） | Compiler（Style Phase）+ Semantic Validator | 不阻断，可选展示 |
| **Info** | 信息性说明 | 任何模块 | 不阻断，默认隐藏 |

## 2.2 权限矩阵

> **核心约束：Semantic Validator 永远不产 Error。**

只有确定性模块（Compiler / Parser）能产出 Error。这保证了"阻断提交"的决定永远来自确定性检查，而非 AI 的概率判断。

| 产出者 | Error | Warning | Hint | Info |
|:--|:--|:--|:--|:--|
| Parser | ✅ | ✅ | ✅ | ✅ |
| Compiler | ✅ | ✅ | ✅ | ✅ |
| Semantic Validator | ❌ | ❌ | ✅ | ✅ |

> Semantic Validator 只产 Hint / Info（RFC-0001 §6 Core Concepts）。这维护了确定性边界——任何阻断性判断都来自确定性检查。

## 2.3 级别覆盖

作者可通过 `config/compiler.toml`（RFC-0003 §5.6）覆盖规则的默认级别：

```toml
# 将默认 Warning 提升为 Error
[severity_overrides]
item_disappeared = "error"

# 将默认 Error 降级为 Warning（谨慎！）
# dead_character_revived = "warning"
```

**限制：** Semantic Validator 产出的 Hint **不可被提升为 Error**——配置覆盖只作用于 Compiler 规则。这防止了"用配置绕过确定性边界"。

# 3. Diagnostic Structure（诊断结构）

## 3.1 核心结构

```rust
/// 一条诊断——所有检查结果的统一表示
pub struct Diagnostic {
    /// 产出此诊断的规则 / 模块标识
    pub source: DiagnosticSource,

    /// 严重级别
    pub severity: Severity,

    /// 诊断的分类码（稳定标识，用于抑制 / 过滤）
    pub code: DiagnosticCode,

    /// 人类可读的描述（中文）
    pub message: String,

    /// 定位（实体 / Fragment / 断言，块级）
    pub loc: SourceLocation,

    /// 生命周期标记（增量编译用）
    pub lifecycle: Lifecycle,

    /// 可选的快速修复建议
    pub quickfixes: Vec<QuickFix>,
}
```

## 3.2 DiagnosticSource

标识诊断的产出者：

```rust
pub enum DiagnosticSource {
    /// Parser 产出的解析错误
    Parser,
    /// Compiler 的具体规则（携带 rule_id）
    Compiler { rule_id: String },
    /// Semantic Validator（携带 validator 名称）
    SemanticValidator { name: String },
}
```

## 3.3 DiagnosticCode

每条诊断携带稳定的分类码，用于抑制（§6）与统计：

```rust
/// 诊断分类码——格式：模块前缀 + 动作
/// 稳定标识，不随 message 变化
pub struct DiagnosticCode(String);

// 示例：
// "parse.id_mismatch"          — Parser: id 不匹配
// "compile.dead_revived"       — Compiler: 死人复活
// "compile.age_inconsistency"  — Compiler: 年龄矛盾
// "semantic.foreshadow_lost"   — Semantic Validator: 伏笔丢失
```

Code 的稳定性保证了：抑制规则与历史统计不会因 message 措辞调整而失效。

# 4. Source Location（定位模型）

## 4.1 块级定位，非行级

遵循 RFC-0001 §10.1 的锚点驱动定位，诊断定位到**块 / 实体级**，不到行号：

```rust
pub struct SourceLocation {
    /// 涉及的 Semantic 实体（如出错的角色 / 道具）
    pub entity: Option<StableId>,

    /// 涉及的 Fragment（文本块定位）
    pub fragment: Option<StableId>,

    /// 涉及的断言（KB 相关诊断）
    pub assertion: Option<StableId>,

    /// 涉及的结构节点（Chapter / Scene）
    pub structure: Option<StableId>,
}
```

**定位优先级**（Editor 跳转时）：

1. 若有 `fragment` → 跳转到该 Fragment 块（通过 Location Index）
2. 若有 `entity` → 跳转到该实体的 Entity 文件
3. 若有 `assertion` → 跳转到 KB 中的断言条目
4. 若有 `structure` → 跳转到 structure.toml 对应位置

> **为什么不到行号？** RFC-0001 §10.1 已论证：Markdown 行号极易漂移，AI 不保持换行结构。块级定位通过 StableId + 锚点，稳定且可跳转。

## 4.2 多定位

某些诊断涉及多个位置（如"角色 A 在 f_0001 死亡，但在 f_0042 仍出场"）。此时用主定位 + 相关定位：

```rust
pub struct Diagnostic {
    pub loc: SourceLocation,           // 主定位（跳转目标）
    pub related: Vec<RelatedLocation>, // 相关定位（辅助信息）
}

pub struct RelatedLocation {
    pub loc: SourceLocation,
    pub label: String,                 // 如"死亡发生处"、"复活发生处"
}
```

# 5. Lifecycle（生命周期）

## 5.1 三态

增量编译（RFC-0004 §7）中，诊断有三种生命周期状态：

```rust
pub enum Lifecycle {
    /// 本次编译新产出或确认的诊断（最新）
    Fresh,

    /// 增量编译未重新检查，但可能已过时
    /// UI 以灰色 / 虚线展示
    Stale,

    /// 本次编译确认已不存在（问题已修复）
    /// Editor 可播放消失动画后移除
    Resolved,
}
```

## 5.2 状态转移

```text
   ┌──────────────────────────────────┐
   │                                  │
   ▼                                  │
 Fresh ──增量未命中──► Stale ──全量──► (重新检查)
   │                     │               │
   │                     │          ┌────┴────┐
   │                     │          ▼         ▼
   │                   仍有问题   Fresh    Resolved
   │                                ▲         │
   │                                │         │
   └──────── 增量命中 ──────────────┘         │
                                              │
   问题已修复 ──────────────────────────────► │
```

| 转移 | 触发 |
|:--|:--|
| Fresh → Stale | 增量编译时，诊断所属规则未重新执行（Dirty Set 未命中） |
| Stale → Fresh | 全量编译或增量命中后重新检查，确认问题仍在 |
| Stale → Resolved | 全量编译确认问题已消失 |
| Fresh → Resolved | 增量命中后重新检查，发现问题已修复 |

## 5.3 Resolved 的 UI 处理

- Resolved 诊断不是立即删除，而是标记后由 Editor **短暂展示**（如绿色淡出动画），给作者"问题已解决"的反馈。
- 下一次编译周期开始时，Resolved 诊断从结果集中移除。

# 6. Suppression（抑制机制）

作者可抑制特定诊断，类似 `eslint-disable`。

## 6.1 内联抑制

在 Fragment 文件中用特殊注释抑制：

```markdown
<!-- fragments/f_0042.md -->
---
id: f_0042
anchors:
  - entity: c_8A91D4
    role: appears
---

<!-- diagnostic-suppress: compile.dead_revived -->
<!-- 原因：这是回忆场景，角色已死亡但以回忆形式出场 -->

林风站在雨中，回忆起那天的情形……
```

- 抑制作用于**当前 Fragment**，只抑制指定 code。
- 抑制必须提供注释原因（鼓励记录"为什么抑制"）。
- 被抑制的诊断不产出（不进 Diagnostics），但 Compiler 记录抑制事实（可用于审计）。

## 6.2 全局抑制

在 `config/compiler.toml` 中全局禁用规则（RFC-0003 §5.6）：

```toml
[rules]
# 完全禁用某规则
dead_character_revived = "off"
```

**内联 vs 全局的区别：**

| | 内联抑制 | 全局禁用 |
|:--|:--|:--|
| 作用范围 | 单个 Fragment | 整个 Project |
| 粒度 | 单条 code | 整条规则 |
| 需要原因 | ✅（注释） | ❌ |
| 审计可见 | ✅（在文件中） | 需查看 config |

## 6.3 安全约束

> **Error 级诊断不可被内联抑制。**

只有 Warning / Hint / Info 可被内联抑制。Error 代表结构损坏或时序矛盾，抑制它会让 Dry-Run 通过一个实际有问题的 IR——这破坏了整个安全网。

若作者确实要让"死人复活"合法（回忆场景），正确做法是：在 Knowledge Layer 中为该场景标注 `alive: true (回忆)` 的 valid 窗口，而非抑制诊断。

```rust
/// 检查抑制是否合法
fn can_suppress(code: &DiagnosticCode, severity: Severity) -> bool {
    // Error 不可被内联抑制
    severity != Severity::Error
}
```

> **全局禁用 Error 规则**（`rule = "off"`）在技术上是允许的，但 Compiler 会产出一条特殊的 Info 级 Meta-Diagnostic："规则 X 已被全局禁用"，提醒作者安全网有缺口。

# 7. QuickFix（快速修复）

诊断可携带建议的修复操作，供 Editor / Agent 一键应用。

## 7.1 结构

```rust
/// 一条快速修复建议
pub struct QuickFix {
    /// 修复的标题（展示给作者）
    pub label: String,

    /// 修复方式
    pub action: QuickFixAction,

    /// 置信度（是否需要作者确认）
    pub confidence: FixConfidence,
}

pub enum QuickFixAction {
    /// 提交一个 Change（走 Dry-Run 验证后应用）
    ApplyChange(Change),

    /// 跳转到相关位置（让作者手动修）
    NavigateTo(SourceLocation),

    /// 建议在 KB 中添加一条断言
    SuggestAssertion(AssertionDraft),
}

pub enum FixConfidence {
    /// 高置信度：可直接应用（如修复引用断裂）
    Safe,
    /// 需作者确认：应用前需人工 Review
    NeedsConfirmation,
}
```

## 7.2 什么样的诊断适合 QuickFix

| 诊断类型 | QuickFix 示例 | 置信度 |
|:--|:--|:--|
| 引用断裂（anchor 指向不存在的 Entity） | "创建缺失的 Entity" 或 "移除 anchor" | Safe |
| 孤儿 Fragment（未被 structure.toml 引用） | "将此 Fragment 加入 Scene X" | NeedsConfirmation |
| 年龄矛盾（两条断言冲突） | "查看两条断言的证据" (NavigateTo) | NeedsConfirmation |
| 死人复活 | "在 KB 中标注回忆场景" (SuggestAssertion) | NeedsConfirmation |
| 缺失锚点 | "为 Fragment 添加 @entity 标注" | NeedsConfirmation |

> **QuickFix 不自动执行**——即使是 Safe 级别也需作者点击确认。QuickFix 是"建议操作"，不是"自动修复"。所有 QuickFix 若涉及 Change，都走正常的 Dry-Run 流程。

## 7.3 谁产出 QuickFix

| 产出者 | 能否产 QuickFix |
|:--|:--|
| Compiler 规则 | ✅（确定性修复，如引用断裂） |
| Parser | ✅（如 id 不匹配时建议重命名） |
| Semantic Validator | ✅（但需标注 NeedsConfirmation） |

# 8. Diagnostic Collection & Sorting（收集与排序）

## 8.1 DiagnosticSink

RFC-0004 §3.2 定义的 DiagnosticSink 负责收集与排序：

```rust
pub struct DiagnosticSink {
    diagnostics: Vec<Diagnostic>,
}

impl DiagnosticSink {
    pub fn push(&mut self, diag: Diagnostic) {
        self.diagnostics.push(diag);
    }

    /// 排序后输出——确定性排序
    pub fn into_diagnostics(self) -> Diagnostics {
        let mut diags = self.diagnostics;
        // 排序键：severity（Error 优先）→ location → code
        diags.sort_by(|a, b| {
            a.severity.cmp(&b.severity)
                .then(a.loc.cmp(&b.loc))
                .then(a.code.0.cmp(&b.code.0))
        });
        Diagnostics(diags)
    }
}
```

## 8.2 确定性排序

排序必须确定（RFC-0004 §8），保证同一 IR 的诊断列表顺序一致：

1. **Error 优先**于 Warning 优先于 Hint
2. 同级别内按 SourceLocation 排序
3. 同位置按 DiagnosticCode 字典序

## 8.3 去重

同一条诊断可能被多个编译周期产出。Diagnostics 集合对 `(source, code, loc)` 三元组去重：

```rust
fn deduplicate(diags: &mut Vec<Diagnostic>) {
    diags.dedup_by(|a, b| {
        a.source == b.source && a.code == b.code && a.loc == b.loc
    });
}
```

> 去重保证：同一位置的同一问题只展示一次，不因规则重复执行而堆叠。

# 9. Consumers（消费方）

诊断产出后，被多个模块消费：

## 9.1 Editor

- 展示诊断划线（Error 红色波浪线、Warning 黄色）
- 点击跳转到 SourceLocation
- 展示 QuickFix 建议
- Stale 诊断以灰色 / 虚线展示

## 9.2 Agent Runtime（Dry-Run 反馈）

- Dry-Run 失败时，Compiler 返回 Error 级诊断列表
- Agent 读取诊断的 message + loc，理解"哪里出了什么问题"
- Agent 据此修正 Change 并重试（RFC-0001 §9.2）

```rust
/// Agent 收到的 Dry-Run 反馈
pub struct DryRunFeedback {
    pub result: DryRunResult,       // Passed / Failed
    pub errors: Vec<Diagnostic>,    // 仅 Error 级
}
```

## 9.3 Export

- Export 前检查是否有 Error 级诊断
- **有 Error 则阻断导出**（可配置为允许带警告导出）

```rust
fn can_export(diagnostics: &Diagnostics, config: &ExportConfig) -> bool {
    let has_error = diagnostics.0.iter().any(|d| d.severity == Severity::Error);
    !has_error || config.allow_export_with_errors
}
```

# 11. Open Questions

1. **诊断的持久化**：诊断是否需要跨会话持久化（存 `.novelstudio/cache/`）？还是每次启动重新编译？（倾向：不持久化，重新编译。诊断是派生物，持久化会带来一致性问题。）
2. **诊断的国际化**：message 是否支持多语言？还是 v0.1 只支持中文？（倾向：v0.1 中文，code 是稳定标识不翻译。）
3. **抑制的嵌套**：内联抑制是否支持嵌套 Fragment（父 Fragment 抑制是否覆盖子 Fragment）？（倾向：不支持嵌套，每个 Fragment 独立。）
4. **QuickFix 的权限**：Semantic Validator 产出的 QuickFix 是否需要额外标注"AI 生成"？（倾向：是，区分确定性修复与 AI 建议。）

# Appendix

> **诊断是所有检查结果的统一表示。Error 只来自确定性模块，Semantic Validator 永不阻断。定位到块而非行，增量编译中 Fresh / Stale / Resolved 三态流转。Error 不可被内联抑制——安全网不允许自己打洞。**
