# 1. Abstract（摘要）

Compiler 是 Story Studio 数据流的第四层：读取 Story IR（+ Knowledge Base），执行**确定性的一致性检查**，产出 Diagnostics。

```text
   Story IR + Knowledge Base  ──Compiler──►  Diagnostics
   (结构 + 命题)                           (Error / Warning / Hint)
```

Compiler 是 Parser 的**对称镜像**：

| | Parser | Compiler |
|:--|:--|:--|
| 输入 | Project Format（文件） | Story IR + Knowledge Base |
| 输出 | Story IR | Diagnostics |
| 确定性 | 纯确定 | 纯确定 |
| 不做 | 推理 | AI 推理 |
| 职责 | **能否解析** | **是否合理** |

Compiler **永远是确定性的**。它不调用 AI，不做语义判断——那些是 Semantic Validator（RFC-0001 §3.4）的职责。

------

# 2. Responsibilities（职责边界）

## 2.1 Compiler 做什么

- 遍历 Story IR，检查结构一致性（引用完整、无环、ID 唯一等）
- 读取 Knowledge Base，检查命题一致性（矛盾、时序非法、状态冲突）
- 读取 Location Index，检查证据失配（断言的证据是否仍存在）
- 产出 Diagnostics（Error / Warning / Hint / Info）
- 提供 Dry-Run 能力：在 draft IR 上试运行，供 Agent / Extraction 的 Commit Gate 使用

## 2.2 Compiler 不做什么

| 不做的事 | 归属 | 理由 |
|:--|:--|:--|
| 语义判断（"这段伏笔是否回收"） | Semantic Validator（RFC-0001 §3.4） | 需要 AI，违反确定性 |
| AI 推理（"角色此刻的心理状态"） | Knowledge Layer inference | 非确定性 |
| 文本质量评估（"文笔好不好"） | Semantic Validator / 人工 Review | 主观判断 |
| 修改 IR | 无（Compiler 只读） | Compiler 是只读校验器，不产生副作用 |

## 2.3 与 Semantic Validator 的边界

RFC-0001 §3.4 定义了三层检查，Compiler 与 Semantic Validator 各管一层：

| 检查层 | 数据源 | 负责模块 | 确定性 | 级别 |
|:--|:--|:--|:--|:--|
| 结构 / 引用 | Story IR | **Compiler** | ✅ 确定 | Error |
| 时序 / 逻辑 | Knowledge Base | **Compiler** | ✅ 确定 | Error |
| 语义 / 文学 | IR + 文本 | Semantic Validator | ❌ 非确定 | Hint / Suggestion |

Compiler 产出 Error（阻断）与 Warning（非阻断）。Semantic Validator 只产 Hint / Suggestion（永远非阻断）。

# 3. Rule Architecture（规则架构）

## 3.1 统一 Rule 接口

每条检查规则实现统一的 `Rule` trait。规则**不返回 Diagnostic**，而是通过 `RuleContext` 的 `report()` 方法产出诊断（Sink 模式）。

```rust
/// 所有检查规则的统一接口
pub trait Rule {
    /// 规则的唯一标识（对应 config/compiler.toml 的 key）
    fn id(&self) -> &str;

    /// 默认严重级别
    fn default_severity(&self) -> Severity;

    /// 所属阶段（决定执行顺序，见 §3.4）
    fn phase(&self) -> RulePhase;

    /// 声明本规则依赖的数据维度（调度器据此决定是否执行）
    fn depends_on(&self) -> &[Dependency];

    /// 执行检查——通过 ctx.report() 产出诊断
    fn run(&self, ctx: &mut RuleContext);
}

pub enum Severity {
    Error,      // 阻断提交（Dry-Run 失败）
    Warning,    // 非阻断，提示作者
    Hint,       // 建议性
    Info,       // 信息性
}

/// 规则依赖的数据维度——简洁枚举，不做复杂 scope 拆分
pub enum Dependency {
    Structure,      // Document Graph 结构（Chapter/Scene/Fragment 层级、链表）
    Fragment,       // Fragment 正文内容
    Entity,         // Semantic Graph 实体节点
    Assertion,      // Knowledge Base 断言
    Knowledge,      // Knowledge Layer 推理结果（未来）
}
```

> **为什么用 ctx.report() 而非返回 Vec<Diagnostic>？** Sink 模式让规则可以在执行中产出多种结果（Diagnostic / QuickFix / Progress），且支持长任务的中途报告与取消。若用返回值，trait 签名会随功能增加不断膨胀。

## 3.2 RuleContext

规则通过 RuleContext 访问所有数据与服务。这个结构**现在就定全**，避免后续逐个加参数导致 trait 炸裂：

```rust
/// 规则执行上下文（一次性定义全，API 后续不再变）
pub struct RuleContext<'a> {
    // —— 数据访问（只读）——
    pub ir: &'a StoryIR,
    pub kb: Option<&'a KnowledgeBase>,
    pub derived: &'a DerivedIndexes,       // Location Index + Symbol Table + 等
    pub config: &'a CompilerConfig,

    // —— 执行控制 ——
    pub mode: CompileMode,
    pub request: &'a CompileRequest,       // 触发本次编译的请求（见 §4.1）

    // —— 产出（Sink 模式）——
    sink: &'a mut DiagnosticSink,
}

impl<'a> RuleContext<'a> {
    /// 产出诊断——规则的唯一输出方式
    pub fn report(&mut self, diag: Diagnostic) {
        self.sink.push(diag);
    }

    /// 便捷方法：报 Error
    pub fn error(&mut self, rule_id: &str, msg: impl Into<String>, loc: SourceLocation) {
        self.report(Diagnostic::error(rule_id, msg, loc));
    }

    /// 便捷方法：报 Warning
    pub fn warning(&mut self, rule_id: &str, msg: impl Into<String>, loc: SourceLocation) {
        self.report(Diagnostic::warning(rule_id, msg, loc));
    }
}

/// 派生索引集合——规则可按需访问
pub struct DerivedIndexes {
    pub location_index: Option<LocationIndex>,
    pub symbol_table: &'a SymbolTable,
    // 未来可扩展：mention_index, reverse_edges 等
}

/// 诊断收集器（Sink）
pub struct DiagnosticSink {
    diagnostics: Vec<Diagnostic>,
}

impl DiagnosticSink {
    pub fn push(&mut self, diag: Diagnostic) {
        self.diagnostics.push(diag);
    }
    pub fn into_diagnostics(self) -> Diagnostics {
        // 确定性排序（见 §8）
        let mut diags = self.diagnostics;
        diags.sort_by(|a, b| a.loc.cmp(&b.loc).then(a.rule_id.cmp(&b.rule_id)));
        Diagnostics(diags)
    }
}
```

## 3.3 Rule Phase（执行阶段）

规则不是全部塞进一个队列，而是分阶段执行。每个阶段的规则全部跑完后，才进入下一阶段：

```rust
pub enum RulePhase {
    /// 阶段 1：结构检查（IR Invariants、引用完整性）
    /// 必须先跑——若结构有 Error，后续阶段的规则拿到的是损坏的 IR
    Structure,
    /// 阶段 2：时序/逻辑检查（Knowledge Base 一致性）
    /// 依赖阶段 1 已确认结构合法
    Semantic,
    /// 阶段 3：风格/约定检查（命名规范、缺失标注等）
    /// 非阻断性，最低优先级
    Style,
}
```

**阶段顺序的必要性：**

- `DuplicateSymbol`（阶段 1）必须先于 `TimelineRule`（阶段 2）——后者需要通过 Symbol 解析实体，若 Symbol 冲突未先解决，Timeline 检查会拿到错误数据。
- 若阶段 1 产出 **Error**，阶段 2/3 仍可执行（产出更多诊断），但 Compiler 标记整体状态为"结构损坏"，Dry-Run 必定失败。

```rust
/// 调度器按阶段遍历
fn run_phases(&self, ctx_builder: impl Fn() -> RuleContext) {
    for phase in [RulePhase::Structure, RulePhase::Semantic, RulePhase::Style] {
        let rules_in_phase: Vec<_> = self.rules
            .iter()
            .filter(|r| r.phase() == phase)
            .collect();

        for rule in rules_in_phase {
            // 调度逻辑（增量/全量）见 §4
            if self.should_run(rule, ...) {
                let mut ctx = ctx_builder();
                rule.run(&mut ctx);
            }
        }
    }
}
```

## 3.4 RuleRegistry

```rust
/// 规则注册表——编译开始时构建
pub struct RuleRegistry {
    /// 按 phase 分组的规则
    rules_by_phase: BTreeMap<RulePhase, Vec<Box<dyn Rule>>>,
    config: CompilerConfig,     // 来自 config/compiler.toml
}

impl RuleRegistry {
    pub fn new(config: CompilerConfig) -> Self {
        let mut registry = Self { rules_by_phase: BTreeMap::new(), config };

        // 阶段 1：Structure
        registry.register(RulePhase::Structure, Box::new(IrInvariantChecker));
        registry.register(RulePhase::Structure, Box::new(OrphanReference));
        registry.register(RulePhase::Structure, Box::new(DuplicateSymbol));
        registry.register(RulePhase::Structure, Box::new(AnchorTargetExists));

        // 阶段 2：Semantic
        registry.register(RulePhase::Semantic, Box::new(AssertionContradiction));
        registry.register(RulePhase::Semantic, Box::new(DeadCharacterRevived));
        registry.register(RulePhase::Semantic, Box::new(AgeInconsistency));
        registry.register(RulePhase::Semantic, Box::new(ValidityWindowIllegal));
        registry.register(RulePhase::Semantic, Box::new(EvidenceMismatch));

        // 阶段 3：Style
        registry.register(RulePhase::Style, Box::new(MissingAnchor));
        registry.register(RulePhase::Style, Box::new(EmptyScene));

        registry
    }

    pub fn register(&mut self, phase: RulePhase, rule: Box<dyn Rule>) {
        self.rules_by_phase.entry(phase).or_default().push(rule);
    }
}
```

> **v0.1 不支持用户插件**，但 Rule trait 的抽象允许未来扩展为可插拔实现，无需修改 Compiler 主流程。插件规则的确定性约束由 RFC-0011 定义。

## 3.5 配置驱动

规则的启用 / 禁用 / 级别覆盖由 `config/compiler.toml` 控制（RFC-0003 §5.6）：

```rust
pub struct CompilerConfig {
    /// rule_id → 覆盖后的严重级别（None 表示用规则默认值）
    severities: BTreeMap<String, Severity>,
    /// 被禁用的规则 ID 集合
    disabled: BTreeSet<String>,
}

impl CompilerConfig {
    /// 查询某条规则的实际严重级别
    fn severity_of(&self, rule: &dyn Rule) -> Option<Severity> {
        if self.disabled.contains(rule.id()) {
            return None;  // 被禁用，不执行
        }
        Some(
            self.severities
                .get(rule.id())
                .copied()
                .unwrap_or_else(|| rule.default_severity()),
        )
    }
}
```

配置只控制**开关与级别**，不控制检查逻辑——逻辑由 Rule 的 Rust 实现决定。

# 4. Compile Model（编译模型与依赖调度）

## 4.1 核心思想

> **不要把问题定义成"全量还是增量"，也不要让 CompileEvent 直接决定 Rule 执行。**

正确的调度链路是：

```text
   CompileEvent（发生了什么）
         │
         ▼
   Dependency Resolver（传播：哪些数据失效了）
         │
         ▼
   Dirty Set（失效的数据维度集合）
         │
         ▼
   Rule Scheduler（匹配：谁的 depends_on 命中 Dirty Set）
         │
         ▼
   Rules（执行）
```

**CompileEvent 是输入，Dirty Set 是调度依据。** 一个 `AssertionChanged` 事件可能传播到 Timeline、Character、Location——Event 本身不知道，Dependency Graph 知道。

## 4.2 CompileRequest

触发一次编译的请求。**DryRun / Build / Release 不是 CompileMode，而是不同的 CompileRequest**：

```rust
pub struct CompileRequest {
    /// 触发本次编译的事件（空 = 无变化，通常配合 Full 模式）
    pub events: Vec<CompileEvent>,
    /// 编译模式
    pub mode: CompileMode,
    /// 请求类型
    pub kind: RequestKind,
}

pub enum CompileMode {
    /// 增量：基于 events + Dirty Set 调度
    Incremental,
    /// 全量：忽略 events，重新检查一切
    Full,
}

pub enum RequestKind {
    /// 普通编译（Editor 保存触发）
    Build,
    /// Dry-Run（Agent / Extraction 的 Commit Gate）
    /// 在 draft IR 上试运行，不修改真实 IR
    DryRun { change: Change },
    /// 手动全量重建（用户显式触发 / 缓存失效）
    Rebuild,
}
```

> **DryRun 和 Build 共享同一个 CompileMode**——它们只是不同的 RequestKind。`DryRun { change }` + `Incremental` 就是"AI 增量试运行"；`Build` + `Full` 就是"手动全量检查"。

## 4.3 CompileEvent → Dirty Set（Dependency Resolver）

CompileEvent 描述"发生了什么"，Dependency Resolver 将其传播为"哪些数据维度失效了"：

```rust
/// 编译事件——描述"什么发生了变化"
pub enum CompileEvent {
    FragmentChanged { id: StableId },
    EntityChanged { id: StableId },
    StructureChanged { scope: StableId },
    AssertionChanged { id: StableId },
    Batch(Vec<CompileEvent>),
}

/// Dirty Set——失效的数据维度
/// 这是调度的真正依据，不是 CompileEvent
pub struct DirtySet(pub BTreeSet<Dependency>);

/// Dependency Resolver：将事件传播为 Dirty Set
pub fn resolve_dirty(events: &[CompileEvent]) -> DirtySet {
    let mut dirty = BTreeSet::new();

    for event in events {
        match event {
            CompileEvent::FragmentChanged { .. } => {
                dirty.insert(Dependency::Fragment);
                // Fragment 变化可能影响实体出场 → 间接影响 Location Index
                dirty.insert(Dependency::Structure);
            }
            CompileEvent::EntityChanged { .. } => {
                dirty.insert(Dependency::Entity);
                // Entity 的 alias 变化会影响 Fragment 中的匹配
                dirty.insert(Dependency::Fragment);
            }
            CompileEvent::StructureChanged { .. } => {
                dirty.insert(Dependency::Structure);
            }
            CompileEvent::AssertionChanged { .. } => {
                dirty.insert(Dependency::Assertion);
                // 断言变化传播到所有依赖 KB 的维度
                dirty.insert(Dependency::Knowledge);
                // 角色状态断言（alive/age）变化影响角色检查
                dirty.insert(Dependency::Entity);
            }
            CompileEvent::Batch(inner) => {
                // 递归传播
                let sub = resolve_dirty(inner);
                dirty.extend(sub.0);
            }
        }
    }

    DirtySet(dirty)
}
```

> **传播规则是确定性的，由 Compiler 内置**——不需要 Rule 自己判断"这个事件影响不影响我"。Resolver 集中管理传播逻辑，Rule 只声明 `depends_on`。

## 4.4 Rule Scheduler（调度器）

调度器根据 Dirty Set + Rule 的 `depends_on()`，决定每条规则是否执行：

```rust
impl RuleRegistry {
    /// 执行编译
    pub fn compile(
        &self,
        ir: &StoryIR,
        derived: &DerivedIndexes,
        kb: Option<&KnowledgeBase>,
        request: &CompileRequest,
    ) -> Diagnostics {
        // 1. 解析 Dirty Set（全量模式跳过，直接全 dirty）
        let dirty = match request.mode {
            CompileMode::Full => DirtySet::all(),         // 全量：所有维度 dirty
            CompileMode::Incremental => resolve_dirty(&request.events),
        };

        // 2. 构建 Sink
        let mut sink = DiagnosticSink::new();

        // 3. 按阶段执行
        for phase in [RulePhase::Structure, RulePhase::Semantic, RulePhase::Style] {
            for rule in self.rules_of(phase) {
                // 3a. 配置禁用检查
                let severity = match self.config.severity_of(rule.as_ref()) {
                    Some(s) => s,
                    None => continue,
                };

                // 3b. 依赖可用性检查
                let deps = rule.depends_on();
                if deps.contains(&Dependency::Assertion) && kb.is_none() { continue; }

                // 3c. Dirty 匹配：规则的依赖是否命中 Dirty Set
                let should_run = deps.iter().any(|d| dirty.contains(d));

                if should_run {
                    let mut ctx = RuleContext {
                        ir,
                        kb,
                        derived,
                        config: &self.config,
                        mode: request.mode,
                        request,
                        sink: &mut sink,
                        rule_severity: severity,
                    };
                    rule.run(&mut ctx);
                }
            }
        }

        // 4. 确定性排序输出
        sink.into_diagnostics()
    }
}
```

> **Compiler 不需要知道 Rule 的内容**——它只看 `depends_on()` 是否命中 Dirty Set。这让 Rule 的添加/修改完全不影响调度逻辑。

## 4.5 RuleContext 已在 §3.2 定义

规则通过 `RuleContext`（§3.2）访问所有数据。它包含 IR、KB、DerivedIndexes、Config、CompileMode、Request，以及用于产出诊断的 Sink。这个结构一次定全，后续新增数据维度时只需在 `DerivedIndexes` 内加字段，Rule 的 trait 签名不变。

规则**只读**数据，通过 `ctx.report()` 产出诊断，不修改 IR。Compiler 是纯函数：相同输入 → 相同输出。

# 5. Built-in Rules（内置规则）

v0.1 内置的检查规则。按 RFC-0001 §3.4 的三层分类组织。

## 5.1 结构不变量检查（phase: Structure, depends_on: [Structure]）

这些规则验证 RFC-0002 §3.3 的 IR Invariants，是 Compiler 的**最底层检查**，优先于所有其他规则。

| 规则 ID | 检查内容 | 默认级别 |
|:--|:--|:--|
| `ir_stable_id_unique` | 所有 StableId 全局唯一 | Error |
| `ir_edge_id_unique` | 所有 EdgeId 唯一 | Error |
| `ir_fragment_is_leaf` | Fragment 是叶子节点 | Error |
| `ir_edge_endpoints_exist` | 所有 SemanticEdge 端点存在 | Error |
| `ir_doc_graph_acyclic` | Document Graph 无环 | Error |
| `ir_linklist_consistent` | 链表完整（A.next=B → B.prev=A） | Error |

```rust
/// IR 不变量检查器（合并为一条 Rule，内部检查所有不变量）
pub struct IrInvariantChecker;

impl Rule for IrInvariantChecker {
    fn id(&self) -> &str { "ir_invariants" }
    fn default_severity(&self) -> Severity { Severity::Error }
    fn phase(&self) -> RulePhase { RulePhase::Structure }
    fn depends_on(&self) -> &[Dependency] {
        &[Dependency::Structure]  // 结构不变量只依赖 Document Graph
    }
    fn run(&self, ctx: &mut RuleContext) {
        // 逐一检查 RFC-0002 §3.3 的 10 条不变量，通过 ctx.report() 产出
        check_id_uniqueness(ctx);
        check_edge_endpoints(ctx);
        check_doc_graph_acyclic(ctx);
        check_linklist_consistency(ctx);
        // ...
    }
}
```

## 5.2 引用完整性检查（phase: Structure, depends_on: [Structure, Entity]）

| 规则 ID | 检查内容 | 默认级别 |
|:--|:--|:--|
| `orphan_reference` | structure.toml 引用了不存在的 Fragment | Error |
| `orphan_fragment` | Fragment 文件存在但未被 structure.toml 引用 | Warning |
| `duplicate_id` | 两个 Entity 使用同一 StableId | Error |
| `duplicate_symbol` | 两个 Entity 使用同一 Symbol | Error |
| `anchor_target_exists` | anchor 引用的 Entity 存在 | Error |

## 5.3 时序 / 逻辑检查（phase: Semantic, depends_on: [Assertion, Entity]）

这些规则读取 Knowledge Base，检查命题一致性。

| 规则 ID | 检查内容 | 默认级别 |
|:--|:--|:--|
| `assertion_contradiction` | 两条 active 断言，同 subject+predicate，不同 object，valid 重叠 | Error |
| `validity_window_illegal` | valid_until 早于 valid_from | Error |
| `dead_character_revived` | 角色死亡（Assertion: alive=false）后，后续场景有其活动（anchor: appears） | Error |
| `age_inconsistency` | 角色年龄断言与时间线矛盾（年龄不随时间增长 / 倒退） | Error |

```rust
/// 死人复活检查
pub struct DeadCharacterRevived;

impl Rule for DeadCharacterRevived {
    fn id(&self) -> &str { "dead_character_revived" }
    fn default_severity(&self) -> Severity { Severity::Error }
    fn phase(&self) -> RulePhase { RulePhase::Semantic }
    fn depends_on(&self) -> &[Dependency] {
        &[Dependency::Assertion, Dependency::Entity, Dependency::Fragment]
    }
    fn run(&self, ctx: &mut RuleContext) {
        let kb = match ctx.kb {
            Some(kb) => kb,
            None => return,  // KB 不可用时跳过
        };
        let loc_idx = match &ctx.derived.location_index {
            Some(idx) => idx,
            None => return,
        };

        // 1. 找到所有"已死亡"断言
        for death in kb.find_assertions(predicate = "alive", object = false) {
            let char_id = death.subject;
            let death_time = death.valid.from;

            // 2. 查找该角色在死亡时间之后的出场
            for frag_id in loc_idx.appearances_of(char_id) {
                let frag_time = ctx.ir.timeline_of(frag_id);
                if frag_time > death_time {
                    ctx.error(
                        "dead_character_revived",
                        format!("角色 {:?} 在死亡后仍出场", char_id),
                        SourceLocation::fragment(frag_id),
                    );
                }
            }
        }
    }
}
```

## 5.4 证据检查（phase: Semantic, depends_on: [Assertion, Fragment]）

| 规则 ID | 检查内容 | 默认级别 |
|:--|:--|:--|
| `evidence_mismatch` | 断言的 Evidence 指向的 Fragment 已不存在或内容不再支持 | Warning |
| `orphan_assertion` | 断言引用的 Entity 在 IR 中不存在 | Warning |

# 6. Dry-Run（试运行）

Dry-Run 是 Compiler 的核心能力之一，服务于 Agent Change 与 Extraction 的 Commit Gate（RFC-0001 §9.2、RFC-0015 §6）。

## 6.1 定位

> **Dry-Run 是"必要但不充分"的安全网。** 它只校验结构与时序层（Error 级），不保证语义质量。

## 6.2 实现——DryRun 是一种 CompileRequest

DryRun 不是独立的 CompileMode，而是 `RequestKind::DryRun`。它复用 §4 的完整调度管线：

```rust
impl RuleRegistry {
    /// 在 draft IR 上试运行，不修改真实 IR
    pub fn dry_run(
        &self,
        current_ir: &StoryIR,
        change: &Change,
        kb: Option<&KnowledgeBase>,
        derived: &DerivedIndexes,
    ) -> DryRunResult {
        // 1. 应用 Change 到当前 IR 的副本
        let mut draft_ir = current_ir.clone();
        if let Err(e) = draft_ir.apply(change) {
            return DryRunResult::Failed(vec![e.into()]);
        }

        // 2. 构建请求：DryRun + Incremental
        let request = CompileRequest {
            events: vec![change.into()],
            mode: CompileMode::Incremental,
            kind: RequestKind::DryRun { change: change.clone() },
        };

        // 3. 复用 compile() 管线
        let diags = self.compile(&draft_ir, derived, kb, &request);

        // 4. 判定：只有 Error 阻断
        let errors: Vec<_> = diags.0.into_iter()
            .filter(|d| d.severity == Severity::Error)
            .collect();

        if errors.is_empty() {
            DryRunResult::Passed
        } else {
            DryRunResult::Failed(errors)
        }
    }
}

pub enum DryRunResult {
    /// 无 Error，可以提交
    Passed,
    /// 存在 Error，不可提交，附诊断反馈
    Failed(Vec<Diagnostic>),
}
```

## 6.3 Change → CompileEvent 映射

Dry-Run 的增量调度依赖 Change 到 CompileEvent 的转换，再经 Dependency Resolver 传播为 Dirty Set：

```rust
impl From<&Change> for CompileEvent {
    fn from(change: &Change) -> Self {
        match change {
            Change::InsertFragment { scene, .. } => {
                CompileEvent::StructureChanged { scope: *scene }
            }
            Change::UpdateCharacter { id, .. } => {
                CompileEvent::EntityChanged { id: *id }
            }
            Change::MoveChapter { .. } => {
                CompileEvent::StructureChanged { scope: ROOT }
            }
            Change::SubmitAssertion { .. } => {
                CompileEvent::AssertionChanged { id: change.assertion_id() }
            }
            // ...
        }
    }
}
```

> **Change → Event → Dirty Set → Rule 调度**，全程确定性。Agent 频繁提交时，Dry-Run 只跑命中 Dirty Set 的规则，响应快。

# 7. Incremental Compilation（增量编译）

## 7.1 与 Parser 增量解析的对称

Parser 的增量是"只重解析脏文件"（RFC-0006 §10）。Compiler 的增量是"只重检查命中 Dirty Set 的规则"。二者共享 RFC-0001 §10.2 的两层 + Stale 策略。

## 7.2 两层 + Stale 策略

增量编译时，受影响的诊断范围：

| 层级 | 范围 | 处理 |
|:--|:--|:--|
| **L0** | 直接变化的实体 | 立即重算诊断 |
| **L1** | 直接引用该实体的实体（一层引用） | 增量重算诊断 |
| **L2+** | 间接依赖 | 标 Stale，不立即重算 |

这与 RFC-0001 §10.2 的策略完全对齐。CompileEvent + Rule.dependencies 实现了这一调度：

- L0/L1 的规则：`is_affected()` 返回 true → 执行
- L2+ 的规则：`is_affected()` 返回 false → 跳过（但不删除旧诊断，标 Stale）

```rust
/// 增量编译时，对未执行规则的旧诊断标记 Stale
fn mark_stale(
    previous_diags: &mut Diagnostics,
    events: &[CompileEvent],
) {
    for d in &mut previous_diags.0 {
        // 如果诊断的来源受事件影响，但规则未重新执行，标记 Stale
        if is_scope_affected(&d.loc, events) && !d.is_fresh {
            d.stale = true;
        }
    }
}
```

## 7.3 Stale 的 UI 表现

- Stale 诊断在 Editor 中以灰色 / 虚线展示，提示"可能已过期"。
- 不阻断保存或 Change 提交。
- 下次全量编译时清除所有 Stale 标记。

# 8. Determinism（确定性）

与 Parser（RFC-0006 §3）对称，Compiler 必须确定：

> **同一 IR + KB + Config + Compiler 版本 → 永远产出完全一致的 Diagnostics。**

### 核心不变量：增量 == 全量

> **对于同一份 IR，增量编译的结果必须与全量编译完全一致。**

这是增量编译的基石。若增量结果与全量不同，就无法信任增量——Debug 时会疯，因为"重新编译一下结果变了"。

- 增量跳过的规则，其**旧诊断保留**，标 Stale。
- 增量执行的规则，其**新诊断覆盖旧诊断**。
- 全量编译时所有 Stale 清除，重新产出——结果必然与"从未增量过"一致。
- Dirty Set 的传播必须**完备**：若某条规则依赖的数据变了，Dirty Set 必须命中它。漏传播会导致增量漏检。

### 保证确定性的设计约束

1. **规则遍历顺序确定**：按 RulePhase 顺序 × phase 内按注册顺序遍历，不依赖 HashMap 迭代序。
2. **Diagnostics 排序确定**：最终诊断按 (SourceLocation, rule_id) 排序（DiagnosticSink::into_diagnostics）。
3. **规则本身必须确定**：每条 Rule 的 `run()` 是纯函数，不调用随机数、不读取系统时间、不发起网络请求。
4. **Dirty Set 传播确定**：Dependency Resolver 的传播规则固定，同一组 CompileEvent 永远产出同一 DirtySet。
5. **Dry-Run 确定性**：相同 Change 在相同 IR 上的 Dry-Run 结果唯一。

### 被依赖的场景

- **增量编译**：假设"未变化的规则结果不变"，可以跳过。若不确定，增量结果可能出错。
- **Dry-Run**：Assertion 层假设"重新跑得到相同结果"，否则 Dry-Run 不可信。
- **Git Diff**：两次全量编译的诊断 Diff 只反映 IR 变化，不反映 Compiler 的随机性。

# 9. Error Handling & Diagnostics

## 9.1 Diagnostic 结构

Compiler 产出的诊断遵循 RFC-0005 的结构：

```rust
pub struct Diagnostic {
    pub rule_id: String,           // 产出此诊断的规则 ID
    pub severity: Severity,        // Error / Warning / Hint / Info
    pub message: String,           // 人类可读的描述
    pub loc: SourceLocation,       // 定位（实体 ID + Fragment 块）
    pub stale: bool,               // 增量编译时是否标记为过期
}

pub struct SourceLocation {
    pub entity: Option<StableId>,  // 涉及的实体
    pub fragment: Option<StableId>,// 涉及的 Fragment（块级定位）
    pub assertion: Option<StableId>,// 涉及的断言（KB 相关诊断）
}
```

> 定位到**块/实体级**，不到行号——与 RFC-0001 §10.1 的锚点驱动定位一致。

## 9.2 错误阻断逻辑

| 级别 | 是否阻断提交 | 场景 |
|:--|:--|:--|
| Error | ✅ 阻断 | Dry-Run 返回 Failed，Change 不可提交 |
| Warning | ❌ 不阻断 | 提示作者，但不阻止 |
| Hint | ❌ 不阻断 | Semantic Validator 产出，建议性 |
| Info | ❌ 不阻断 | 信息性 |

**只有 Compiler 产出 Error。** Semantic Validator 永远不产 Error（RFC-0001 §6 Core Concepts）。

# 10. Performance（性能）

## 10.1 预估

百万字小说的编译规模：

| 数据 | 规模 |
|:--|:--|
| Fragment | ~2000 个 |
| Entity | ~300 个 |
| Assertion | ~500 条 |
| 规则 | ~15 条 |

全量编译：遍历 IR + KB，每条规则 O(n)，总计约 O(规则数 × 数据量) ≈ 毫秒级到秒级。

## 10.2 优化策略

- **增量编译**（默认）：只跑受影响规则，大多数编译 < 10ms。
- **规则并行**：无依赖的规则可并行执行（v0.2+）。
- **KB 索引**：Knowledge Base 维护 `subject → assertions` 索引，避免全量扫描。

# 12. Open Questions

1. **规则并行执行**：同一 Phase 内无依赖的规则可否并行？需要分析规则间的读写冲突（它们都只读 IR，但共享 DiagnosticSink，需要线程安全）。（倾向：v0.2+，v0.1 串行。）
2. **Stale 诊断的精确性**：增量编译标记 Stale 时，如何精确判断"这条诊断确实受影响"？当前用 Dependency 粗粒度匹配，可能误标。（倾向：接受误标，宁过勿漏——增量漏检比误标危险得多。）
3. **Dry-Run 的 Location Index**：Dry-Run 的 draft IR 未跑 Entity Linking，无 Location Index。部分规则（如 dead_character_revived）依赖它。Dry-Run 是否应该对 draft 跑轻量 Entity Linking？（倾向：v0.1 Dry-Run 跳过依赖 Location Index 的规则，它们在全量编译时检查；Dry-Run 聚焦结构安全。）
4. **Dirty Set 传播的完备性验证**：如何确保 Dependency Resolver 的传播规则没有遗漏？需要一个测试套件：对每个 CompileEvent，验证所有应受影响的 Dependency 都在 Dirty Set 中。（倾向：v0.1 用单元测试覆盖。）

> **Compiler 是 Parser 的对称镜像。Parser 管"能否解析"，Compiler 管"是否合理"。两者都纯确定、都只读、都不碰 AI。规则统一注册、调度器按依赖执行——全量还是增量不是选择题，而是模式切换。**
