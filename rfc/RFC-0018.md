# 1. Abstract（摘要）

Story Mechanics 是世界规则的按需叠加层。修仙、穿越、轮回、系统流——这些不是核心模型的特例，而是独立的世界设定机制，按项目需要叠加。

```text
   核心层（所有小说通用）
   ├── Timeline（线性时间）
   ├── Character（角色）
   ├── Compiler（时序 + 结构检查）
   │
   └── Mechanics 层（按需叠加）
       ├── 修仙体系（cultivation）
       ├── 时间穿越（time_travel）
       ├── 轮回转世（reincarnation）
       └── 系统流（system）...
```

> **核心不变，复杂能力按需叠加。** 修仙小说装修仙 Mechanic，穿越小说装穿越 Mechanic，都市现实小说什么都不装。一本"穿越 + 修仙 + 系统流"的小说可叠加三个 Mechanic，互不干扰。

### 核心设计原则

> **Timeline 描述世界时间，不描述实体在时间中的移动。任何时间跳跃（如 Time Travel）均建模为独立的 Mechanic + Travel Event，而不是修改 Timeline 本身。**
>
> Timeline 永远保持线性。变化的是 Mechanic 层。这与 ECS 思想一致：世界没变，是实体状态变了。

------

# 2. Motivation（为什么需要 Mechanics）

RFC-0001 §2 列出的痛点（年龄矛盾、死人复活等）靠线性时序检查解决。但有些小说类型的世界规则使得这些检查**不适用**：

- **修仙小说**：角色寿元随境界增长，线性年龄检查会误报
- **穿越小说**：角色穿越到死前时代出场，dead_character_revived 误报
- **轮回小说**：角色死后转世为新角色，旧断言和新出场不冲突
- **系统流**：系统面板的数值不受现实时间约束

如果为每种类型修改核心 Compiler 规则，会让 95% 的线性小说背负不必要的复杂度。

**Mechanics 的核心思路**：不修改核心模型，而是让世界规则**声明豁免**——告诉 Compiler "这些场景/角色不受某条规则约束"。

------

# 3. Design Principle（设计原则）

## 3.1 核心不变，Mechanics 叠加

Timeline 保持线性、Character 保持基础模型、Compiler 保持确定性规则。Mechanics 是**可选的扩展层**，不改变核心数据结构。

```text
   不装 Mechanic 的项目      装 Mechanic 的项目
   ┌─────────────┐          ┌─────────────────────┐
   │  核心规则    │          │  核心规则             │
   │  全部生效    │          │  + Mechanic 豁免      │
   └─────────────┘          │  + Mechanic 自定义规则 │
                             └─────────────────────┘
```

## 3.2 Compiler 不理解 Mechanic 语义

Compiler 不需要知道"穿越是什么"或"修仙怎么修炼"。它只需要理解一个概念：**豁免（Exemption）**。

Mechanic 通过结构化的豁免声明告诉 Compiler：
- 哪些规则被豁免
- 在什么条件下豁免（哪些 Scene / Entity 受此 Mechanic 保护）

## 3.3 组合自由

多个 Mechanic 可以共存。一本"穿越 + 修仙"的小说：

```toml
[[mechanic]]
type = "time_travel"
# 穿越场景豁免 dead_character_revived

[[mechanic]]
type = "cultivation"
# 修仙者豁免 age_inconsistency
```

两个 Mechanic 独立声明、独立生效、互不干扰。

## 3.4 确定性

Mechanics 的豁免逻辑是**确定性的**——Scene 是否标记了某 Mechanic 是客观事实，Compiler 的判断结果唯一。

------

# 4. Core Concepts（核心概念）

## 4.1 Mechanic

一条世界规则声明：

```toml
# mechanics.toml

[[mechanic]]
id = "m_time_travel"
type = "time_travel"
description = "角色可通过时空阵法穿越到过去或未来"
```

| 字段 | 说明 |
|:--|:--|
| `id` | Mechanic 的唯一标识（前缀 `m_`） |
| `type` | Mechanic 类型（见 §4.3） |
| `description` | 人类可读说明 |

## 4.2 Exemption（豁免声明）

Mechanic 通过豁免声明告诉 Compiler 跳过某些检查：

```toml
[[mechanic]]
id = "m_time_travel"
type = "time_travel"
description = "角色可通过时空阵法穿越到过去或未来"

# 豁免声明
[mechanic.exemptions]
# 被豁免的规则 ID 列表
rules = ["dead_character_revived"]
# 豁免范围：哪些对象受此豁免保护
# scene_tagged:<tag> = 标记了某 tag 的 Scene
# entity_tagged:<tag> = 标记了某 tag 的 Entity
# global = 全局豁免（所有对象）
scope = "scene_tagged:time_travel"
```

### 豁免作用域

| scope 格式 | 含义 |
|:--|:--|
| `global` | 全局豁免——所有对象不受此规则约束 |
| `scene_tagged:<tag>` | 标记了 `<tag>` 的 Scene 内的所有检查被豁免 |
| `entity_tagged:<tag>` | 标记了 `<tag>` 的 Entity 相关检查被豁免 |

### Scene / Entity 打标签

Scene 和 Entity 通过 `mechanic_tags` 字段声明受哪些 Mechanic 保护：

```toml
# structure.toml 中的 Scene
[scene.sc_20_01]
title = "重逢"
mechanic_tags = ["time_travel"]    # 此场景涉及时间穿越
fragments = ["f_0042"]

# entities/characters/c_001.toml
id = "c_001"
display_name = "林风"
mechanic_tags = ["cultivator"]     # 此角色是修仙者
```

## 4.3 Mechanic Types（预定义类型）

这些是常见的小说世界规则类型。类型本身不影响 Compiler 行为（Compiler 只看豁免声明），但用于：

- AI 上下文构建（告诉 AI 这个世界的规则）
- 文档分类
- 未来可能的类型专属检查

| type | 说明 | 常见豁免规则 |
|:--|:--|:--|
| `time_travel` | 时间穿越 | dead_character_revived, age_inconsistency |
| `cultivation` | 修仙体系 | age_inconsistency |
| `reincarnation` | 轮回转世 | dead_character_revived |
| `system` | 系统流 | （通常不需要豁免） |
| `magic` | 魔法体系 | （视设定而定） |
| `parallel_world` | 平行宇宙 | dead_character_revived |
| `custom` | 自定义 | 任意 |

> **type 是开放集合**——作者和插件可自由定义新类型。以上是常见参考。

## 4.4 Travel Event（穿越事件的叙事建模）

`time_travel` 类型的 Mechanic 可选地携带结构化的 **Travel Event** 数据——记录具体的时间跳跃。

> Travel Event 属于 **Narrative Layer**，不属于 Timeline。穿越是叙事中发生的一件事，和"死亡""觉醒""飞升"本质一样。Timeline 只是它引用的数据。

```toml
# mechanics.toml

[[mechanic]]
id = "m_time_travel"
type = "time_travel"
description = "角色可通过时空阵法穿越到过去或未来"

[mechanic.exemptions]
rules = ["dead_character_revived", "age_inconsistency"]
scope = "scene_tagged:time_travel"

# Travel Events（time_travel 专属结构化数据）
[[mechanic.travel_events]]
scene = "sc_12_01"            # 穿越发生在哪个场景
traveler = "c_001"            # 谁穿越
from_time = { year = 1203 }   # 从哪个时间
to_time = { year = 1200 }     # 到哪个时间
effect = "stable"             # 时间线效应（见下表）
```

### Travel Event 字段

| 字段 | 说明 |
|:--|:--|
| `scene` | 穿越事件发生的 Scene ID |
| `traveler` | 穿越者的 Entity ID |
| `from_time` | 出发时间（StoryTime） |
| `to_time` | 到达时间（StoryTime） |
| `effect` | 时间线效应类型 |

### effect 类型（替代 creates_branch 布尔值）

| effect | 含义 | 代表作品类型 |
|:--|:--|:--|
| `stable` | 固定时间线——穿越后历史自洽，无分支 | 《哈利波特与阿兹卡班的囚徒》 |
| `overwrite` | 覆盖未来——改变过去会改写未来 | 《蝴蝶效应》 |
| `branch` | 分支宇宙——产生平行时间线 | 《命运石之门》 |
| `merge` | 时间线合并（未来扩展） | — |

> **effect 是开放枚举**——v0.1 只定义三种，未来可扩展。

### Compiler 可检查的 Travel Event 规则

| 规则 ID | 检测 | 级别 |
|:--|:--|:--|
| `travel_scene_mismatch` | Travel Event 的 scene 的 story_time 不等于 from_time | Warning |
| `travel_no_effect` | Travel Event 的 to_time 晚于 from_time（前向跳跃，语义不明） | Info |

## 4.5 层级定位

Mechanics 横跨 Narrative Layer 和 Compiler Layer：

```text
   Timeline Layer
   ──────────────
   TimePoint / Calendar / Duration

   Narrative Layer
   ──────────────
   TravelEvent（属于 Mechanics）
   Thread（RFC-0017）
   Outline（RFC-0016）

   Compiler Layer
   ──────────────
   Mechanics 的 Exemption 声明
```

> **空间传送、梦境、记忆回溯**等未来扩展也放 Narrative Layer。Timeline 永远不用动。

# 5. Compiler Integration（Compiler 集成）

## 5.1 豁免执行流程

Compiler 在执行规则前，检查当前对象是否被任何 Mechanic 豁免：

```text
   遍历规则
      │
      ▼
   检查规则是否被当前对象的 Mechanic 豁免
      │
      ├─ 是 → 跳过此规则
      └─ 否 → 正常执行
```

## 5.2 豁免匹配逻辑

```rust
/// 检查某条规则在给定上下文下是否被豁免
fn is_exempted(
    rule_id: &str,
    scene_tags: &[String],
    entity_tags: &[String],
    mechanics: &[Mechanic],
) -> bool {
    for mechanic in mechanics {
        for exemption in &mechanic.exemptions {
            // 规则是否在豁免列表中
            if !exemption.rules.contains(&rule_id.to_string()) {
                continue;
            }

            // 检查 scope 匹配
            let matched = match exemption.scope.as_str() {
                "global" => true,
                s if s.starts_with("scene_tagged:") => {
                    let tag = &s["scene_tagged:".len()..];
                    scene_tags.iter().any(|t| t == tag)
                }
                s if s.starts_with("entity_tagged:") => {
                    let tag = &s["entity_tagged:".len()..];
                    entity_tags.iter().any(|t| t == tag)
                }
                _ => false,
            };

            if matched {
                return true;
            }
        }
    }
    false
}
```

## 5.3 规则传入的上下文

每条 Compiler 规则在执行时，RuleContext 提供当前检查对象的 tags：

```rust
// RuleContext 扩展（RFC-0004 §3.2）
pub struct RuleContext<'a> {
    pub ir: &'a StoryIR,
    pub location_index: Option<&'a LocationIndex>,
    pub kb: Option<&'a KnowledgeBase>,
    pub threads: Option<&'a ThreadCollection>,
    pub mechanics: Option<&'a MechanicCollection>,   // 新增
    pub severity: Severity,
    sink: &'a mut DiagnosticSink,
}
```

规则在检查某个 Scene / Entity 时，从 MechanicCollection 查询是否被豁免。

## 5.4 已有规则的豁免支持

以下规则天然支持被 Mechanic 豁免（因为它们检查的是"角色在场景中的行为合法性"）：

| 规则 ID | 可被豁免的场景 |
|:--|:--|
| `dead_character_revived` | time_travel（穿越到死前时代）/ reincarnation（转世后出场） |
| `age_inconsistency` | cultivation（寿元随境界）/ time_travel |
| `assertion_contradiction` | parallel_world（平行宇宙的同一角色有不同状态） |

# 6. Custom Rules（自定义检查规则）

Mechanic 除了豁免现有规则，还可以**注册自定义检查规则**（v0.2+）：

```toml
[[mechanic]]
id = "m_cultivation"
type = "cultivation"

# 自定义规则（v0.2+，通过插件实现）
[[mechanic.custom_rules]]
id = "realm_breakthrough_consistency"
description = "境界突破需要前置境界"
severity = "warning"
```

v0.1 不实现自定义规则——只支持豁免。自定义规则需要 Plugin 系统（RFC-0011）配合。

# 8. Source of Truth Model

| 数据 | 性质 | 进 Git |
|:--|:--|:--|
| Mechanic 定义 | Source of Truth | ✓ |
| Scene / Entity 的 mechanic_tags | Source of Truth | ✓（随各自文件） |
| 豁免判断结果 | 派生（Compiler 运行时计算） | ✗ |

**Mechanics 不复制核心数据**——它只声明"哪些规则在什么条件下跳过"。

# 9. AI Context（AI 上下文中的 Mechanics）

AI Runtime 构建 Prompt 时，Mechanics 提供世界规则上下文：

```text
=== 世界规则 ===
1. 时间穿越：角色可通过时空阵法穿越到过去或未来
2. 修仙体系：灵气修炼，境界突破可增长寿元

注意事项：
- 当前场景（sc_20_01）涉及时间穿越
- POV 角色（林风）是修仙者
```

AI 上下文使用 description（人类可读），不用 scope / rules（那是 Compiler 用的）。

# 11. Open Questions

1. **嵌套豁免**：如果一个 Scene 同时被 time_travel 和 cultivation 标记，两条 Mechanic 的豁免规则是否合并？还是分别判断？（倾向：合并——任一 Mechanic 豁免即生效。）
2. **豁免的范围传递**：Scene 标记了 time_travel，其下的 Fragment 是否自动继承？（倾向：是——Scene 级标记传递到 Fragment。）
3. **Mechanic 之间的交互**：time_travel + reincarnation 同时存在时，dead_character_revived 的豁免逻辑是否需要特殊处理？（倾向：否——独立豁免，叠加生效。）
4. **自定义规则的实现路径**：v0.2 通过 Plugin 系统（RFC-0011）注册 Mechanic 专属规则，还是通过内嵌的规则 DSL？（倾向：Plugin。）
5. **Mechanic 版本化**：作者修改了豁免规则后，已有的 Diagnostics 如何处理？（与 Compiler 增量编译对齐——重算受影响规则。）
6. **knowledge propagation across Travel Events**：角色穿越回过去时，Thread 的 knowledge state 是否重置为 Unknown？不同小说答案不同（《Re:Zero》保持，《蝴蝶效应》可能改变）。未来可定义 `knowledge_policy = "retain" | "reset" | "branch"`。v0.1 不实现——留作 Travel Event 的未来扩展。

------

# 12. 不做什么

- **不做时间线分裂**——穿越不创建分支时间线。Mechanics 只声明豁免，不模拟时间线结构。
- **不做物理模拟**——Mechanics 不模拟灵气浓度、境界数值等。那属于 Entity 的 attributes（各自 RFC 定义）。
- **不做于 v0.1**——v0.1 只记录设计。实现优先级低于核心功能完善。
- **不做通用规则引擎**——Mechanics 不是让用户写任意逻辑，而是有限的结构化声明（豁免 + 预定义自定义规则）。
