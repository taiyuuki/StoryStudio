**Version**

**Depends On**

RFC-0001（总体架构）, RFC-0002（Story IR）, RFC-0006（Parser）

> **不依赖 RFC-0004（Compiler）。** 本 RFC 只定义 Knowledge Layer 的**数据模型与不变量**（Assertion / Evidence / ValidityWindow 的结构、KB 的 SoT 性质、收录边界）。KB 的"生成→验证→提交"执行编排由 RFC-0010（AI Runtime）负责，编译检查由 RFC-0004（Compiler）负责。三者构成有向无环依赖：`0015（数据）→ 0004（读 KB）→ 0010（编排两者）`。

------

# 1. Abstract（摘要）

Story Studio 的数据流在 Story IR 与 Compiler 之间引入一层 **Knowledge Layer**：

```text
Markdown → Parser → Story IR → Knowledge Layer → Compiler
                     (结构)      (可推理的知识)     (验证一致性)
```

每一层只有一个职责：

- **Parser**：理解文本结构。
- **Story IR**：表示故事结构（章节、场景、实体节点）。
- **Knowledge Layer**：表示故事中**可以被推理和验证的知识**（断言 + 证据）。
- **Compiler**：验证知识之间是否一致。

Knowledge Layer 的引入，使"哪些事实可被检查"从隐式假设变为显式、可版本化的工程产物。

------

# 2. Motivation（为什么需要这一层）

RFC-0001 的 Motivation 列出的痛点中，有一类**无法靠结构检查解决**，必须依赖被结构化标注的事实：

- 年龄错误 → 需要"角色 X 在时间 T 的年龄"这一断言
- 死人复活 → 需要"角色 X 在时间 T 的存活状态"这一断言
- 道具消失 → 需要"道具 Y 在时间 T 的位置 / 持有者"这一断言

但这些事实从哪来？此前的 RFC 存在三个悬空问题：

1. **没有家**：IR 只表示结构，不表示可推理的命题；事实无处存放。
2. **没有来源**：即便有事实，也无法追溯到原文哪一段，无法校验、无法审计。
3. **确定性与非确定性混在一起**：若让 Compiler 直接从文本推断事实，就会把 LLM 的概率性引入本应确定性的检查。

Knowledge Layer 一次性解决三者：事实有存放处（Knowledge Layer）、有来源（Evidence）、且生成与验证解耦（Extraction 非确定，Compiler 确定）。

------

# 3. Layer Position（层级定位与职责边界）

| 层 | 表示什么 | 时序性 | 确定性 | 谁生产 |
|:--|:--|:--|:--|:--|
| **Story IR** | 故事结构（章节树、场景、实体节点、引用图） | 无（结构是静态的） | 确定 | Parser |
| **Knowledge Layer** | 可推理的命题（断言 + 证据） | **有**（每条断言带 valid 区间） | 确定（提交后） | Extraction（AI / 手动） |
| **Compiler** | 一致性判定 | — | **永远确定** | 系统 |

> **与 Reference Index 的区别（避免混淆）：**
> - **Reference Index**（RFC-0001 §6）：结构性的、无时间的"实体↔实体"引用（"角色 A 出现在场景 X"）。
> - **Knowledge Layer**：语义性的、带时间有效期的命题（"角色 A 在 1086 年年龄为 17"）。
>
> 二者是不同维度，互不替代。

------

# 4. Core Concepts（核心概念）

| 概念 | 说明 |
|:--|:--|
| **Assertion（断言）** | 一条可被验证的命题。形如"主体 在 时间T 具有 属性P = 值V"。是 Knowledge Layer 的基本记录。正式术语用 Assertion；"Fact" 作为非正式同义词保留——因为提交时刻它只是 claim，是否为真由 Compiler 判定。 |
| **Evidence（证据）** | 一条断言的文本依据。指向源文本的位置（复用 Location Index 的实体 ID + 块定位），并摘录原文。没有 Evidence 的断言不可提交。 |
| **Knowledge Base** | 一个 Project 内全部已提交断言的集合，随主干数据版本化，提交 Git。 |
| **Validity Window** | 每条断言带 `valid_from` / `valid_until` 时间区间。角色状态会变化（活着→死亡、年龄增长），时间维度是检查矛盾的核心。 |
| **Extraction** | 从 Story IR（及其源文本）生成候选断言的过程。可由 AI 或人工完成。Extraction 产出的候选断言**必须经过 commit gate**，不得直接进入 Knowledge Base。 |

### Assertion 的表示（示意）

```yaml
@assertion a_linxia_age_1:
  subject:    char:linxia
  predicate:  age
  object:     17
  valid:      { from: year-1086, until: year-1088 }
  evidence:   [ ev_ch2_age ]
  status:     active          # active | superseded | contradicted
  extracted_by: manual         # manual | ai:claude-... 
```

### Evidence 的表示（示意）

```yaml
@evidence ev_ch2_age:
  loc:    ch2 @scene:ch2s1     # 复用 Location Index 的锚点定位
  quote:  "林夏今年十七岁"
  source: manual
```

# 5. Source of Truth Model（真相源模型）

Knowledge Base 是 **Source of Truth**，不是派生缓存。理由：

- 若断言是可随时重建的派生缓存，则其内容取决于非确定性的 Extraction，Compiler 就失去了确定性依据——确定性承诺破产。
- 因此断言一旦提交，即成为版本化的事实，提交 Git，与文本共同构成 Project 的真相。

**两个真相源如何避免漂移：**

- **文本**是散文本身的真相源（写了什么）。
- **Knowledge Base**是关于文本的可验证命题的真相源（这些命题是否互相一致）。
- **Evidence**是二者之间的桥：每条断言必须能指回至少一处文本。当文本被大幅修改导致 Evidence 失效时，Compiler 产出 Warning（"断言 a_xxx 的证据已失配"），提示重新抽取——**但不自动删除断言**，由作者决定。

| 数据 | 性质 | 进 Git | 可重建 |
|:--|:--|:--|:--|
| 源文本（Markdown + 锚点） | Source of Truth | ✓ | ✗ |
| Knowledge Base（断言 + 证据） | Source of Truth | ✓ | ✗ |
| Location Index | 派生缓存 | ✗ | ✓ |

------

# 6. Extraction & Commit Contract（抽取与提交的数据契约）

本节定义 Extraction 的**数据契约**（什么是合法的候选断言、提交前必须满足什么条件）。具体的执行编排（调用 Dry-Run、重试循环、错误反馈）由 **RFC-0010（AI Runtime）** 负责——RFC-0010 §9 已将 Extraction 实现为一种 Task。

## 6.1 候选断言的合法性约束

Extraction 产出的候选 Assertion 必须满足以下条件，否则不进入提交流程：

| 约束 | 说明 |
|:--|:--|
| **Evidence 完整** | 每条候选断言必须带至少一条 Evidence（loc + quote），否则拒绝 |
| **Subject 存在** | 断言的 subject 必须是 IR 中已存在的 StableId |
| **Predicate 合法** | predicate 在系统的谓词集合内（或为插件自定义） |
| **Object 类型匹配** | object 的类型与 predicate 期望的类型一致（如 age 期望整数） |

这些是**纯数据校验**，不依赖 Compiler——只检查"断言本身是否结构合法"。

## 6.2 提交门（Commit Gate）的职责划分

提交候选断言时有两层校验，分属不同模块：

| 层 | 校验内容 | 归属 |
|:--|:--|:--|
| **数据契约校验** | §6.1 的四条约束（Evidence 完整、subject 存在等） | Knowledge Layer 自身（纯数据检查） |
| **一致性校验** | 断言之间是否矛盾（contradiction）、时序是否非法 | Compiler Dry-Run（RFC-0004） |

- 第一层是 Knowledge Layer 自己能做的检查（不依赖 Compiler）。
- 第二层需要 Compiler 参与，但**调用动作由 AI Runtime 发起**——AI Runtime 调用 `compiler.dry_run()`，而非 KB 直接调用 Compiler。

```text
   候选断言
      │
      ▼
   数据契约校验（KB 自身）          ← 本 RFC 定义
      │ 通过
      ▼
   AI Runtime 调用 Compiler Dry-Run  ← RFC-0010 编排
      │
      ├─ Error = 0 → 提交到 KB
      └─ Error > 0 → 反馈重试
```

> **为什么这样划分？** KB 是数据结构，不应知道 Compiler 的存在。AI Runtime 是编排者，它同时持有 KB 和 Compiler 的引用，负责把两者串联起来。这让依赖图保持为 DAG：`0015（数据）→ 0004（读 KB 检查）`，`0010（编排两者）`。

------

# 7. Non-determinism Quarantine（非确定性隔离）

这是 Knowledge Layer 的核心设计约束：

| 环节 | 确定性 | 归属 RFC |
|:--|:--|:--|
| Extraction 生成候选断言 | **非确定** | RFC-0010（AI 生成） |
| 候选断言的数据契约校验 | 确定 | **本 RFC**（纯数据检查） |
| Commit Gate（Dry-Run） | 确定 | RFC-0004 + RFC-0010（编排） |
| Knowledge Base（已提交） | **确定** | **本 RFC**（数据模型） |
| Compiler 读取 KB | **确定** | RFC-0004 |

**关键性质：** KB 本身是确定性的数据结构——给定一组已提交断言，其内容完全确定。非确定性只存在于 Extraction 生成环节，且由 AI Runtime 隔离。一旦断言通过 Commit Gate 提交，它就成为确定性的、版本化的事实，Compiler 可以确定性地读取它。

> **与 RFC-0001 §9.2 的对称性：** Agent 生成 Change → Dry-Run → 提交 IR；Extraction 生成 Assertion → Dry-Run → 提交 KB。两条管线同构，且都由 AI Runtime（RFC-0010）编排。

------

# 8. Consistency Checks Consuming KB（消费 KB 的一致性检查）

> 本节定义"KB 数据被一致性检查时需要满足什么约束"——这是 **Compiler（RFC-0004）单向消费 KB 的契约**，不产生反向依赖。

Compiler 读取 Knowledge Base 后，确定性检查包括（但不限于）：

| 检查类型 | 规则 | 举例 | 级别 |
|:--|:--|:--|:--|
| **矛盾** | 两条 active 断言，同 subject+predicate，不同 object，valid 区间重叠 | "linxia 1086 年 17 岁" vs "linxia 1086 年 20 岁" | Error |
| **时序非法** | valid_until 早于 valid_from | 断言区间倒置 | Error |
| **状态冲突** | 角色死亡后的断言仍为 active，但后续场景有其活动 | ch5 死亡，ch8 仍以 active 状态行动 | Error |
| **证据失配** | Evidence 指向的文本块已不存在或内容不再支持断言 | 原文被删，断言悬空 | Warning |
| **孤儿断言** | 断言引用的实体在 IR 中不存在 | char:xxx 已被删除 | Warning |

**Compiler 的两个输入：**

Compiler 同时读取 **Story IR**（结构一致性）和 **Knowledge Base**（命题一致性）。二者职责不同，但都由同一个 Compiler 检查，因为"结构"与"知识"的不一致最终都表现为 Diagnostics。

### 8.1 断言冲突仲裁策略

当 Extraction 产生的新断言与已提交断言矛盾（同 subject + predicate，不同 object，valid 区间重叠）：

**默认行为：人工裁决优先。**

- 系统不自动 supersede 或删除旧断言，而是将新候选断言连同矛盾诊断一起提交给作者确认。
- 作者在 Editor 中看到冲突后，选择：接受新断言（旧断言标 `superseded`）、保留旧断言（拒绝候选）、或两者都标 `contradicted` 留待后续处理。

**可配置：自动标 `contradicted`。**

- 项目配置（`project.toml`）可开启 `knowledge.auto_contradict: true`。
- 开启后，新候选断言若与旧断言冲突，系统自动将两者标为 `contradicted` 并提交（仍走 Dry-Run，但不再阻塞等人工），由作者事后批量处理。

**设计理由：** 冲突往往意味着故事本身的逻辑分歧（"林夏到底是 17 岁还是 20 岁"），自动选择任一方都可能丢失作者意图。默认交还人，保证作者对 Knowledge Base 的最终控制权。

# 9. Scope Constraints（范围约束——不是通用知识图谱）

**铁律：Knowledge Layer 只收录 Compiler 规则需要的断言。**

明确**排除**：

✗ 通用知识图谱（角色关系网的任意推理）
✗ 情感 / 风格 / 文学评价（属 Semantic Validator，非 Knowledge Layer）
✗ 未被任何检查规则引用的事实

收录准则：**一条断言必须有至少一条 Compiler 规则会消费它**，否则不收录。这避免 Knowledge Base 无限膨胀。

**v0.1 收录的最小集：**

- 角色存活状态（alive/dead）+ 时间区间
- 角色年龄 + 时间锚点
- 道具持有者 + 位置 + 时间区间
- 关键事件的发生时间（供 Timeline 检查）

# 10. Relationship to Existing RFCs

| RFC | 关系 |
|:--|:--|
| RFC-0001 | 在总体架构（§7）中插入 Knowledge Layer 层；§3.4 的三层检查现在精确映射（结构→IR，时序→KB，语义→Validator）。 |
| RFC-0002 Story IR | Assertion 的 `subject` 引用 IR 实体 ID。IR 是 Knowledge Layer 的实体来源。 |
| RFC-0006 Parser | Evidence 的 `loc` 复用 Location Index 的锚点定位，不发明新机制。 |
| RFC-0004 Compiler | **单向消费**：Compiler 读取 KB 执行一致性检查（§8）。KB 不依赖 Compiler——本 RFC 只定义数据模型与被检查的契约。 |
| RFC-0010 AI Runtime | **编排者**：Extraction 的执行流程（生成→契约校验→调用 Compiler Dry-Run→提交/重试）由 AI Runtime 负责。本 RFC 只定义候选断言的合法性契约（§6），不定义执行机制。 |
| RFC-0009 Timeline | Assertion 的 `valid` 区间以 Timeline 为坐标轴。 |

# 11. Open Questions（待后续 RFC 解决）

1. **AI Extraction 的置信度**：AI 抽取的断言是否带 confidence 分数，低置信度走人工确认？（倾向：是。）
2. **断言的批量撤销**：删除一个场景后，其 Evidence 支撑的断言如何级联处理？（倾向：标 Warning，不级联删除。）

> **已决策（由 RFC-0003 解决）：** Knowledge Base 的存储格式采用 TOML 集中存储（`knowledge/assertions.toml` + `knowledge/evidence.toml`），与项目配置格式统一。详见 RFC-0003 §5.5。
