# 1. Abstract（摘要）

本 RFC 定义 Story Studio Project 的**文件格式与目录结构**——Story IR 如何落盘、如何从文件重建。

核心设计原则：**每一种信息只有一个 Source of Truth**。

```text
project/
├── project.toml          # 项目级配置
├── structure.toml        # 文档结构树（所有序列关系的 SoT）
├── fragments/            # Fragment 正文（最小编辑单元）
│   ├── f_0001.md
│   └── f_0002.md
├── entities/             # 语义实体
│   ├── characters/
│   ├── locations/
│   ├── items/
│   └── organizations/
├── knowledge/            # Knowledge Base（断言 + 证据）
├── config/               # 配置（compiler/formatter/ai/plugins）
└── .novelstudio/         # 工具私有目录（.gitignore）
    └── cache/            # 派生缓存
```

每个文件**只存自己负责的信息**，不从别处复制。序列关系（谁在谁下面、什么顺序）由各级父节点集中维护，子节点不反向持久化。

------

# 2. Motivation

RFC-0002 定义了 Story IR 的内存数据结构（Typed Graph Model），但未规定它如何序列化为文件。

文件格式的设计直接影响：

- **Git 友好性**：改一个 Fragment 的正文是否只 Diff 一个文件？重排顺序是否只 Diff 一个索引？
- **AI 协作**：AI 能否精确定位到"改哪个文件"而非"改一大坨 JSON"？
- **人类可读性**：作者能否直接在文件系统里浏览自己的小说？
- **Parser 效率**：能否只重读改动的文件，而非全量扫描？

本 RFC 的设计目标：**让文件的物理边界与逻辑边界对齐**。

------

# 3. Design Principle: Single Source of Truth（单一真相源）

Project 中每一种信息**只能有一个 Source of Truth**。同一条关系不得在两处持久化。

| 信息 | Source of Truth | 不在哪里 |
|:--|:--|:--|
| Fragment 正文 | Fragment 文件（`fragments/f_xxxx.md`） | 不在 structure.toml |
| Fragment 锚点（anchors） | Fragment 文件的 frontmatter | 不在 structure.toml |
| Fragment 属于哪个 Scene | structure.toml 的 `Scene.fragments` 列表 | **不在 Fragment frontmatter** |
| Fragment 的 prev/next | structure.toml 的 `Scene.fragments` 列表顺序 | **不持久化**（IR 内存层推导） |
| Scene 属于哪个 Chapter | structure.toml 的 `Chapter.scenes` 列表 | 不在 Scene 独立文件 |
| Chapter 顺序 | structure.toml 的 `Book.chapters` 列表 | 不在 Chapter 独立文件 |
| Entity 信息（三重 ID + 属性） | Entity 文件（`entities/<type>/<id>.toml`） | 不在 IR 序列化产物 |
| Symbol → StableId 映射 | Entity 文件（Symbol 是 Entity 的字段） | 不在单独的符号表文件 |

**关键推论：** Fragment 文件**不含 `scene` 字段**。Fragment 的 Scene 归属完全由 `structure.toml` 中 `Scene.fragments` 列表决定。Parser 加载时，从该列表反向建立 `Fragment → Scene` 映射。

这避免了"Fragment frontmatter 的 scene 字段与 structure.toml 的列表不一致"的双写问题。

## 3.1 File Ownership（文件归属）

SoT 表回答"信息存哪里"，**File Ownership** 回答"谁有权限写什么"。后者对 Parser / Editor / AI Runtime / Plugin 的开发更具指导性——每个模块只需关注自己拥有的文件。

| 拥有者 | 拥有的文件 | 拥有的信息 |
|:--|:--|:--|
| **Book** | `structure.toml` | Book 元信息、Chapter 顺序、Scene 顺序、Fragment 顺序 |
| **Fragment** | `fragments/<id>.md` | 正文、anchors |
| **Entity** | `entities/<type>/<id>.toml` | 三重 ID、display_name、aliases、attributes |
| **Knowledge Base** | `knowledge/*.toml` | assertions、evidence |
| **Config** | `config/*.toml` | lint 规则、格式化、AI 配置 |
| **Cache（工具私有）** | `.novelstudio/cache/` | location index、derived edges、诊断快照 |

**Ownership 规则：**

- 一个文件**只能被一个拥有者写**。例如 AI Runtime 修改 Fragment 正文时，写 `fragments/<id>.md`；重排顺序时，写 `structure.toml`——它不会跨拥有者写。
- 读取不受限——任何模块可读任何文件。
- Plugin 只能通过 Change 机制间接修改，不能直接写非自己拥有的文件（见 RFC-0011）。

# 4. Directory Structure（目录结构）

```text
my-novel/                        # Project 根目录
├── project.toml                 # 项目级配置（见 §5.1）
├── structure.toml               # 文档结构树（见 §5.2）
├── fragments/                   # Fragment 正文（见 §5.3）
│   ├── f_0001.md
│   ├── f_0002.md
│   └── ...
├── entities/                    # 语义实体（见 §5.4）
│   ├── characters/
│   │   └── c_8A91D4.toml
│   ├── locations/
│   │   └── l_3F2B1C.toml
│   ├── items/
│   │   └── i_A7E902.toml
│   └── organizations/
│       └── o_5D1C88.toml
├── knowledge/                   # Knowledge Base（见 §5.5）
│   ├── assertions.toml
│   └── evidence.toml
├── config/                      # 配置（见 §5.6）

├── .novelstudio/                # 工具私有目录（.gitignore，见 §5.7）
│   └── cache/
│       ├── location-index/
│       └── derived-edges/
└── .gitignore
```

## 4.1 文件数量预估（百万字小说）

| 目录 | 文件数（估） | 单文件大小 | 说明 |
|:--|:--|:--|:--|
| fragments/ | ~1000–2000 | ~1–5 KB | 每个约 500–1000 字 |
| entities/ | ~100–300 | ~0.5–2 KB | 角色、地点、道具等 |
| knowledge/ | 少量大文件 | ~50–200 KB | 断言与证据集中存储 |
| structure.toml | 1 | ~50–100 KB | 结构索引 |
| config/ | 1–3 | ~1–5 KB | 配置 |

> Fragment 数量较多但单文件小，在主流文件系统（APFS / ext4 / NTFS）下单目录 2000 文件无性能问题。若未来 Fragment 超过 5000，可采用分片子目录（`fragments/00/f_0001.md`），v0.1 不需要。

# 5. File Formats（文件格式）

## 5.1 project.toml（项目级配置）

```toml
# project.toml — 项目级配置

[project]
name = "雨夜行"
author = "Taiyuuki"
created = "2026-07-10"
language = "zh-CN"

# IR Schema 版本（RFC-0002 §10），Parser 据此执行迁移
ir_version = 1

# Knowledge Layer 配置（RFC-0015 §8.1）
[knowledge]
auto_contradict = false          # 断言冲突：false=人工裁决, true=自动标 contradicted

# AI Provider 默认配置（不在此存密钥，密钥从环境变量读取）
[ai]
default_provider = "claude"
extraction_model = "claude-sonnet"   # Extraction 用的模型
```

## 5.2 structure.toml（文档结构树）

**这是所有序列关系的唯一 Source of Truth。** 维护 Book → Chapter → Scene → Fragment 的完整层级与顺序。

```toml
# structure.toml — 文档结构树

[book]
id = "b_0001"                    # StableId
title = "雨夜行"
symbol = "rain_night"            # 可选 Symbol

# Chapter 顺序（数组 = 顺序，这是 Chapter 序列的唯一来源）
chapters = ["ch_01", "ch_02", "ch_03"]

# ---- Chapter 定义 ----

[chapter.ch_01]
title = "雨夜"                   # Display Name
symbol = "ch_storm_night"        # 可选
scenes = ["sc_01_01", "sc_01_02"] # Scene 顺序（唯一来源）

[chapter.ch_02]
title = "渡河"
scenes = ["sc_02_01"]

# ---- Scene 定义 ----

[scene.sc_01_01]
title = "推门"                   # 可选
pov = "c_8A91D4"                 # 视角角色的 StableId
fragments = ["f_0001", "f_0002"]  # Fragment 顺序（唯一来源）

[scene.sc_01_02]
title = "河岸"
pov = "c_8A91D4"
fragments = ["f_0003", "f_0004", "f_0005"]

[scene.sc_02_01]
pov = "c_9B3E01"
fragments = ["f_0006"]
```

### 顺序如何表达

顺序由**数组的元素顺序**表达，不使用 `prev` / `next` / `order` 字段：

- `chapters = ["ch_01", "ch_02"]` → ch_01 在 ch_02 之前
- `scenes = ["sc_01_01", "sc_01_02"]` → sc_01_01 在 sc_01_02 之前
- `fragments = ["f_0001", "f_0002", "f_0003"]` → 正文中按此顺序拼接

### 重排操作的 Diff 表现

| 操作 | 改动的文件 | Diff 范围 |
|:--|:--|:--|
| 改 Fragment 正文 | `fragments/f_0001.md` | 单文件 |
| 在 Scene 内重排 Fragment | `structure.toml`（该 Scene 的 fragments 数组） | 单行交换 |
| 移动 Fragment 到另一 Scene | `structure.toml`（两个 Scene 的数组各改一行） | 两行 |
| 在 Chapter 内重排 Scene | `structure.toml`（该 Chapter 的 scenes 数组） | 单行交换 |

> **注意：** prev/next（RFC-0002 §5.3 的链表）是 IR **内存层**的派生表示，Parser 加载时从 `fragments` 数组构建，保存时序列化回数组。**不持久化链表指针**。

### 拆分扩展点（未来）

百万字小说的 `structure.toml` 可能增长到数百 KB。v0.1 采用单文件，但格式预留拆分能力——`structure.toml` 支持按 Chapter include 子文件：

```toml
# structure.toml（拆分后）
[book]
chapters = ["ch_01", "ch_02"]
include = ["chapters/ch_01.toml", "chapters/ch_02.toml"]
```

```toml
# chapters/ch_01.toml（拆出的 Chapter 定义）
[chapter.ch_01]
title = "雨夜"
scenes = ["sc_01_01", "sc_01_02"]
```

**触发时机**：当 Book 超过约 50 个 Scene（或 structure.toml 超过 100 KB）时，Parser 提示拆分。v0.1 不实现自动拆分，但格式设计已不阻碍未来引入。

## 5.3 Fragment 文件格式

每个 Fragment 一个文件，**只存正文与锚点**，不存结构归属信息。

```markdown
<!-- fragments/f_0001.md -->

---
id: f_0001                      # StableId，必须 == 文件名（不含扩展名）
# 锚点：本 Fragment 涉及哪些 Semantic 实体
anchors:
  - entity: c_8A91D4          # StableId（或 Symbol，Parser 解析）
    role: appears             # appears | mentioned | referenced
  - entity: i_A7E902
    role: mentioned
---

林风推开门，雨水顺着他的发梢滴落。手中的油纸伞已被风吹折，
他望向河对岸灯火阑珊的客栈，迟疑了片刻。
```

### 格式规则

- **frontmatter 用 YAML**（Markdown 生态标准，Parser 通用）。
- **`id` 必填且必须等于文件名**——`fragments/f_0001.md` 的 `id` 必须为 `f_0001`。Parser 加载时校验，不匹配报 Error。这是 Cargo（`package.name`）、npm（`package.json`）、Unity（`.meta`）等工程的通行做法，防止重命名文件时丢失引用。
- **正文是 Markdown**，渲染时多个 Fragment 按 `structure.toml` 的顺序无缝拼接。
- **不含 `scene` 字段**——Scene 归属由 `structure.toml` 决定（见 §3）。
- **不含 `prev` / `next`**——顺序由 `structure.toml` 决定。
- **`anchors` 是 Source of Truth**——实体出场关系的原始事实。

### 锚点中的 Entity 引用

`anchors` 的 `entity` 字段可写 StableId 或 Symbol：

```yaml
anchors:
  - entity: c_8A91D4        # StableId（精确，推荐）
    role: appears
  - entity: hero            # Symbol（可读，Parser 通过 Symbol Table 解析）
    role: mentioned
```

Parser 解析时统一转为 StableId 存入 IR。Symbol 更可读但依赖 Symbol Table 完整性；StableId 更健壮。

## 5.4 Entity 文件格式

每个 Semantic 实体一个文件，存三重 ID + 属性。

```toml
# entities/characters/c_8A91D4.toml

id = "c_8A91D4"                  # StableId（不可变，文件名 = ID）
symbol = "hero"                  # Symbol（可改，RenameSymbol 只改此处）
display_name = "林风"            # Display Name

# 别名 / 称谓（Parser 用于文本实体识别）
aliases = ["林少侠", "风哥", "那个年轻人"]

# 可扩展属性（强类型字段由 Entity Model RFC 细化，这里只定义骨架）
[attributes]
age = 17
faction = "o_5D1C88"
# 自定义属性由插件扩展
```

### 各实体类型共用骨架

所有 Entity 文件共享以下必填字段：

| 字段 | 类型 | 说明 |
|:--|:--|:--|
| `id` | StableId | 不可变，等于文件名（不含扩展名） |
| `symbol` | String? | 可选，可改 |
| `display_name` | String | 正文与 UI 展示用 |
| `aliases` | [String] | 别名列表 |
| `[attributes]` | Table | 实体专属属性，由 RFC-0008/0014 等细化 |

### 文件路径规则

- `characters/c_8A91D4.toml` → `entities/<entity_type>/<stable_id>.toml`
- entity_type 映射：Character→characters, Location→locations, Item→items, Organization→organizations, Event→events
- **文件名 = StableId**，因此无需额外路径索引——给定 ID 即可定位文件。

## 5.5 Knowledge Base 文件格式

> **本节解决 RFC-0015 Open Question #3（KB 存储格式）。**

Knowledge Base 是 Source of Truth（RFC-0015 §5），提交 Git。采用 **TOML 集中存储**（与项目配置格式一致）。

```toml
# knowledge/assertions.toml — 已提交断言

[[assertion]]
id = "a_linxia_age_1"           # 断言的 StableId（前缀 a_）
subject = "c_8A91D4"             # 角色 StableId
predicate = "age"               # 属性
object = 17                     # 值
status = "active"               # active | superseded | contradicted
extracted_by = "manual"         # manual | ai:claude-sonnet-...

[assertion.valid]
from = "year-1086"
until = "year-1088"

[[assertion]]
id = "a_linxia_alive_1"
subject = "c_8A91D4"
predicate = "alive"
object = true
status = "active"
extracted_by = "ai:claude-sonnet"
evidence = ["ev_ch2_age", "ev_ch5_death"]

[assertion.valid]
from = "year-1086"
until = "year-1092"             # 角色死亡时间
```

```toml
# knowledge/evidence.toml — 证据

[[evidence]]
id = "ev_ch2_age"               # 证据的 StableId（前缀 ev_）
loc = "f_0001"                  # Fragment 的 StableId（复用 Location Index）
quote = "林风今年十七岁"
source = "manual"

[[evidence]]
id = "ev_ch5_death"
loc = "f_0042"
quote = "林风倒在了血泊中，再也没有站起来"
source = "manual"
```

### 为什么用 TOML 而非 YAML / JSON / 自定义 DSL

| 格式 | 选择理由 |
|:--|:--|
| **TOML** ✓ | 与项目配置统一；Rust 生态有成熟的 `toml` crate；无缩进陷阱（YAML）；支持注释；人类可读 |
| YAML ✗ | 锚点 frontmatter 已用 YAML（Markdown 生态惯例），但 KB 结构更复杂，YAML 的缩进敏感易出错 |
| JSON ✗ | 无注释，人类编辑不友好 |
| 自定义 DSL ✗ | v0.1 不值得投入 Parser 开发成本 |

### 为什么集中存储（而非每断言一文件）

- 断言数量远少于 Fragment（通常几十到几百条），集中存储可接受。
- 断言经常被批量审阅（"检查所有角色年龄矛盾"），单文件方便全局视图。
- 若未来断言数量爆炸，可按 predicate 分文件（`age.toml`, `alive.toml`），v0.1 不需要。

### 断言复杂度的演化路径

当前断言字段较精简（subject / predicate / object / valid / evidence / status）。未来可能增加 `confidence`（AI 抽取置信度）、`history`（状态变更记录）、`review`（人工审阅批注）等字段，单条断言变大。此时可拆分为每断言一文件：

```text
knowledge/
├── assertions/
│   ├── a_linxia_age_1.toml       # 每断言一文件
│   └── a_linxia_alive_1.toml
└── evidence/
    └── e_ch2_age.toml
```

**v0.1 采用集中存储**（`assertions.toml` + `evidence.toml`），但格式设计不阻碍未来拆分——拆分只是把 `[[assertion]]` 数组的每条移到独立文件，结构不变。

## 5.6 config/ 目录（配置）

存放项目级配置。用 `config/` 而非 `compiler/`，因为未来还会有 formatter、plugin、ai 等配置，统一收纳。**是配置，提交 Git。**

```text
config/
├── compiler.toml     # Lint 规则与严重级别
├── formatter.toml    # 文本格式化规则（未来）
├── ai.toml           # AI Provider 配置（未来）
└── plugins.toml      # 插件配置（未来）
```

### config/compiler.toml（Lint 规则配置）

类似 `.eslintrc` 的角色。

```toml
# config/compiler.toml — Lint 规则配置

# 启用 / 禁用规则
[rules]
dead_character_revived = "error"          # 死人复活 → Error
age_inconsistency = "error"               # 年龄矛盾 → Error
item_disappeared = "warning"              # 道具消失 → Warning
location_conflict = "warning"             # 地理冲突 → Warning
missing_scene_anchor = "warning"          # Scene 缺少锚点 → Warning
evidence_mismatch = "warning"             # 证据失配 → Warning

# 自定义规则（插件提供，见 RFC-0011）
[plugins.weather_consistency]
enabled = true
severity = "warning"

# 全局严重级别覆盖
[severity_overrides]
# 将某条默认 Warning 提升为 Error
item_disappeared = "error"
```

## 5.7 .novelstudio/cache/（派生缓存）

**不提交 Git**（`.gitignore`），可由 Compiler 随时重建。遵循 RFC-0001 §9.4。

> **路径改为 `.novelstudio/cache/`**（非根目录下的 `cache/`），与 `.vscode` / `.git` / `.idea` 的隐藏目录惯例一致，避免污染项目根目录。这与 RFC-0001 §9.4 的表述一致。

```text
.novelstudio/
└── cache/
    ├── location-index/      # 实体 → 文本块定位（RFC-0001 §10.1）
    ├── derived-edges/       # Fragment.anchors 的反向索引（RFC-0002 §7.3）
├── diagnostics-snapshot/    # 上次编译的诊断结果快照
└── ir-snapshot/             # IR 的序列化缓存（加速加载，可选）
```

- `.novelstudio/` 全部

# 7. Path Conventions（路径约定）

StableId 到文件路径的映射是确定性的，无需额外索引：

```text
StableId        →  文件路径
─────────────────────────────────────
f_0001          →  fragments/f_0001.md
c_8A91D4        →  entities/characters/c_8A91D4.toml
l_3F2B1C        →  entities/locations/l_3F2B1C.toml
i_A7E902        →  entities/items/i_A7E902.toml
o_5D1C88        →  entities/organizations/o_5D1C88.toml
b_0001          →  structure.toml（Book 恒为单例，特殊处理）
a_linxia_age_1  →  knowledge/assertions.toml（内嵌条目）
ev_ch2_age      →  knowledge/evidence.toml（内嵌条目）
```

### 前缀 → 实体类型 → 子目录 映射

| IdPrefix | 实体类型 | 目录 | 文件类型 |
|:--|:--|:--|:--|
| `f_` | Fragment | `fragments/` | `.md` |
| `c_` | Character | `entities/characters/` | `.toml` |
| `l_` | Location | `entities/locations/` | `.toml` |
| `i_` | Item | `entities/items/` | `.toml` |

# 8. Serialization & Reconstruction（序列化与重建）

## 8.1 持久化 → IR（加载）

Parser 加载 Project 时的步骤：

1. 读 `project.toml` → 获取 `ir_version`，必要时执行 Migration（RFC-0002 §10）。
2. 读 `structure.toml` → 构建 Document Graph：
   - `chapters` 数组 → Chapter 顺序 → 构建 Chapter 链表（内存层 prev/next）
   - 每个 `chapter.scenes` → Scene 顺序 → 构建 Scene 链表
   - 每个 `scene.fragments` → Fragment 顺序 → 构建 Fragment 链表
   - 反向建立 `Fragment → Scene`、`Scene → Chapter` 映射
3. 读 `fragments/*.md` → 填充 Fragment 正文与 anchors。
4. 读 `entities/**/*.toml` → 构建 Semantic Graph 节点 + Symbol Table。
5. 读 `knowledge/*.toml` → 构建 Knowledge Base。
6. 构建 Location Index、derived edges 等派生缓存（若 `.novelstudio/cache/` 失效）。

## 8.2 IR → 持久化（保存）

保存时的步骤（逆过程）：

1. 遍历 Document Graph，将链表序列化为 `structure.toml` 的数组。
2. 将每个 Fragment 的正文与 anchors 写回 `fragments/*.md`。
3. 将每个 Entity 写回 `entities/**/*.toml`。
4. 将 Knowledge Base 写回 `knowledge/*.toml`。
5. 序列化时遵守确定性约束（RFC-0002 §9）：按 StableId 排序，字段顺序固定。

## 8.3 增量保存（Incremental Save）

遵循 RFC-0001 §9.1 的"保存时增量"层级：

- Editor 跟踪脏文件集合（Dirty Set）。
- Ctrl+S 时只写回 Dirty Set 中的文件，不全量重写。
- `structure.toml` 若有结构变更则重写（它是结构 SoT，重排必涉及它）。

------

# 9. Deterministic Serialization（确定性序列化）

遵循 RFC-0002 §9，文件内容的序列化必须稳定：

- **TOML 输出排序**：`structure.toml` 中的 Chapter / Scene / Fragment 按定义顺序（数组顺序）输出；Entity 文件的 `aliases` 等数组按原始输入序。
- **YAML frontmatter**：锚点列表按 Fragment 内出场顺序（不重排），避免无意义 Diff。
- **无时间戳**：文件内不写入"最后修改时间"等非确定字段（Git 已记录提交时间）。
- **无机器信息**：不写入生成工具版本、操作系统等环境信息。

------

# 10. Relationship to RFC-0002

本 RFC 是 RFC-0002 Story IR 的**持久化映射**。二者的对应关系：

| RFC-0002（IR 内存层） | RFC-0003（持久化层） |
|:--|:--|
| `FragmentNode.prev/next` | `structure.toml` 的 `scene.fragments` 数组顺序 |
| `FragmentNode.scene` | `structure.toml` 的 `scene.fragments` 包含关系（反向推导） |
| `FragmentNode.text` | `fragments/<id>.md` 的正文 |
| `FragmentNode.anchors` | `fragments/<id>.md` 的 YAML frontmatter |
| `CharacterNode` 等 | `entities/<type>/<id>.toml` |
| `NodeStore`（BTreeMap） | 各目录下的文件集合（StableId = 文件名） |
| `SymbolTable` | Entity 文件的 `symbol` 字段（Parser 汇总构建） |

> **prev/next 不持久化：** RFC-0002 §5.3 的双向链表是 IR 内存层的高效遍历表示。持久化层用 `structure.toml` 的数组表达顺序，加载时构建链表，保存时序列化回数组。这是同一信息的两种表示，不违反 SoT。
