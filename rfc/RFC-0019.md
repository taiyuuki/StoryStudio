# 1. Abstract（摘要）

项目数据全部是磁盘明文（RFC-0003），因此**磁盘就是天然的实时真相源**。本 RFC 在桌面端（src-tauri）引入项目级文件监听：`notify` + 防抖器守在项目目录上，把变更以 Tauri 全局事件推给前端，前端按内容合并规则更新 store——使 **MCP 写入、外部编辑器直接改 TOML** 都能秒级反映到界面。

核心设计信条：

> **去重不问"是谁写的"，只问"前端是否已知这份内容"。**
>
> UI 自己保存、进程内 MCP / 妙笔写入、外部编辑器改文件，三类来源在 watcher 眼里一律平等。重复推送靠"内容已知则合并为 no-op"消解，正确性不依赖任何来源检测。

------

# 2. Motivation（为什么需要）

桌面端打开项目后，写盘来源有三类，前端对它们的知情程度完全不同：

| 来源 | 写入路径 | 前端是否知情 |
|:--|:--|:--|
| UI 命令（保存片段、建档、改设定…） | Tauri command → `story_studio_lib` mutations | **知情**——命令返回后前端已在 store 本地 patch |
| 进程内写（MCP HTTP、妙笔工具、逐章流水线、AI 续写） | 同上，经同一把 ProjectLock | **部分知情**——依赖各操作事后手动 `refresh()`，时机不保证、覆盖不全 |
| 外部写（文本编辑器改 TOML、外部 CLI、git restore） | 任意 | **完全不知情** |

后两类的现状：外部 Agent 或编辑器改了书，桌面界面停在旧数据上，直到用户碰巧触发一次刷新。对一个"数据全在明文文件里"的工具，这是可感知的割裂——文件明明变了，界面装作没变。

期望形态：**项目打开期间，界面是磁盘的实时镜像**；任何来源的落盘在典型 0.8s、最坏 1.5s 内反映到前端（延迟构成见 §3 Goal 1），且 UI 自己保存时不会产生可见的重复更新。

------

# 3. Goals / Non-Goals

**Goals**

1. MCP / 外部编辑器写入 → 前端秒级自动更新。端到端延迟预算：Rust 防抖 400ms + 前端 300ms + IPC refetch ≈ 50ms + 渲染 ≈ 50ms ≈ **0.8s 典型 / 1.5s 最坏**（多文件批量跨两个防抖窗口）。前端 300ms 是**固定批处理间隔**而非 trailing 防抖：定时器随首个批次启动、固定 300ms 到期、取走全部累积路径后重置——持续写入流下最坏延迟恒有界，每 300ms 出一批（幂等，无害）。
2. UI 自己保存触发的 watcher 回推，对用户**严格不可见**（不闪回、不重置滚动、不重复编译）。
3. 三类写入来源统一一套机制，不给每条写路径打来源标记（不侵入 mutations 签名）。
4. watcher 不参与 ProjectLock，不加剧写争用。

**Non-Goals**

1. 不做协作编辑（OT / CRDT）——冲突采用 last-write-wins + 提示（§8.3）。
2. 不做文件事件持久化 / 重放——重启后靠全量加载对齐。
3. 不承诺网络盘、休眠唤醒场景的实时性——提供聚焦兜底（§10，Phase 2）。
4. 不监听 `.novelstudio/` 内部账本（统计、日志、版本快照、缓存、锁文件）——它们不是书籍数据。

------

# 4. 现状抓手（为什么这套设计恰好成立）

本 RFC 不引入新的并发原语，而是搭在四个既有事实上：

**4.1 明文 + 原子替换**——所有数据文件经 `write_atomic`（同目录 `.tmp` → fsync → rename，`crates/project-format/src/atomic.rs`）落盘。watcher 任意时刻读文件，读到的都是完整一代数据，不存在半截 TOML。代价是 rename 会产生一串事件（remove/create/modify），必须在事件层合并。

**4.2 UI 写后前端已自更新**——`workspace.ts` 的每条写命令都在返回后本地 patch（`patchSceneLocal`、`f.text` 回写、`ws.chapters.push`…），十余处操作已把 `void refresh()` 当惯例。所以"UI 保存又触发 watcher 回推"本质是**推送前端已知的内容**——内容比对即可消解。

**4.3 运行时噪音全部隔离在 `.novelstudio/`**——stats.json（`stats.rs`）、写取证日志（`journal.rs`）、片段版本快照（`history.rs`）、cache（`paths.rs`）、跨进程锁文件，加上 `.git/` 与 `*.tmp` 暂存文件，排除后剩下的**恰好全是有语义的书籍数据**：

```text
project/
├── project.toml  structure.toml  chapters.toml  threads.toml
├── outline.toml  relations.toml  anchoring.toml        ← 根级 TOML，全监听
├── fragments/*.md                               ← 正文
├── entities/**.toml                             ← 设定档案
├── worldview/  knowledge/  config/  guides/  prompts/   ← 全监听
└── .novelstudio/  .git/  *.tmp                  ← 全排除
```

**4.4 单一写咽喉**——进程内所有写入（UI / MCP / 妙笔）最终都过 `write_atomic`，且都在 ProjectLock 写守卫内（`project_lock.rs`）。这给 Phase 2 的"自写记账"留了唯一挂点（§7.2 L3）。

# 5. 总体架构

```text
磁盘文件变更（UI 保存 / MCP / 妙笔 / 流水线 / 外部编辑器 / git restore）
   │
   ▼
notify + notify-debouncer-full          ← src-tauri 专用线程
   │  排除 .novelstudio/  .git/  *.tmp    （§6.2）
   │  防抖 400ms，rename 事件串合并成批次   （§7.2 L1）
   ▼
AppHandle::emit("project-fs-changed", { files: [相对路径] })
   │
   ▼
workspace store：listen + 300ms 二次合并（固定批处理间隔，非防抖——§3 Goal 1）  ← 前端
   │  按 paths 粗分类（§8.2）
   ▼
含 fragments/ 或根级结构文件 → 重拉当前 scene，按 §8.1 合并规则回写
其余 / 混合变更                → refresh()（整树替换，既有惯例）
全部路径                       → scheduleCompile()（1.2s 防抖，天然去重）
```

事件**只携带"哪些文件变了"，不携带数据**。前端收到后自己去读（refetch），watcher 是提示器不是数据通道——这避免了"事件里的快照已过时"的整类问题。

# 6. Watcher 设计（src-tauri）

## 6.1 选型与落点

`notify`（平台后端：macOS FSEvents / Linux inotify / Windows ReadDirectoryChangesW）+ `notify-debouncer-full`，直接依赖进 `app/src-tauri`，不用社区 Tauri 插件——逻辑很薄（过滤 + 转发），插件反而引入不必要的权限面。

## 6.2 监听范围与过滤

递归监听项目根；防抖批次内过滤掉以下相对路径，**过滤后为空的批次不 emit**：

| 排除项 | 理由 |
|:--|:--|
| `.novelstudio/**` | stats / journal / history / cache / tool-gate.lock——高频运行时噪音，无界面语义 |
| `.git/**` | git 内部对象，书籍数据变更会以工作区文件事件再次出现 |
| `*.tmp`（任意层级） | `write_atomic` 的暂存文件，rename 前的中间态 |

## 6.3 生命周期（对偶 MCP 服务模式）

照抄 `mcp_server_start/stop/status` 的既有模式（`commands.rs`）：全局 `Mutex<Option<WatcherHandle>>` 槽位 + 两个命令：

| 命令 | 行为 |
|:--|:--|
| `watch_start(root)` | 启动（已运行且同 root 则幂等返回；root 变化则先停旧再启新） |
| `watch_stop()` | 停止（未运行为空操作） |

前端挂钩点：`openRoot` 成功后启动（紧挨现有 `mcpFollowProject`）；`closeProject` 停止；切书由 root 变化的幂等重启覆盖。**watcher 生命周期 = MCP 服务生命周期 = 当前打开的项目**，三者对齐。

## 6.4 异常恢复与健康上报

watcher 线程 panic 或 `notify` 底层报错（macOS FSEvents 句柄耗尽、Linux inotify watch 数达上限 `fs.inotify.max_user_watches`、Windows 缓冲区溢出）时的处理：

1. **错误捕获**——watcher 线程用 `catch_unwind` 包裹事件循环；`notify` 返回的 `Error` / `Event::Error` 统一进 `tracing::error!`。
2. **状态上报**——新增 `watch_status` 命令，返回 `Running | Stopped | Error(reason)`；前端在 status bar 或项目抽屉角标展示，`Error` 状态显示"文件监听已断开"警示。
3. **自动重试**——错误后延迟 5s 自动重建 watcher（最多 3 次，指数退避 5s / 15s / 45s）；连续 3 次失败则锁定 `Stopped`，前端 toast 提示"文件监听多次失败，已停止。可手动重启或等待窗口聚焦时兜底刷新"。
4. **聚焦兜底联动**（Phase 2）——watcher 处于 `Error` / `Stopped` 状态时，窗口聚焦兜底（Phase 2，§10）自动升级为每次聚焦必跑，不再依赖"是否可能丢了事件"的启发判断。

## 6.5 事件契约

```ts
// 事件名：project-fs-changed
{ files: string[] }   // 相对项目的路径，'/' 分隔，已去重排序
```

**事件不携带事件类型**（create / modify / delete）。取舍理由：

1. 原子替换（rename）在不同平台上产生的事件类型组合不一致（macOS 常报 create，Linux 常报 modify），逐类型分流需要大量平台特例；
2. 前端的处理逻辑对类型不敏感——无论文件是新增、修改还是删除，都走同一套 refetch + 内容合并（§8）；文件消失时 refetch 自然返回 404 / null，由上层处理；
3. 防抖合并窗口内同一路径可能经历 delete → create（原子替换的事件串），拆分类型反而让前端多跑一轮无谓的"场景消失 → 又回来"。

Rust 端是哑管道：不分类、不解析语义、不读文件内容。分类放前端——只有前端知道自己当前打开的场景（§8.2）。

# 7. 去重模型（本 RFC 的核心）

## 7.1 原则：内容已知性，而非来源识别

直观思路是"标记写入来源，自己的写就别推了"。本 RFC 明确**不做**：

1. 来源标记要穿三层（Tauri command → studio-lib mutations → write_atomic），侵入所有签名；
2. 进程内 MCP 与 UI 命令走**同一条** mutations 路径，进程内无法靠路径区分，还得再引入 actor 概念；
3. 就算分清了来源，前端仍需内容合并兜底（事件可能乱序、合并到达）——那正确性反正靠合并，来源识别就只剩省一次 refetch 的优化价值。

统一改问一个问题：**"推送的内容，前端是否已经知道？"** 已知 → 合并为 no-op；未知 → 更新。三类来源自然统一。

## 7.2 三层防线

| 层 | 机制 | 必要性 | 消除什么 |
|:--|:--|:--|:--|
| **L1 事件防抖** | debouncer 400ms + 前端 300ms 定时器合并 | **必须** | 一次原子替换的事件串；一次 MCP 批量调用的多文件写入 |
| **L2 前端内容合并** | 片段 text 仅在"saved 且新 text ≠ 旧 text"时赋值；非 saved 状态绝不回写（§8.1） | **必须（正确性保障）** | UI 保存后的回推（内容相等 → 不赋值 → 严格 no-op） |
| **L3 自写记账** | `write_atomic` 咽喉挂 thread-local 记账 `path → 内容哈希`，仅 UI 命令的写守卫启用；watcher 事件哈希命中账本则**不 emit** | 可选优化（Phase 2） | UI 写入引发的整条事件链（省一次 refetch + 一次防抖批次） |

> **L2 是正确性的唯一承载**：内容相等 ⇒ 赋值被跳过 ⇒ CodeMirror 不换文档 ⇒ 滚动、IME、选区纹丝不动。UI 保存 → watcher 回推 → 合并 no-op，全程用户不可见。

> **L3 误判无害的性质**：哈希相等意味着这次推送本来就是 no-op，弃掉它不损失任何正确性——正确性永远不依赖 L3。这就是把 L3 放在优化层而非正确性层的理由。

L3 的挂点：Tauri 命令的 `write_gate` 守卫（`commands.rs`）启用 thread-local 记账，MCP / 妙笔工具的守卫不启用——进程内两类写在此分岔，无需改 mutations 签名。账目带时间戳，过期（如 10s）淘汰。

## 7.3 反模式（明确不做）

- **mtime + 路径的"最近我写过"窗口**：原子替换下相同内容也会换 inode、变 mtime，只能靠内容哈希做键。
- **actor 枚举穿透 mutations**：见 §7.1。
- **事件携带数据快照**：防抖批次读取时文件可能又变了，快照即刻过时；前端 refetch 永远拿当前代（见 §9）。

# 8. 前端合并规则

## 8.1 片段级（唯一敏感区）

编辑器防闪回是既有铁律（`saveFragment` 的保存单飞 + 过时文本不回写，`workspace.ts`），watcher 回写遵守**同一套守卫**：

| 片段保存状态 | 磁盘 vs store | 处理 |
|:--|:--|:--|
| `saved` | text 相同 | **不赋值**（防 CodeMirror 换文档导致滚动重置） |
| `saved` | text 不同 | 赋值新 text + 重算字数（外部/MCP 改写正文，实时反映） |
| `dirty` / `saving` / `error` | 任意 | **绝不回写 text**；toast 提示冲突（§8.3） |
| 任意 | anchors 等元数据变 | 回写元数据（沿用"只回写 f.anchors 不碰 text"的既有做法） |

## 8.2 场景级 / 工作区级

| 变更路径 | 动作 |
|:--|:--|
| `fragments/**` 或根级结构文件（structure / chapters） | 重拉当前 `getScene`（场景↔片段的映射在结构文件里，路径上判断不了归属，直接重拉当前场景最便宜）；当前场景已在磁盘上消失 → `scene = null` + `refresh()` |
| 其余（entities / worldview / knowledge / threads / relations / anchoring / outline / config / guides / prompts / project.toml） | `refresh()` 整树替换——`ws` 全量替换是本 app 既有惯例，面板按 id 为 key 渲染，无害 |
| 全部 | `scheduleCompile()`（复用 1.2s 防抖，与保存路径共享计时器，**不会双跑编译**）+ `void refreshStats()` |

监听注册一次（store 初始化时 `listen('project-fs-changed')`），事件仅在 watcher 存活时发出，无需随项目挂卸。

## 8.3 冲突提示（dirty 片段 vs 磁盘变更）

用户编辑中（dirty）的片段被外部修改：静默跳过回写，弹一次性 toast——"此段在磁盘上已被外部修改，保存时将以你正在编辑的内容为准"。**last-write-wins**：用户下次保存以保存时刻的编辑器全文覆盖，外部改动丢失（Non-Goal §3.1，diff 视图留 Open Question）。

增强措施（Phase 1 可选 / Phase 2）：冲突发生后在该片段的保存按钮旁显示橙色冲突标记（`conflictedSince` 时间戳），提示用户磁盘版本已不同；保存动作时弹二次确认——"此片段在你编辑期间被外部修改（{时间}），确认以当前编辑内容覆盖？"。具体交互形态见 Open Question §13.1。

# 9. 并发与一致性

**watcher 不取 ProjectLock。** 理由：

1. 它只读，而写入是原子替换（§4.1）——任意时刻读到的都是完整一代，读无需与写互斥（既有读命令同样不加闸的同一论证）；
2. 事件线程若排队等锁，会被长写（流水线批量落盘）阻塞，拖慢所有项目的推送；
3. 事件只是"有变化"的提示，真正的数据由前端 refetch 获得，refetch 走既有读路径，天然读到锁后的一致代。

**时序安全**：防抖批次到达时文件可能已被再次修改——无所谓，前端 refetch 读的是当下状态，最坏情况是连续两个批次、后一个的 refetch 结果已覆盖前一个（幂等）。**事件丢失**（休眠唤醒、网络盘）是真实风险，兜底见 §10，不靠 watcher 自身可靠性。

# 10. 边界情况

| 情形 | 处理 |
|:--|:--|
| AI 续写 / 流水线流式期间（`aiWriting` / workflow 运行中） | 见 §10.1 暂存策略 |
| 当前场景被外部删除 | `getScene` 失败 → `scene = null` + `refresh()` + toast |
| git restore 等批量重写 | 一批防抖事件 → 一次 `refresh()` + 一次编译——正是想要的行为 |
| watcher 启动瞬间 | 无需 baseline：启动前的事件收不到，启动后的第一个事件按正常流程处理 |
| 事件丢失（休眠 / 网络盘） | Phase 2：窗口聚焦时主动 `refresh()` + `scheduleCompile()` 兜底；极端介质可配置 PollWatcher 降级 |
| 同一内容被再次写入（touch / 重复保存） | L2 内容比对吸收，no-op |
| watcher 线程 panic / notify 底层报错 | §6.4 异常恢复：自动重试 + 状态上报 + 聚焦兜底升级 |

## 10.1 AI / 流水线暂存策略

流式写入（AI 续写）或逐章流水线期间，watcher 事件风暴会导致前端反复重拉场景，产生闪烁和无谓开销。处理方式：

> **MCP 连续写不在暂存范围内**：外部 Agent 批量调用前端无法感知（没有可检测的运行信号），也不需要——每次写间隔通常 > 400ms，各自成批，每批一次廉价 refetch，相等内容由 L2 吸收。暂存只覆盖前端自身持有运行标志的场景。

**进入暂存**：前端检测到 `aiWriting === true`（`workspace.ts`）或 `useBookStore().running === true`（`book.ts`）时，watcher 事件处理器切换为暂存模式——事件路径收集进 `Set<string>`（天然去重），不立即执行 §8 的分流逻辑。

**暂存期间行为**：
- 路径 Set **无容量上限**——项目文件数量有限（典型数百、极端数千），路径字符串 Set 内存可忽略（< 1MB）；
- 暂存期间新到事件只做 Set.add，**O(1)**，不读文件、不 refetch、不编译；
- 若暂存超过 **5 分钟** 仍未结束（流水线异常挂住），自动降级：清空 Set 并退出暂存模式，恢复实时处理，同时触发一次 `refresh()` + `scheduleCompile()` 全量兜底。

**退出暂存**（流结束 / workflow 完成）：
1. 取出累积的路径 Set，作为一个**合成大批次**走 §8.2 的分流逻辑——效果等同于"暂存期间的所有变更在结束瞬间一次性到达"；
2. finish 路径自身的刷新（`aiWriting` 结束时的既有 refresh）与 watcher 补推是幂等的——L2 内容合并保证不重复；
3. 清空 Set，恢复实时处理。

# 13. Open Questions

1. **冲突 UI 形态**——toast 是最小实现；保存按钮橙色标记 + 二次确认（§8.3）与 banner + diff 视图（"磁盘版本 vs 你的未保存版本"）之间的档位如何取舍？建议 Phase 1 上线后观察冲突频率再定。
2. **多窗口 / 多前端**——当前单窗口架构下事件广播天然够用；未来若多窗口，`emit` 广播即覆盖，无需改设计。
3. **guides / prompts 的细粒度热更新**——当前并入整树 refresh；若提示词编辑页需要独立响应，再按路径加规则。
4. **L3 是否值得做**——一次多余 refetch 的成本（KB 级文件 × 数十）与记账复杂度的权衡，建议 Phase 1 上线后实测再定。
5. **聚焦兜底的触发面**——仅窗口聚焦，还是加低频心跳（如 30s）？取决于实测中 FSEvents 的丢事件率。
6. **大项目下 `refresh()` 整树替换的性能基线**——数百 entities、上千片段时，全量 refetch 的 IPC 开销与 Vue reactivity 渲染成本是否可感？若超过 100ms 需考虑按变更路径细粒度 refetch（如 entities/** 只重拉 entities 子树）。建议在测试中造一个 50 万字级别的样本项目实测。
7. **防抖是否需要 leading edge**——当前 trailing edge 防抖（400ms + 300ms）对单文件写入偏保守；改为"首事件立即推送 + 后续防抖"可将单写延迟压到 ~400ms，但会增加事件批次数（每批都触发一次前端分流判断）。Phase 1 先按 trailing 上线，实测延迟不满意再议。
