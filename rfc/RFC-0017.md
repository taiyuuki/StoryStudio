# 1. Abstract（摘要）

Narrative Thread（叙事线索）是 Story Studio 的**叙事模型**。它不是建模世界（World），而是建模叙事（Narrative）——追踪作者设计的故事节奏与信息流。

```text
   Assertion（Knowledge Layer）     回答："这件事是否为真？"
         ↑ 引用
   Narrative Thread                  回答："谁知道？何时埋？何时揭晓？"
         ↓ 关联
   Scene / Character / Outline       回答："在哪个场景？涉及谁？"
```

Thread 统一承载所有长期叙事元素：

- **伏笔（Foreshadowing）**——埋下后回收
- **悬疑（Mystery）**——逐步揭晓
- **秘密（Secret）**——角色知道、读者不知道
- **阴谋（Conspiracy）**——多角色、多层次的暗线
- **感情线（Relationship Arc）**——角色关系的演变轨迹
- **主线 / 支线（Story Arc）**——贯穿全书的叙事骨架
- **预言 / 承诺 / Flag**——长期悬挂、等待触发的叙事元素

> **Thread 不是 Knowledge。Knowledge 只是 Thread 的一部分——Thread 管理的是"故事怎么讲"，不是"世界里有什么"。**

------

# 2. Motivation（为什么需要 Thread）

RFC-0001 §2 列出的痛点中，有一类无法靠 Assertion 或 Compiler 的时序规则解决：

- **伏笔遗忘**——埋了不回收
- **线索断裂**——线索发展了一半突然消失
- **信息差失控**——角色不应该知道的事，角色却基于它行动了
- **节奏失衡**——所有线索集中在后半回收，前半没有钩子

这些是**叙事层**的问题，不是事实层的问题。Assertion 能告诉你"林风是皇子"这个事实为真，但无法告诉你"读者什么时候知道林风是皇子"、"周明什么时候猜到的"、"这个伏笔到结尾有没有回收"。

Thread 就是管理这些叙事维度的一等公民。

------

# 3. Layer Position（层级定位）

Thread 引入了一个新的概念层：**Narrative Layer**。

```text
   ┌──────────────────────────────────────────┐
   │          Narrative Layer（叙事层）          │
   │  Thread（叙事线索）                          │
   │  Outline（故事大纲，见 RFC-0016）              │
   └──────────────────────┬───────────────────┘
                          │ 引用
   ┌──────────────────────┴───────────────────┐
   │          Semantic Layer（语义层）            │
   │  Character / Location / Item / Organization │
   └──────────────────────┬───────────────────┘
                          │ 锚定
   ┌──────────────────────┴───────────────────┐
   │          Document Layer（文档层）            │
   │  Book / Chapter / Scene / Fragment          │
   └────────────────────────────────────────────┘
```

| 层 | 建模对象 | 代表问题 |
|:--|:--|:--|
| Document | 文本结构 | "第几章第几场景？" |
| Semantic | 世界实体 | "涉及哪些角色？" |
| **Narrative** | **叙事对象** | **"谁知道？何时埋？何时回收？"** |
| Knowledge | 客观事实 | "这件事是否为真？" |

Thread 横跨所有层——它引用 Semantic 的实体、Document 的场景、Knowledge 的 Assertion、Narrative 的 Outline。

------

# 4. Core Concepts（核心概念）

## 4.1 Thread

一条叙事线索——贯穿故事的一个长期叙事元素。

Thread 是独立的叙事对象，**不必须依赖 Assertion**。很多线索（如感情线、成长线）根本没有事实层的对应物——Thread 本身就是叙事层的一等公民。

```toml
# threads.toml

[[thread]]
id = "t_001"
title = "林风的皇子身份"
description = "林风实际上是前朝皇子，幼年被隐士收养，自己并不知情。"

# 这个叙事对象的目标（给 AI 的上下文）
goal = "最终在第三幕揭晓林风的身份，引发抉择"

# 优先级（影响检查规则严格度）
priority = "main"              # main | minor（main 未回收 → Error，minor → Warning）

# 标签（开放集合，不用 enum）
tags = ["foreshadowing", "identity", "secret"]

# 关联的底层事实（可选——引用 Knowledge Base 的 Assertion）
# 很多 Thread（如感情线）不需要关联 Assertion
assertions = ["a_00152", "a_00153"]

# 叙事锚点（这些是作者输入的，status 由系统从这些推导——见 §4.3）
planted_at = "sc_01_02"     # 在哪个场景埋下
revealed_at = null           # 尚未揭晓
resolved_at = null           # 尚未回收

# 唯一需要作者手工维护的状态标记
abandoned = false            # 作者决定放弃此线索

# 线索关联（伏笔回收网络）
resolves = []                # 本线索回收了哪些线索
resolved_by = []             # 本线索被哪些线索回收

# 叙事对象关系（多对象线索，如三角关系涉及三个角色）
[[thread.relationships]]
entities = ["c_001", "c_002", "c_005"]
relation = "love_triangle"
description = "林风、周明、林雨的三角关系"

# 知识状态（核心维度——见 §4.2）
[[thread.knowledge]]
observer = "reader"
state_timeline = [
    { scene = "sc_01_02", state = "suspected" },
    { scene = "sc_03_01", state = "known" },
]

[[thread.knowledge]]
observer = { character = "c_001" }     # 林风自己
state_timeline = [
    { scene = "sc_05_03", state = "suspected" },
    { scene = "sc_07_02", state = "known" },
]

[[thread.knowledge]]
observer = { character = "c_002" }     # 周明
state_timeline = [
    { scene = "sc_08_01", state = "known" },
]

[[thread.knowledge]]
observer = { organization = "o_001" }  # 青衣门
state_timeline = [
    { scene = "sc_02_01", state = "known" },
]
```

## 4.2 Knowledge State（知识状态）

每个 Thread 对每个**观察者**（Observer）有一条知识状态时间线。

### Observer

观察者可以是多种类型：

```rust
pub enum Observer {
    /// 读者（上帝视角的一种）
    Reader,
    /// 作者（总是知道一切，默认不显式声明）
    Author,
    /// 角色
    Character { entity: StableId },
    /// 组织
    Organization { entity: StableId },
    /// 全知叙述者（与 Reader 可区分）
    Omniscient,
}
```

> **Observer 统一处理**——Reader 不是特殊字段，而是 Observer 的一种。Compiler 统一遍历 observer 列表，代码简洁。

### Knowledge State

单个观察者在某时间点的知晓程度：

```rust
pub enum KnowledgeState {
    /// 完全不知道
    Unknown,
    /// 怀疑 / 猜测（有线索但不确定）
    Suspected,
    /// 确切知道
    Known,
}
```

状态是**渐进的**：`Unknown → Suspected → Known`。

> **不用 known_until**——小说中角色"知道了"之后一般不会忘掉（除非失忆/魔法等极少数场景，用新的 state_timeline 条目表达即可）。

### State Timeline

每个观察者的状态随场景变化，记录为时间线：

```toml
state_timeline = [
    { scene = "sc_01_02", state = "suspected" },   # 开始怀疑
    { scene = "sc_03_01", state = "known" },        # 确认
]
```

- 在 `sc_01_02` 之前，该观察者对这条线索的状态是 `Unknown`（默认）。
- 在 `sc_01_02` 到 `sc_03_01` 之间，状态是 `Suspected`。
- 在 `sc_03_01` 之后，状态是 `Known`。

> **初始态**：所有观察者在全书第一个场景之前的状态都是 `Unknown`（包括 reader——读者在开篇前什么都不知道，除非是开篇旁白直给）。这是一个明确的初始态，推导状态机从 `Unknown` 开始。

Compiler 可查询"某角色在某场景的知识知识"，用于检查信息差一致性。此检查依赖 RFC-0009 的全局时序——若 Scene 的 `story_time` 乱序，knowledge state 的推导会失效，因此 Thread 的时序检查强依赖 Timeline 排序。

## 4.3 Thread Status（线索生命周期——自动推导）

> **status 不是作者手工维护的字段，而是系统从其他字段推导的。**

作者只需维护以下输入：
- `abandoned`（布尔）——唯一的手工状态标记
- `planted_at` / `revealed_at` / `resolved_at`（场景 ID）——叙事锚点
- `knowledge`（观察者状态时间线）——信息可见性

系统从这些输入推导 Thread 的当前状态：

```rust
/// 推导出的 Thread 状态（只读，不持久化）
pub enum ThreadStatus {
    /// 计划中：planted_at 为 null（作者标注了意图但未写入正文）
    Planned,
    /// 已埋下：planted_at 不为 null，revealed_at 为 null
    Planted,
    /// 已揭晓：revealed_at 不为 null，resolved_at 为 null
    Revealed,
    /// 已回收：resolved_at 不为 null
    Resolved,
    /// 已放弃：abandoned = true（作者决定放弃）
    Abandoned,
}

/// 推导逻辑（纯函数）
fn derive_status(thread: &Thread) -> ThreadStatus {
    if thread.abandoned {
        return ThreadStatus::Abandoned;
    }
    if thread.resolved_at.is_some() {
        return ThreadStatus::Resolved;
    }
    if thread.revealed_at.is_some() {
        return ThreadStatus::Revealed;
    }
    if thread.planted_at.is_some() {
        return ThreadStatus::Planted;
    }
    ThreadStatus::Planned
}
```

推导规则：

| 条件 | 推导状态 |
|:--|:--|
| `abandoned = true` | Abandoned（最高优先级） |
| `resolved_at` 不为 null | Resolved |
| `revealed_at` 不为 null | Revealed |
| `planted_at` 不为 null | Planted |
| 全为 null | Planned |

> **为什么不手工维护 status？**
> 1. **心智负担**——作者改了 planted_at 后还得记得改 status，容易遗忘导致过期。
> 2. **矛盾风险**——手工 status 可能与锚点矛盾（status=resolved 但 resolved_at=null），产生无意义的诊断。
> 3. **Abandoned 足够**——除了"放弃"这个需要显式表达的意图，其余状态都能从锚点自动推导。
>
> status 是**派生数据**（如 RFC-0003 §3 的链表），不持久化，每次需要时从输入字段计算。

### 优先级 Priority

```toml
priority = "main"    # main | minor
```

priority 影响 Compiler 检查规则的严格度：

| 规则 | main 线索 | minor 线索 |
|:--|:--|:--|
| 到结尾未 Resolved | **Error** | Warning |
| 从未 Planted（Planned 到结尾） | Warning | Info |

主线不回收是严重问题，支线不回收可接受。

### 目标 Goal

```toml
goal = "最终在第三幕揭晓林风的身份，引发抉择"
```

goal 是给 AI 的叙事意图说明。AI Runtime 构建上下文时，goal 告诉 AI "这条线要往哪个方向发展"。对于伏笔类线索，goal 通常是"何时、如何回收"；对于感情线，goal 通常是"关系的终态"。

### 叙事对象关系 Relationships

```toml
[[thread.relationships]]
entities = ["c_001", "c_002", "c_005"]
relation = "love_triangle"
description = "林风、周明、林雨的三角关系"
```

一条线索可涉及多个角色/实体（如三角关系、阴谋集团的多人博弈）。relationships 记录这些多对象关联，供 Compiler 检查和 AI 上下文使用。

## 4.4 Tags（开放标签）

Thread 的类型用**标签数组**表达，不用 enum：

```toml
tags = ["foreshadowing", "identity", "secret"]
```

常见标签（不固定）：

| 标签 | 含义 |
|:--|:--|
| `foreshadowing` | 伏笔 |
| `mystery` | 悬疑 |
| `secret` | 秘密（角色知道、读者不知道） |
| `conspiracy` | 阴谋 |
| `romance` | 感情线 |
| `prophecy` | 预言 |
| `promise` | 承诺 |
| `flag` | Flag（等待触发的叙事标记） |
| `identity` | 身份相关 |
| `betrayal` | 背叛 |
| `main_plot` | 主线 |
| `sub_plot` | 支线 |

> **开放集合**——作者和插件可自由添加标签，不被 enum 约束。Compiler 只关心少数结构化字段（status / planted_at / revealed_at），标签用于分类、查询、AI 上下文。

# 5. Thread Relationships（线索关联）

线索之间可以构成**回收网络**：

```toml
# 线索 t_001 回收了线索 t_002 和 t_003
[[thread]]
id = "t_001"
resolves = ["t_002", "t_003"]
resolved_by = []

# 线索 t_005 被 t_001 回收
[[thread]]
id = "t_005"
resolves = []
resolved_by = ["t_001"]
```

这支持"多条伏笔在一个高潮场景同时回收"的叙事模式。

# 6. Source of Truth Model（真相源模型）

| 数据 | 性质 | 进 Git | 存储位置 |
|:--|:--|:--|:--|
| Thread 定义 | Source of Truth | ✓ | `threads.toml` |
| Thread 引用的 Assertion | Source of Truth | ✓ | `knowledge/assertions.toml` |
| Thread 引用的 Scene / Entity | Source of Truth | ✓ | `structure.toml` / `entities/` |

**Thread 不复制引用对象的内容**——它只持有 ID 引用。修改 Assertion 的 object 时不需要改 Thread（符合 RFC-0003 §3 单一真相源）。

# 7. Compiler Rules（Compiler 检查规则）

> **确定性边界（RFC-0001 §3.4）：** Compiler 只做**确定性结构检查**——字段完整性、引用存在性、时序合法性、图结构合法性。
>
> **"伏笔是否被妥善回收"是语义判断**，由 Semantic Validator（AI）产出 Hint / Suggestion。Compiler **不**对叙事质量下 Error 定论。

Thread 为 Compiler 提供新的检查维度。规则属于 Semantic Phase。

检查规则基于**推导状态**（§4.3）而非手工 status。

## 7.1 确定性规则（Compiler，v0.1）

| 规则 ID | 检测 | 级别 |
|:--|:--|:--|
| `premature_reveal` | `revealed_at` 的场景早于 `planted_at` | Error |
| `thread_resolve_cycle` | `resolves` 引用图存在环（A 回收 B，B 回收 A） | Error |
| `resolve_without_reveal` | `resolved_at` 不为 null 但 `revealed_at` 为 null（可能笔误） | Warning |
| `orphan_thread_ref` | Thread 的 assertions / resolves / relationships / observer 引用了不存在的对象 | Warning |
| `unused_thread` | Thread 推导状态为 Planned（planted_at 为 null）且全书结束 | Warning（main）/ Info（minor） |
| `abandoned_thread` | `abandoned = true`（提示作者回顾） | Info |

> **所有规则都是确定性的**——检查的是字段值、引用 ID、图结构，不涉及正文语义。
>
> **没有 `unresolved_thread` Error**——"线索到结尾未回收"可能是作者有意设计（留到续作、开放式结局）。Compiler 只产 Warning 提示，最终判断交给作者或 Semantic Validator。

## 7.2 语义规则（Semantic Validator，未来）

| 规则 ID | 检测 | 级别 |
|:--|:--|:--|
| `semantic_unresolved` | 线索的 resolved_at 为 null，但正文读起来确实未回收（AI 阅读全文判断） | Hint |
| `weak_foreshadowing` | 线索 planted 后正文再无涉及（AI 检测） | Hint |
| `knowledge_inconsistency` | 角色在 Unknown/Suspected 的场景中基于该线索行动（AI 检测） | Hint |

> **语义规则永远非阻断**——它们帮助作者发现问题，但不阻止提交。作者拥有最终决定权（RFC-0001 §3.8）。

## 7.3 priority 的作用

priority **不影响 Compiler 规则的级别**（Compiler 的确定性规则是全局的）。priority 主要影响：

- **Semantic Validator 的提示优先级**——main 线索的 semantic_unresolved 优先提示
- **AI 上下文构建**——main 线索在 Prompt 中的权重更高
- **Editor 可视化**——main 线索用醒目颜色标记

# 8. File Format（文件格式）

遵循 RFC-0003 的 TOML 集中存储策略。

```toml
# threads.toml — 项目根目录
# 注意：TOML 不支持 null，可选字段省略即可（不写 = 默认值）

id = "t_001"

description = "林风实际上是前朝皇子。"

priority = "main"
tags = ["foreshadowing", "identity", "secret"]
assertions = ["a_00152", "a_00153"]
planted_at = "sc_01_02"
abandoned = false

[[thread.knowledge]]
observer = "reader"
state_timeline = [
    { scene = "sc_01_02", state = "suspected" },
    { scene = "sc_03_01", state = "known" },
]

[[thread.knowledge]]
observer = { character = "c_001" }
state_timeline = [
    { scene = "sc_05_03", state = "suspected" },
    { scene = "sc_07_02", state = "known" },
]

[[thread.knowledge]]
observer = { organization = "o_001" }
state_timeline = [
    { scene = "sc_02_01", state = "known" },
]

[[thread]]
id = "t_002"
title = "青衣门内鬼"
description = "青衣门内部有叛徒。"
goal = "第二幕揭晓内鬼身份"
priority = "main"
tags = ["mystery", "conspiracy"]
planted_at = "sc_03_02"

[[thread]]
id = "t_003"
title = "林风与林雨的感情线"

goal = "最终在第三幕抉择时达到情感高潮"
priority = "minor"
tags = ["romance"]
# 感情线不需要 assertions——Thread 本身就是叙事对象
planted_at = "sc_02_01"

[[thread.relationships]]
entities = ["c_001", "c_003"]
relation = "romance"
description = "林风与林雨"

[[thread]]
id = "t_004"
title = "废弃的支线：寻找龙珠"
description = "原计划的长生不老支线。"
priority = "minor"
tags = ["adventure"]
abandoned = true               # 作者放弃了这条线
planted_at = "sc_01_03"
```

```
project/
├── structure.toml
├── threads.toml          ← 本 RFC

├── fragments/
├── entities/

```

`threads.toml` 在项目根目录，与 `structure.toml` 同级。

### 前缀约定

Thread 的 StableId 前缀为 `t_`（如 `t_001`）。

# 9. AI Context（AI 上下文中的 Thread）

AI Runtime（RFC-0010）构建 Prompt 时，Thread 提供关键叙事上下文：

```text
当前场景：sc_05_03
POV：林风

涉及线索：
1. [developing] 林风的皇子身份
   - 读者：Known（已知）
   - 林风：Suspected（正在怀疑）
   建议推进：让林风发现更多证据

2. [planted] 青衣门内鬼
   - 读者：Unknown（不知）
   - 林风：Unknown
   建议保持：此场景不应让林风发现内鬼线索
```

AI 上下文使用 title 和 description（人类可读），不用 StableId。

1. **Thread 的增量更新**——作者改了 threads.toml 后，是否需要类似 Parser 的增量解析？Thread 数量通常远少于 Fragment，v0.1 全量解析可接受。
2. **Thread 与 Scene 的自动关联**——能否自动检测"哪些 Fragment 的正文涉及某 Thread"？需正文语义分析，属 Semantic Validator 范畴。
3. **Thread 的可视化**——Thread 回收网络（伏笔关系图）的可视化方案，属于 Graph（RFC-0012）。
4. **knowledge_inconsistency 的实现**——需要理解"角色基于某信息行动"的语义，可能需要 AI 辅助。
5. **Thread 版本与迁移**——Thread 模型演进时（新增字段）的迁移策略，复用 RFC-0002 §10 的 IRVersion 机制。

# Appendix

> **Thread 是 Story Studio 的叙事模型。它不建模世界，它建模故事——谁知道、何时埋、何时揭晓、是否回收。Thread 是独立的叙事对象，不必须依赖 Assertion。作者只维护意图（goal / priority / abandoned / 锚点），状态由系统自动推导。**
