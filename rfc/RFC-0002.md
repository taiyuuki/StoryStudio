# 1. Abstract（摘要）

Story IR 是 Story Studio 的核心数据结构——所有模块共享的、对故事的单一表示。

Story IR 是一个 **Typed Graph Model（类型化图模型）**，由两张图组成：

```text
   Document Graph   +   Semantic Graph   =   Story IR
   (文本结构)             (实体与关系)          (完整表示)
```

- **Document Graph**：表达"故事在文本上是怎么组织的"——Book → Chapter → Scene → Fragment 的层级，以及段落、对话块等文本节点。
- **Semantic Graph**：表达"故事在语义上涉及什么"——角色、地点、道具、组织等实体节点，以及它们之间的关系（出场、持有、位于、认识……）。

两张图通过 **Fragment** 桥接——Fragment 既是 Document Graph 的叶子节点，也是 Semantic Graph 实体出场的锚点。

------

# 2. Motivation

RFC-0001 §6 定义了 Story IR 为"Story 的标准表示"，但未规定其内部结构。本 RFC 回答：

1. IR 的内部数据结构是什么？（Typed Graph Model）
2. 实体如何被稳定引用？（三重 ID 系统）
3. 什么是所有子系统对齐的最小粒度？（Fragment）
4. 用什么类型系统表达？（Rust 类型定义）

这些决策一旦确定，即被 Parser / Compiler / Knowledge Layer / Editor / Export 全体引用，不得轻易变更。

------

# 3. Typed Graph Model（类型化图模型）

## 3.1 为什么是图，而不是树（AST）

Parser 产出的是 AST（树），但 AST 的生命周期仅在解析阶段。Story IR 需要在整个项目生命周期内存在，且需要表达**非层级关系**：

- 角色跨越多个章节出场（无法用树表达）
- 道具在不同角色间转手（多对多）
- 时间线与文本顺序不一致（倒叙、插叙）

树只能表达"包含"，图能表达"任意关联"。因此 Story IR 的结构基础是图。

## 3.2 双图模型

### Document Graph（文档图）

表达文本的物理 / 结构组织。

```text
Book
 └─ Chapter (ch_01)
     └─ Scene (sc_01_02)
         ├─ Fragment (f_0001)    ← 叶子，最小编辑单元
         ├─ Fragment (f_0002)
         └─ Fragment (f_0003)
```

- 节点类型：`Book`, `Chapter`, `Scene`, `Fragment`, `Paragraph`, `Dialogue`
- 边类型：`contains`（层级包含）
- **Fragment 是叶子节点**——Document Graph 的最细粒度
- 这张图是"树状为主"的（主要是 contains 边），但允许跨层级引用边（如 Scene 引用 Fragment 的另一种组织方式）

### Semantic Graph（语义图）

表达故事世界中的实体与关系。

```text
Character:linxia ──appears_in──► Scene:sc_01_02
Character:linxia ──holds────────► Item:umbrella
Character:linxia ──located_at───► Location:riverside
Character:linxia ──knows────────► Character:zhou
```

- 节点类型：`Character`, `Location`, `Item`, `Organization`, `Event`, `Concept`（见 §6）
- 边类型：`appears_in`, `holds`, `located_at`, `knows`, ...（开放集合，可由 Plugin 扩展）
- 边**带时序属性**（`valid` 区间），因为关系会随剧情变化（角色 A 第 3 章持有剑，第 7 章丢失）
- **Semantic Graph 的边可以引用 Document Graph 的节点**（如 `AppearsIn(Character → Scene)`），但 Scene / Chapter 本身不是 SemanticNode——它们只属于 Document Graph（见 §5.3）

### 桥接：Fragment 是两张图的交点

```text
Document Graph                    Semantic Graph
                                  
Scene:sc_01_02 ──contains──► Fragment:f_0001
                                   │
                              anchors (锚定)
                                   │
                                   ▼
                         Character:linxia ──appears_in──► Scene:sc_01_02
```

- 一个 Fragment 可以锚定多个 Semantic 实体（这段文本里林夏出场，且提到了伞）
- 一个 Semantic 实体可以被多个 Fragment 锚定（林夏在全书出场 200 次）
- **Fragment 是 Document Graph 唯一能锚定 Semantic 实体的节点类型**——这保证了"文本↔语义"的映射只发生在 Fragment 粒度，与 RFC-0001 §10.1 的"块级定位"一致

## 3.3 IR Invariants（架构不变量）

以下不变量是 Story IR 的结构性约束，**由 Compiler 的最底层检查保证**。违反任一条即产出 Error 级 Diagnostic：

1. **StableId 全局唯一**：每个 StableId 在整个 Project 中唯一，不存在重复。
2. **EdgeId 全局唯一**：每条 SemanticEdge 的 EdgeId 唯一（边是一级公民，见 §7.2）。
3. **Fragment 是叶子**：Fragment 是 Document Graph 的叶子节点，不 contains 任何子节点。
4. **只有 Fragment 能锚定 Semantic 实体**：其他 DocNode（Chapter / Scene / Book）不得拥有 `anchors` 字段。
5. **边的端点必须存在**：所有 SemanticEdge 的 `from` / `to` 必须指向存在于 SemanticGraph 或 DocumentGraph 中的节点。
6. **Document Graph 无环**：`contains` 边不形成环（Chapter 不能包含自身）。`prev/next` 链表也不成环。
7. **Semantic Graph 允许环**：`Knows(A→B)` 和 `Knows(B→A)` 可共存，不视为错误。
8. **StableId 永不复用**：被删除的 StableId 进入 tombstone，永不分配给新实体。
9. **链表完整性（内存层）**：若 A.next = B，则必须 B.prev = A（双向链表的一致性）。此不变量约束 IR 内存状态；持久化层（RFC-0003）用数组表达顺序，不存指针，加载时构建的链表必须满足此完整性。
10. **确定序列化**：所有持久化集合必须按 ID（StableId / EdgeId）确定序列化，与 §9 一致。

> 这些不变量是"结构安全网"——Compiler 首先验证它们，再执行更高级的时序 / 语义检查。任何 Change 提交后若违反不变量，即 Dry-Run 失败，阻止提交。

# 4. Triple ID System（三重 ID 系统）

实体有三个层级的标识，各有不可替代的用途：

| 层级 | 示例 | 可修改 | 生成方式 | 用途 |
|:--|:--|:--|:--|:--|
| **Stable ID** | `c_8A91D4` | **否** | 系统生成，终身不变 | Graph 边、存储、内部引用、Knowledge Layer 的 subject |
| **Symbol** | `hero`, `royal_guard` | 是（IDE 重构） | 作者或 AI 命名 | Parser 引用解析、Prompt 上下文、插件 API、可读引用 |
| **Display Name** | `林风` | 是 | 作者命名 | 正文、UI 展示、Diagnostics 展示 |

## 4.1 为什么需要三重

- **只用 Stable ID**：Graph 内部完美稳定，但 `c_8A91D4` 对人类不可读，Prompt 里塞一堆哈希毫无意义，Diff 无法 review。
- **只用 Symbol**：可读，但作者改了 Symbol（`hero` → `protagonist`）就要改所有引用，跨分支 Merge 时 Symbol 冲突无法自动解决。
- **只用 Display Name**：正文需要它，但"林风"可能重名（两个叫林风的角色），无法作为唯一键。

三重各司其职，**Stable ID 保证不变性，Symbol 保证可读性，Display Name 保证表现力**。

## 4.2 ID 生成规则

```rust
// Stable ID 的结构：类型前缀 + 不重复 token
// 前缀由实体类型决定，token 保证全局唯一
pub struct StableId {
    prefix: IdPrefix,   // c_, f_, l_, i_, o_, e_, ...
    token: IdToken,     // 短哈希或顺序号，保证唯一
}

pub enum IdPrefix {
    Character,    // c_
    Fragment,     // f_
    Location,     // l_
    Item,         // i_
    Organization, // o_
    Event,        // e_
    SemanticEdge, // se_  (边也是一级公民，见 §7.2)
    // ...
}
```

**Token 生成策略（按实体类型区分）：**

| 实体类型 | Token 策略 | 示例 | 理由 |
|:--|:--|:--|:--|
| Fragment | 顺序号（全局递增） | `f_0001`, `f_0002` | Fragment 有天然顺序，顺序号利于排序与定位 |
| 其他实体 | 短哈希（随机/内容派生） | `c_8A91D4` | 无天然顺序，哈希避免冲突；8 位足够百万级唯一 |

> **设计约束：** Stable ID 一经分配，即使实体被删除也不复用其 ID（tombstone 机制），防止悬空引用指向新实体。

## 4.3 解析链

```text
正文中的 "@hero"  ──Parser──►  Symbol: "hero"
                                   │ Symbol Table 查找
                                   ▼
                              StableId: c_8A91D4
                                   │
                                   ▼
                              Display Name: "林风"  (用于渲染正文)
```

- **Symbol Table**：`Symbol → StableId` 的映射表，由 Parser 维护，存于 IR。
- Symbol 可重名（不同 scope 下），解析时按 scope 规则消歧（v0.1 全局唯一即可，scope 留待后续）。
- 重命名 Symbol 是一个 Change（`RenameSymbol`），只更新 Symbol Table，不改 Stable ID，因此不破坏任何 Graph 边。

# 5. Fragment（最小编辑单元）

## 5.1 定义

> **Fragment 是 Story IR 的最小编辑单元。所有子系统以 Fragment 为对齐粒度。**

Fragment 不是"文件切片"概念——它不是因为"方便存文件"才存在，而是因为：

- AI 一次处理一个 Fragment
- Parser 增量解析一个 Fragment
- Compiler 增量检查一个 Fragment
- Git Diff 一个 Fragment
- Review 一个 Fragment
- Merge 一个 Fragment

**Storage、AI、Parser、Compiler、Editor 全部围绕同一粒度工作。** 这是整个架构的"公倍数"。

## 5.2 Fragment 的内容

一个 Fragment 是一段连续的叙事文本，通常对应一个"节拍"或一个小场景片段：

```markdown
<!-- @fragment f_0001 -->
<!-- @scene sc_01_02 -->

林风推开门，雨水顺着他的发梢滴落。手中的油纸伞已被风吹折，
他望向河对岸灯火阑珊的客栈，迟疑了片刻。

<!-- @entity hero: appears -->
<!-- @entity umbrella: mentioned -->
```

- Fragment 有自己的锚点（`@fragment f_0001`）
- 可属于某个 Scene（`@scene sc_01_02`）
- 可锚定 Semantic 实体出场（`@entity` 标注）
- 文本内容是 Markdown，但**渲染时无缝拼接**（Fragment 边界不产生视觉分隔）

## 5.3 Fragment 与 Scene / Chapter 的关系

| 概念 | 所属图 | 角色 | 粒度 |
|:--|:--|:--|:--|
| **Fragment** | Document（叶子）+ Semantic 锚点桥 | **最小编辑单元（atom）** | 最细 |
| **Scene** | **仅 Document** | 叙事单元（一个完整场景） | 中（含多个 Fragment） |
| **Chapter** | **仅 Document** | 结构单元（一章） | 粗（含多个 Scene） |

> **Scene / Chapter 的唯一归属：** 二者只属于 Document Graph，**不是 SemanticNode**。Semantic Graph 通过 `AppearsIn(Character → SceneId)` 边**引用** Document Graph 中的 Scene，而非将其纳入自身节点集。这避免"双重归属"——一个节点不能同时是 DocNode 和 SemanticNode。

```text
Chapter: ch_01
 ├─ Scene: sc_01_01
 │   ├─ Fragment: f_0001
 │   └─ Fragment: f_0002
 └─ Scene: sc_01_02
     ├─ Fragment: f_0003
     └─ Fragment: f_0004
```

- 一个 Scene 由 1–N 个 Fragment 组成
- 一个 Chapter 由 1–N 个 Scene 组成
- **Fragment 是唯一被 AI / Parser / Compiler / Git 直接操作的单元**；Scene 和 Chapter 是组织层，可重组（移动 Fragment 到另一个 Scene 是合法操作）

> **Fragment 的顺序采用链表式（prev / next），而非序号（order）。**
> 若用 `order: u32`，在中间插入一个 Fragment 会使后续所有 Fragment 的 order 递增，污染 Git Diff。改用 `prev: Option<StableId>` / `next: Option<StableId>` 的双向链表后，插入只需改相邻两个节点的指针，其余节点不动——Diff 聚焦且 Merge 友好。Chapter / Scene 同理。遍历顺序由链表决定，渲染时按链表序拼接。
>
> **持久化层不存链表指针。** prev/next 是 IR **内存层**的高效遍历表示；持久化层（RFC-0003 §5.2）用父节点的数组（`Scene.fragments`）表达顺序。加载时 Parser 从数组构建链表，保存时序列化回数组。这是同一信息的两种表示，不违反单一真相源——持久化数组的 SoT 在 `book.toml`，内存链表是其派生物。

## 5.4 为什么不用 Scene 作为最小单元

Scene 作为叙事单元，粒度可能过大（一个完整场景可能上千字）。AI 单次处理上千字 token 成本高且质量下降；Git Diff 聚焦度不足。Fragment 把粒度降到"一个节拍"，让每个子系统都能高效工作。

# 6. Node Types（节点类型）

## 6.1 Document Graph 节点

```rust
pub enum DocNode {
    Book(BookNode),
    Chapter(ChapterNode),
    Scene(SceneNode),
    Fragment(FragmentNode),
    // 段落级节点（可选，v0.2+）
    Paragraph(ParagraphNode),
    Dialogue(DialogueNode),
}

pub struct BookNode {
    id: StableId,
    title: String,
    metadata: BookMetadata,
}

pub struct ChapterNode {
    id: StableId,
    symbol: Option<Symbol>,      // 可选，如 ch_storm_night
    title: String,               // Display Name
    prev: Option<StableId>,      // 链表式排序（见 §5.3）
    next: Option<StableId>,
}

pub struct SceneNode {
    id: StableId,
    symbol: Option<Symbol>,
    title: Option<String>,
    pov: Option<StableId>,       // 视角角色的 StableId
    chapter: StableId,           // 所属 Chapter
    prev: Option<StableId>,      // 链表式排序
    next: Option<StableId>,
}

pub struct FragmentNode {
    id: StableId,                // f_0001
    scene: Option<StableId>,     // 所属 Scene
    prev: Option<StableId>,      // 链表式排序——中间插入只改相邻两节点
    next: Option<StableId>,
    text: String,                // Markdown 正文
    anchors: Vec<EntityAnchor>,  // 锚定的 Semantic 实体（Source of Truth，见 §7.2）
}

pub struct EntityAnchor {
    entity: StableId,            // 锚定的实体
    role: AnchorRole,            // appears / mentioned / referenced
}

pub enum AnchorRole {
    Appears,    // 实体在场
    Mentioned,  // 被提及但不在场
    Referenced, // 间接引用
}
```

## 6.2 Semantic Graph 节点

```rust
pub enum SemanticNode {
    Character(CharacterNode),
    Location(LocationNode),
    Item(ItemNode),
    Organization(OrganizationNode),
    Event(EventNode),
    Concept(ConceptNode),        // 抽象概念，如"魔法体系""王朝"
}

pub struct CharacterNode {
    id: StableId,
    symbol: Option<Symbol>,
    display_name: String,
    aliases: Vec<String>,        // 别名 / 称谓，用于 Parser 实体识别
    attributes: EntityAttributes, // 可扩展属性
}

pub struct LocationNode {
    id: StableId,
    symbol: Option<Symbol>,
    display_name: String,
    parent: Option<StableId>,    // 层级位置（客栈 → 城 → 国）
}

pub struct ItemNode {
    id: StableId,
    symbol: Option<Symbol>,
    display_name: String,
    item_type: ItemType,         // weapon / artifact / consumable / ...
}

// 各 Entity 共享的扩展属性容器
pub struct EntityAttributes {
    // 核心属性用强类型字段
    custom: BTreeMap<String, AttributeValue>, // 插件可扩展；BTreeMap 保证确定序列化
}
```

> **Entity 的详细字段定义**（如 Character 的年龄、种族、状态机）由各自 RFC 细化：RFC-0008（Character）, RFC-0014（World: Location / Item）等。本 RFC 只定义**所有实体共享的骨架**（三重 ID + display name + aliases + attributes 容器）。

# 7. Edge Types（边类型）

## 7.1 Document Graph 边

```rust
pub enum DocEdge {
    Contains { parent: StableId, child: StableId },
}
// Document Graph 几乎只有 contains 边
// 兄弟顺序由节点的 prev/next 链表表达（见 §5.3），不在边上存 order
```

## 7.2 Semantic Graph 边

**边是一级公民**——拥有自己的 StableId，可被独立删除、修改、diff、引用。

```rust
pub struct SemanticEdge {
    id: EdgeId,                     // 边的唯一标识（一级公民）
    from: StableId,
    to: StableId,
    relation: RelationKind,
    valid: Option<ValidityWindow>,  // 时序区间，None 表示全时段
    evidence: Vec<StableId>,        // 支撑该边的 Fragment 锚点
}

/// 边的 StableId：独立前缀 se_，保证不与节点 ID 冲突
pub struct EdgeId(StableId);        // prefix = se_

pub enum RelationKind {
    // 角色关系
    AppearsIn,      // Character → Scene (引用 Document Graph 节点)
    Knows,          // Character → Character
    RelatedTo,      // Character → Character (泛化亲属/血缘)
    // 物品关系
    Holds,          // Character → Item
    LocatedAt,      // Character/Item → Location
    // 组织关系
    MemberOf,       // Character → Organization
    // 扩展
    Custom(String), // 插件自定义关系类型
}

pub struct ValidityWindow {
    from: Option<StoryTime>,
    until: Option<StoryTime>,
}
```

> **边为何需要 StableId：** 没有身份的边无法被独立删除、无法修改 `valid` 区间、无法被 Knowledge Layer 的 evidence 引用、无法在 Git Diff 中被追踪。边作为一级公民后，这些操作都有明确的操作对象。
>
> **注意：`References`（Fragment → Entity）边已移除**——该语义由 `Fragment.anchors`（Source of Truth）表达，不再用边重复表示，避免双写不一致（见 §7.3）。
>
> **Relation 的 `valid` 区间** 与 Knowledge Layer 的 Assertion `valid` 对应——但二者不同：Relation 是 IR 级的结构性关系（"林夏出现在场景 X"），Assertion 是 KB 级的可验证命题（"林夏在 1086 年年龄为 17"）。详见 RFC-0015 §3。

## 7.3 Anchors vs Edges（单一真相源）

`Fragment.anchors` 与（已移除的）`References` 边曾同时表达"这段文本提到了某实体"。为避免双写不一致，明确职责：

| 表达 | 角色 | 存储位置 | 序列化 |
|:--|:--|:--|:--|
| `Fragment.anchors` | **Source of Truth** | Fragment 节点内 | ✓（随 Fragment 落盘） |
| `(Fragment → Entity)` 派生索引 | **派生缓存** | SemanticGraph 内部索引 | ✗（不序列化，可重建） |

- 锚点天然嵌在文本所属的 Fragment 里，是原始事实。
- 若需"某实体被哪些 Fragment 提及"的反向查询，由 Compiler 构建**派生反向索引**（`Entity → Vec<Fragment>`），存于缓存，不进 Git。
- 这与 RFC-0001 §9.4 的缓存哲学一致：原始数据进 Git，派生索引不进。

# 8. IR Root Structure（IR 根结构）

```rust
/// Story IR 的根——一个 Project 内完整的图表示
pub struct StoryIR {
    // 元信息
    pub version: IRVersion,         // Schema 版本，用于迁移
    pub revision: Revision,         // 修订号，用于增量编译（RFC-0001 §10）

    // 双图
    pub document: DocumentGraph,
    pub semantic: SemanticGraph,

    // 索引
    pub symbol_table: SymbolTable,  // Symbol → StableId
    pub location_index: LocationIndex, // 实体 → 文本块（派生缓存）
}

pub struct DocumentGraph {
    nodes: NodeStore<DocNode>,
    edges: EdgeStore,           // 按 EdgeId 有序
}

pub struct SemanticGraph {
    nodes: NodeStore<SemanticNode>,
    edges: EdgeStore,           // 按 EdgeId 有序
}

/// StableId → Node 的存储。
/// 用 BTreeMap 而非 HashMap：键天然有序，序列化时直接输出确定序，
/// 无需额外排序步骤（符合 §9 确定性约束）。
pub struct NodeStore<N> {
    by_id: BTreeMap<StableId, N>,
}

/// EdgeId → SemanticEdge / DocEdge
pub struct EdgeStore {
    by_id: BTreeMap<EdgeId, SemanticEdge>, // DocGraph 的边较简单，也可并存储
}

pub struct IRVersion(u32);   // Schema 迁移用
pub struct Revision(u64);    // 每次提交自增，增量编译的版本依据
```

## 8.1 NodeStore / EdgeStore 的设计约束

- **StableId / EdgeId 是主键**，所有查找优先走 `by_id`。
- 用 `BTreeMap` 而非 `HashMap`：键按字典序天然有序，**序列化时直接得到确定序**，无需每次序列化额外排序（符合 §9）。
- Symbol 查找通过 `SymbolTable` 间接：Symbol → StableId → Node。
- 增删改查为 O(log n)。Compiler 增量检查场景下访问模式以"按 ID 随机查"为主，BTreeMap 的缓存局部性可接受；若后续性能验证发现瓶颈，可改为 arena + 旁挂有序索引，但外部 API 不变。

# 9. Serialization & Determinism（序列化与确定性）

遵循 RFC-0001 §3.8 Deterministic，IR 的序列化必须稳定：

- **字段顺序固定**：序列化时按声明顺序输出。
- **集合有序**：所有持久化集合使用 `BTreeMap` / `BTreeSet`（见 §8），键天然有序，不依赖哈希迭代序。
- **ID 排序**：节点集合按 StableId 字典序，边集合按 EdgeId 字典序。
- **无随机性**：任何派生字段（如 hash）基于确定输入计算。

> 这一约束确保 Git Diff 只反映语义变更，不产生"重新序列化导致的全量噪声 Diff"。

# 10. Versioning & Migration（版本与迁移）

```rust
pub struct IRVersion(u32);
```

- 每个 Schema 变更（新增字段、修改类型）递增 `IRVersion`。
- Parser 在加载旧版本 IR 时，走 Migration 管线升级到当前版本。
- Migration 是确定性函数：`fn migrate(v1: IRv1) -> IRv2`。
- v0.1 的 IRVersion = 1。

> IR 的演进策略与 Story 本身的版本控制（Git 层）正交：Git 管文本，IRVersion 管 Schema。

# 12. Open Questions

1. **Fragment 的切分标准**：多长算一个 Fragment？是按字数、按叙事节拍、还是按作者手动划分？（倾向：作者手动，Parser 不自动切分。）
2. **Scope 规则**：Symbol 是否支持 namespace / scope（如 `chapter1.hero` vs `chapter2.hero`）？（v0.1 全局唯一，scope 留待后续。）
3. **图的内存表示**：当前用 `BTreeMap` 保证确定序列化。是否在内存层叠加 arena（如 `slotmap`）提升性能与缓存局部性，序列化时仍走 BTreeMap 排序？（待性能验证后决定；外部 API 不变。）
4. **IR 是否支持多 Book**：一个 Project 是否能含多本书（系列小说）？（v0.1 单 Book，留扩展。）
