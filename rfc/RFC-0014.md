# 1. Abstract（摘要）

World Model 定义故事世界中**非角色实体**的结构：Location（地点）与 Item（道具）。这两个实体直接支撑 RFC-0001 §2 列出的痛点——"道具消失"与"地理位置冲突"。

```text
   Location（地点）     Item（道具）
      │                    │
      ├─ 地理层级          ├─ 持有者流转
      ├─ 包含关系          ├─ 状态变化
      └─ 移动检查          └─ 消失检查
```

本 RFC 遵循 RFC-0008 Character Model 确立的原则：**静态属性存 Entity 文件，动态状态存 Knowledge Base。**

------

# 2. Design Principle（设计原则）

## 2.1 与 Character Model 的对称

World Model 与 Character Model（RFC-0008）共享相同的设计模式：

| | 静态属性 | 动态状态 |
|:--|:--|:--|
| **Location** | 地理层级、描述、别名 | 被摧毁 / 季节变化 |
| **Item** | 类型、描述、别名 | 持有者、位置、损坏 / 丢失 |

静态属性 → Entity 文件；动态状态 → KB Assertion（带时序）。

## 2.2 为什么 Location 和 Item 合在一份 RFC

二者解决对称的问题，且共享相同的数据模式（层级 + 时序流转）。分开写会重复大量结构。若未来 Item 变得极复杂，可拆分为独立 RFC。

# 3. Location Model（地点模型）

## 3.1 文件格式

```toml
# entities/locations/l_3F2B1C.toml

id = "l_3F2B1C"
symbol = "riverside"
display_name = "青江渡口"

aliases = ["渡口", "江边"]

[geography]
# 地理层级：父地点（青江渡口 → 青江镇 → 江南道）
parent = "l_1A2B3C"           # 青江镇的 StableId
# 子地点（可派生，不需显式声明——Parser 从 parent 反向构建）
# children: [l_4D5E6F, l_7G8H9I]

# 地理类型
kind = "settlement"           # region | city | settlement | building | landmark | natural

# 坐标描述（自由文本，不强制结构化）
position = "青江下游，江南道东部"

[description]
text = "青江与官道交汇处的小渡口，因常有江湖人士出入而闻名。"
```

## 3.2 Rust 类型

```rust
pub struct LocationNode {
    // 骨架字段
    pub id: StableId,
    pub symbol: Option<Symbol>,
    pub display_name: String,
    pub aliases: Vec<String>,

    // Location 专属
    pub geography: Geography,
    pub description: Option<String>,
}

pub struct Geography {
    /// 父地点（构成地理层级树）
    pub parent: Option<StableId>,
    /// 地理类型
    pub kind: LocationKind,
    /// 位置描述（自由文本）
    pub position: Option<String>,
}

pub enum LocationKind {
    Region,      // 大区域（道、省、国）
    City,        // 城市
    Settlement,  // 聚落（村镇）
    Building,    // 建筑（客栈、府邸）
    Landmark,    // 地标（桥、山、河）
    Natural,     // 自然地貌
}
```

## 3.3 地理层级树

Location 通过 `parent` 字段构成层级树：

```text
  l_eastern_realm（东境）
   ├─ l_jiangnan（江南道）
   │   ├─ l_qingjiang_town（青江镇）
   │   │   ├─ l_3F2B1C（青江渡口）
   │   │   └─ l_9Z0Y1X（镇北客栈）
   │   └─ l_capital（京都）
   └─ l_northern_realm（北境）
```

- 子地点关系**由 parent 反向派生**，不在文件中显式声明 children（避免双写）。
- Parser 加载时构建 `parent → children` 的反向索引。

## 3.4 地理一致性检查

| 规则 ID | Phase | 检查内容 |
|:--|:--|:--|
| `location_parent_exists` | Structure | parent 引用的 Location 存在 |
| `location_cycle` | Structure | 地理层级树无环（A 的 parent 不能是 A 的后代） |
| `location_conflict` | Semantic | 角色的 located_at 断言与场景的地理标注矛盾（角色在 A 地，但场景发生在不包含 A 的 B 地） |
| `location_orphan` | Style | Location 从未被任何 Fragment 提及 |

# 4. Item Model（道具模型）

## 4.1 文件格式

```toml
# entities/items/i_A7E902.toml

id = "i_A7E902"
symbol = "frost_blade"
display_name = "寒霜剑"

aliases = ["霜剑", "那把剑"]

[item]
# 道具类型
kind = "weapon"              # weapon | artifact | consumable | clothing | document | misc

# 品质 / 等级（可选）
grade = "legendary"          # common | uncommon | rare | legendary

# 描述
description = "通体泛着淡蓝光芒的长剑，据说是上古铸剑师遗作。"

# 特殊能力（自由文本，不结构化）
abilities = "挥动时寒气逼人，可冻结近身之敌。"
```

## 4.2 Rust 类型

```rust
pub struct ItemNode {
    // 骨架字段
    pub id: StableId,
    pub symbol: Option<Symbol>,
    pub display_name: String,
    pub aliases: Vec<String>,

    // Item 专属
    pub item: ItemSpec,
}

pub struct ItemSpec {
    pub kind: ItemKind,
    pub grade: Option<ItemGrade>,
    pub description: Option<String>,
    pub abilities: Option<String>,
}

pub enum ItemKind {
    Weapon,       // 武器
    Artifact,     // 法器 / 神器
    Consumable,   // 消耗品（丹药、卷轴）
    Clothing,     // 衣物 / 防具
    Document,     // 文书 / 信件 / 秘籍
    Misc,         // 杂项
}

pub enum ItemGrade {
    Common,
    Uncommon,
    Rare,
    Legendary,
}
```

## 4.3 道具流转（动态状态）

道具的"持有者""位置""损坏状态"是动态的，存为 KB Assertion：

| 状态 | Predicate | 示例 |
|:--|:--|:--|
| 持有者 | `held_by` | `subject=i_A7E902, object=c_8A91D4, valid=[sc_01, sc_07]`（林风持有，第 1-7 场景） |
| 位置（无人持有时） | `located_at` | `subject=i_A7E902, object=l_3F2B1C, valid=[sc_08]`（丢在渡口） |
| 完整性 | `condition` | `subject=i_A7E902, object=damaged, valid=[sc_10]`（第 10 场景损坏） |

## 4.4 道具一致性检查

| 规则 ID | Phase | 检查内容 |
|:--|:--|:--|
| `item_disappeared` | Semantic | 道具在获得后，既无 held_by 也无 located_at（"凭空消失"） |
| `item_double_held` | Semantic | 同一道具同时被两个角色持有（held_by 断言重叠） |
| `item_owner_dead` | Semantic | 持有者已死亡，但道具未流转（无人持有的道具应标 located_at） |
| `item_orphan` | Style | Item 从未被任何 Fragment 提及 |

### 道具消失检查示例

```rust
pub struct ItemDisappeared;

impl Rule for ItemDisappeared {
    fn id(&self) -> &str { "item_disappeared" }
    fn phase(&self) -> RulePhase { RulePhase::Semantic }
    fn depends_on(&self) -> &[Dependency] {
        &[Dependency::Assertion, Dependency::Entity]
    }
    fn run(&self, ctx: &mut RuleContext) {
        let kb = match ctx.kb { Some(kb) => kb, None => return };

        for item in ctx.ir.semantic.all_items() {
            // 获取该道具的所有持有 / 位置断言，按时间排序
            let states = kb.item_timeline(item.id);

            // 检查：从首次获得到故事结束，是否存在"无主"的时间缺口
            if let Some(gap) = find_ownership_gap(&states) {
                ctx.warning(
                    "item_disappeared",
                    format!("道具 {:?} 在 {} 到 {} 之间下落不明",
                        item.display_name, gap.start, gap.end),
                    SourceLocation::entity(item.id),
                );
            }
        }
    }
}
```

# 5. World Integrity（世界一致性）

跨实体的检查规则，确保 Location / Item / Character 之间的地理与持有关系一致：

| 规则 ID | Phase | 检查内容 |
|:--|:--|:--|
| `geo_character_mismatch` | Semantic | 角色的 located_at 不在场景的地理范围内（角色声称在 A 镇，但场景发生在 B 城，且 A 不是 B 的子地点） |
| `item_location_mismatch` | Semantic | 道具的 located_at 与持有者的 located_at 矛盾（角色在 A 地持有道具，但道具断言 located_at 在 B 地） |
| `unreachable_location` | Semantic | 角色连续出现在地理上不相邻的两个地点，无移动描述（"瞬间移动"） |

> 这些规则依赖 Location 的地理层级树（§3.3）做"包含关系"判断：角色在 A 地，场景在 B 地，若 A 是 B 的后代（或反过来），则不视为矛盾。

# 6. Serialization（序列化）

遵循 RFC-0002 §9 + RFC-0003 §5.4。

```toml
# entities/locations/l_3F2B1C.toml — 完整示例
id = "l_3F2B1C"
symbol = "riverside"
display_name = "青江渡口"
aliases = ["渡口", "江边"]

[geography]
parent = "l_1A2B3C"
kind = "settlement"
position = "青江下游，江南道东部"

[description]
text = "青江与官道交汇处的小渡口。"
```

```toml
# entities/items/i_A7E902.toml — 完整示例
id = "i_A7E902"
symbol = "frost_blade"
display_name = "寒霜剑"
aliases = ["霜剑"]

[item]
kind = "weapon"
grade = "legendary"
description = "通体泛着淡蓝光芒的长剑。"
abilities = "挥动时寒气逼人，可冻结近身之敌。"
```

- `id` 必须等于文件名。
- `aliases` 按输入顺序输出。
- Location 的 children 不写入文件（由 parent 派生）。

# 8. Open Questions

1. **Organization 是否纳入 World Model**：组织（门派、势力）是独立的 RFC 还是合并进来？（倾向：独立，组织有自己的成员关系网，复杂度与 Location/Item 不同。）
2. **地理距离**：是否需要结构化表达地点间的距离 / 旅行时间？（倾向：v0.1 用自由文本描述，不结构化。unreachable_location 规则用"无移动描述"而非"距离不可能"。）
3. **道具的唯一性**：同名道具（10 把"长剑"）如何处理？是否需要 unique 标记区分"唯一神器"与"普通物品"？（倾向：是，Item 加 `unique: bool` 字段。）
4. **地点的季节 / 时间变化**：地点的状态随季节变化（"冬天河面结冰"），是否需要结构化？（倾向：v0.1 用 Assertion 表达 condition。）。

# Appendix

> **Location 是地理层级树，Item 是时序流转链。道具不会凭空消失——只要每一段持有 / 位置都有断言记录，Compiler 就能找出缺口。世界的一致性，就是每件东西都在它该在的地方。**
