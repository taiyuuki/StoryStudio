# 1. Abstract（摘要）

Parser 是 Story Studio 数据流的第二层：将 RFC-0003 定义的**文件格式**解析为 RFC-0002 定义的 **Story IR**。

```text
   文件 (TOML + Markdown)  ──Parser──►  Story IR (Typed Graph Model)
```

Parser 是**纯确定性的**。它读取文件、构建图结构、执行基于词典的精确匹配，但**不做任何需要语义推理或 AI 才能完成的识别**。

------

# 2. Responsibilities（职责边界）

## 2.1 Parser 做什么

- 读取 `structure.toml`，构建 Document Graph（Chapter / Scene / Fragment 层级与链表顺序）
- 读取 Fragment 文件，提取正文与显式 anchors
- 校验文件格式合法性（id 匹配、引用完整性、无重复 id）
- 执行**确定性实体链接**：基于 Entity 的 `display_name` + `aliases` 在正文中匹配，产出派生的 mentions
- 构建 Location Index（实体 → 文本块，派生缓存）

## 2.2 Parser 不做什么

| 不做的事 | 归属 | 理由 |
|:--|:--|:--|
| 语义推理（"这段话暗示角色 A 已死亡"） | Knowledge Layer（Extraction） | 需要 AI，违反确定性 |
| 一致性校验（"角色 A 死后仍在场"） | Compiler | Parser 只负责"能否解析"，不负责"是否合理" |
| AI 抽取事实 | Extraction（RFC-0015） | 非确定性 |
| 文本生成 / 改写 | Agent Runtime | Parser 是只读转换器 |

## 2.3 四层可信度模型

Parser 产出的实体关联信息分属不同的可信度层。这是整个系统的核心职责划分：

| 层 | 来源 | 持久化 | 可信度 | 负责模块 |
|:--|:--|:--|:--|:--|
| **anchors** | 作者（Fragment frontmatter） | ✅ 进 Git | **最高** | 作者 + Parser（读取） |
| **mentions** | Parser（别名词典匹配） | ❌ 派生缓存 | 高（确定匹配） | Parser |
| **assertions** | AI / 人工抽取 | ✅ 进 Git（Knowledge Base） | 中 | Extraction（RFC-0015） |
| **inference** | Knowledge Layer 推理 | ❌ 派生 | 最低 | Knowledge Layer |

**Parser 的职责边界：只做确定性词典匹配（mentions 层），不触碰 assertions 与 inference。**

- `anchors` 是作者显式标注的事实，Parser 只读取，不修改。
- `mentions` 是 Parser 通过精确字符串匹配发现的实体提及，作为**派生数据**存于 Location Index（Parser Cache），**既不进 StoryIR，也不回写 Fragment 文件**。
- `assertions` 与 `inference` 完全不属于 Parser 的职责。

> **为什么 mentions 不进 StoryIR？** StoryIR 是原始数据的表示（RFC-0002 定义的双图），只含 Source of Truth。mentions 是可从（正文 + Entity 词典）完全重建的派生数据，放进 IR 会模糊"IR = 原始数据"的边界，也违反单一真相源（RFC-0003 §3）。mentions 与 Location Index 一样属于 Parser 的派生产物。
>
> **为什么不把 mentions 也持久化？** 持久化它会导致双写——作者改了 Entity 的 alias 后，所有 Fragment 的 mentions 都需同步更新。它是派生缓存，可随时重建。

# 3. Parse Determinism（解析确定性）

这是 Parser 最核心的性质，增量编译、Compiler、AI Runtime 都依赖它。

> **同一 Project、同一文件内容、同一 Parser 版本 → 永远生成完全一致的输出。**

"输出"包括：

| 产物 | 确定性要求 |
|:--|:--|
| **StoryIR** | 节点顺序、字段值完全一致 |
| **LocationIndex** | 索引条目、顺序完全一致 |
| **EntityDictionary** | 词条、映射完全一致 |
| **Diagnostics** | 错误列表、顺序、定位完全一致 |

### 保证确定性的设计约束

1. **集合用 BTreeMap / BTreeSet**（RFC-0002 §8），不用 HashMap——避免迭代序不确定。
2. **Aho-Corasick 自动机的构建是确定的**——同一组词条（按字典序排序后输入）构建出的自动机结构唯一。
3. **mentions 按出现位置排序**——同一正文扫描多次，匹配结果的位置序列一致。
4. **不依赖环境**——不读取系统时间、随机数、文件系统遍历顺序。Parser 遍历文件时按 StableId 排序，而非依赖 `readdir` 的返回顺序。
5. **Parser 版本显式化**——IR Schema 版本（RFC-0002 §10）绑定 Parser 行为。升级 Parser 即升 IRVersion。

### 被依赖的场景

- **增量编译（Compiler）**：增量编译假设"未变化的 Fragment 解析结果不变"，因此可以只重算 dirty 部分。若 Parser 不确定，增量结果可能出错。
- **AI Runtime**：AI 构建 Prompt 时引用 IR 内容，若同一输入产生不同 IR，AI 的行为不可复现。
- **Dry-Run**：Assertion 层在 draft IR 上跑诊断，假设"重新解析得到相同 IR"，否则 Dry-Run 结果不可信。

# 4. Parse Pipeline（解析管线）

Parser 分四个阶段执行，每个阶段有明确的输入与输出：

```text
Phase 1:   Load            读文件 → 原始文本/原始 TOML
    │
Phase 1.5: Entity Scan     entities/*.toml → SemanticGraph 节点 + SymbolTable
    │
Phase 2:   Structure       structure.toml → Document Graph（节点 + 链表）
    │
Phase 3:   Fragment        fragments/*.md → 填充正文与 anchors（Symbol→StableId）
    │
Phase 4:   Entity Linking  正文 + Entity 词典 → mentions
    │
    ▼
  Story IR（原始数据：Document Graph + Semantic Graph）
    +
  Location Index（派生缓存：含 mentions，不进 IR）
```

> **Phase 1.5 在 Structure 之前**：Fragment 的 anchors 引用 Symbol（如 `hero`），必须先构建 SymbolTable 才能在 Phase 3 解析 anchors。若先解析 Fragment 再建 SymbolTable，会遇到"引用了尚未加载的 Symbol"的问题。

```rust
/// Parser 的入口：将 Project 目录解析为 Story IR + Location Index
pub fn parse_project(project_dir: &Path) -> Result<ParseOutput, ParseError> {
    let raw = load_files(project_dir)?;           // Phase 1
    let mut ir = build_symbol_table(&raw)?;        // Phase 1.5
    build_document_graph(&mut ir, raw)?;           // Phase 2
    fill_fragments(&mut ir, raw)?;                 // Phase 3
    let location_index = link_and_index(&ir)?;     // Phase 4 → Location Index
    Ok(ParseOutput { ir, location_index })
}

/// Parser 的输出：IR（原始）+ Location Index（派生，含 mentions）
pub struct ParseOutput {
    pub ir: StoryIR,                    // 不含 mentions
    pub location_index: LocationIndex,  // 含 mentions，派生缓存
}
```

### Plugin Extension Point（未来）

管线设计预留插件钩子（RFC-0012 Plugin）。v0.1 不实现，但架构不阻碍未来引入：

```text
Raw Text → Core Parser → [Plugin Hooks] → StoryIR
                         ↑
                    Markdown Extension / Shortcode / Custom Syntax
```

- Core Parser 完成标准解析后，插件可在 IR 落定前介入（如解析自定义 shortcode、注入派生节点）。
- 插件不得绕过 Core Parser 直接改文件——必须通过钩子，保证确定性不被破坏。

# 5. Entity Scan & Symbol Table（Phase 1.5）

## 5.0 为什么在 Structure 之前

Fragment 的 anchors 引用 Entity 的 Symbol（如 `hero`）。Parser 必须在解析 Fragment（Phase 3）**之前**构建完整的 SymbolTable，否则无法将 anchors 中的 Symbol 解析为 StableId。

```rust
/// Phase 1.5：扫描 entities/ 目录，构建 Semantic Graph 节点 + SymbolTable
fn build_symbol_table(raw: &RawFiles) -> Result<StoryIR, ParseError> {
    let mut ir = StoryIR::new();
    let mut sym_table = SymbolTable::new();

    for entity_file in &raw.entities {
        let node = parse_entity_toml(entity_file)?;

        // 校验：id 无重复
        if ir.semantic.contains(node.id) {
            return Err(ParseError::DuplicateId { id: node.id });
        }

        // 校验：Symbol 无冲突
        if let Some(ref sym) = node.symbol {
            if sym_table.contains(sym) {
                return Err(ParseError::DuplicateSymbol {
                    symbol: sym.clone(),
                });
            }
            sym_table.insert(sym.clone(), node.id);
        }

        ir.semantic.insert(node.id, node);
    }

    ir.symbol_table = sym_table;
    Ok(ir)
}
```

## 5.1 SymbolTable 的用途

SymbolTable 在后续阶段被频繁使用：

| 阶段 | 用途 |
|:--|:--|
| Phase 3（Fragment） | 解析 anchors 中的 `entity: hero` → `c_8A91D4` |
| Phase 4（Entity Linking） | 词典构建时，从 Entity 节点取 display_name + aliases |
| Compiler | Diagnostics 展示时用 Symbol 而非 StableId |

# 6. Document Graph 构建（Phase 2）

## 6.1 从数组到链表

RFC-0003 §5.2 规定：顺序由 `structure.toml` 中的数组表达。Parser 的任务是将数组转换为 RFC-0002 §5.3 的双向链表。

```rust
/// 将 structure.toml 的数组结构转换为 Document Graph
fn build_document_graph(raw: RawFiles) -> Result<StoryIR, ParseError> {
    let mut ir = StoryIR::new();

    // 1. Book 节点
    let book = raw.structure.book;
    ir.document.insert_book(book.id, book.metadata);

    // 2. Chapter 列表 → Chapter 节点 + 链表
    let chapters = &book.chapters; // ["ch_01", "ch_02", "ch_03"]
    link_sequence(&mut ir, chapters, |id, prev, next| {
        ir.document.set_chapter_links(id, prev, next);
    });

    // 3. 每个 Chapter 的 scenes → Scene 节点 + 链表
    for ch_id in chapters {
        let scenes = &raw.structure.chapter[*ch_id].scenes;
        link_sequence(&mut ir, scenes, |id, prev, next| {
            ir.document.set_scene_links(id, prev, next);
        });
    }

    // 4. 每个 Scene 的 fragments → Fragment 节点 + 链表 + 反向索引
    for sc_id in all_scenes(&ir) {
        let frags = &raw.structure.scene[*sc_id].fragments;
        link_sequence(&mut ir, frags, |id, prev, next| {
            ir.document.set_fragment_links(id, prev, next);
            ir.document.set_fragment_scene(id, sc_id); // 反向建立 Fragment→Scene
        });
    }

    Ok(ir)
}

/// 通用链表构建：将有序 ID 列表转为 prev/next 双向链表
fn link_sequence<T: Linkable>(
    ir: &mut StoryIR,
    ids: &[StableId],
    setter: T,
) {
    for (i, id) in ids.iter().enumerate() {
        let prev = if i > 0 { Some(ids[i - 1]) } else { None };
        let next = if i < ids.len() - 1 { Some(ids[i + 1]) } else { None };
        setter(*id, prev, next);
    }
}
```

## 6.2 反向索引

Parser 构建 Document Graph 时同时建立反向映射：

| 正向（structure.toml 直接表达） | 反向（Parser 派生） |
|:--|:--|
| `Chapter.scenes = [...]` | `Scene → Chapter` |
| `Scene.fragments = [...]` | `Fragment → Scene` |

反向索引存在 IR 内存层（BTreeMap），不持久化——它可从 structure.toml 完全重建。

## 6.3 完整性校验

Phase 2 执行以下确定性校验，失败则产出 Diagnostics：

| 校验 | 失败级别 | 说明 |
|:--|:--|:--|
| 数组中的 ID 都有对应定义 | Error | `chapters = ["ch_01"]` 但无 `[chapter.ch_01]` |
| ID 无重复 | Error | 同一 ID 出现在两个数组中 |
| 链表无环 | Error | RFC-0002 §3.3 Invariant #6 |
| Scene 的 fragments 非空（Warning） | Warning | 空 Scene 通常是疏漏 |

> Parser 的校验是"结构能否解析"级别的，不涉及语义合理性（如"Chapter 顺序是否符合时间线"是 Compiler 的事）。

# 7. Fragment 解析（Phase 3）

## 7.1 文件格式

每个 Fragment 文件 = YAML frontmatter + Markdown 正文（RFC-0003 §5.3）：

```rust
/// 解析单个 Fragment 文件
fn parse_fragment_file(path: &Path) -> Result<FragmentContent, ParseError> {
    let content = fs::read_to_string(path)?;

    // 分离 frontmatter 与正文
    let (frontmatter, body) = split_frontmatter(&content)?;

    // 解析 frontmatter
    let fm: FragmentFrontmatter = serde_yaml::from_str(&frontmatter)?;

    // id 校验：文件名 == frontmatter.id
    let filename = path.file_stem().unwrap().to_str().unwrap();
    if fm.id != filename {
        return Err(ParseError::IdMismatch {
            file: path.into(),
            expected: filename.into(),
            actual: fm.id.clone(),
        });
    }

    Ok(FragmentContent {
        id: fm.id,
        anchors: fm.anchors,
        text: body,
    })
}
```

## 7.2 id 校验

遵循 RFC-0003 §5.3：

- `fragments/f_0001.md` 的 frontmatter `id` 必须为 `f_0001`。
- 不匹配 → Error（不是 Warning，因为 id 是所有引用的根）。

## 7.3 anchors 提取

Fragment 的 frontmatter anchors 是 **Source of Truth**（§2.3 最高可信度层）：

```yaml
anchors:
  - entity: c_8A91D4        # StableId 或 Symbol
    role: appears
  - entity: hero            # Symbol，Parser 解析为 StableId
    role: mentioned
```

Parser 的处理：

- `entity` 字段若是 Symbol（如 `hero`），通过 Symbol Table 解析为 StableId。
- Symbol 无法解析 → Error（引用断裂）。
- `role` 必须是 `appears` / `mentioned` / `referenced` 之一，否则 Error。

## 7.4 正文处理

- 正文是原始 Markdown 文本，Parser **不做语法解析**（不构建 Markdown AST）。
- 正文按原样存入 `FragmentNode.text`。
- Markdown 渲染是 Editor / Export 的职责，不是 Parser 的。
- Parser 只关心正文中可用于 Entity Linking 的文本。

> **为什么不构建 Markdown AST？** 因为 Story IR 的 Document Graph 只到 Fragment 粒度（RFC-0002 §5）。Paragraph / Dialogue 节点是 v0.2+ 的可选扩展（RFC-0002 §6.1）。v0.1 的 Parser 不解析段落级结构。

# 8. Entity Linking（Phase 4，确定性匹配）

## 8.1 定位

Entity Linking 是 Parser 的最后阶段，**纯确定性**：基于 Entity 词典在 Fragment 正文中做精确字符串匹配。

## 8.2 词典构建

从所有 Entity 节点构建匹配词典：

```rust
struct EntityDictionary {
    /// 词条 → StableId 的映射
    /// 一个词条可能映射到多个 Entity（歧义情况）
    entries: BTreeMap<String, Vec<StableId>>,
}

fn build_dictionary(ir: &StoryIR) -> EntityDictionary {
    let mut dict = EntityDictionary::new();

    for node in ir.semantic.all_entities() {
        // display_name 入典
        dict.add(&node.display_name, node.id);

        // aliases 入典
        for alias in &node.aliases {
            dict.add(alias, node.id);
        }
    }

    dict
}
```

**入典词条：**
- 每个 Entity 的 `display_name`（必填）
- 每个 Entity 的 `aliases`（别名 / 称谓）

**不入典：**
- StableId / Symbol（它们是程序标识，不是正文中出现的名字）
- attributes（属性值不作为匹配词条）

## 8.3 匹配算法

匹配采用 **Aho-Corasick 多模式匹配算法**。这是确定性算法，完全符合 Parser 的确定性约束。

> **为什么确定用 Aho-Corasick：** 百万字 × ~900 个词条（300 Entity × 平均 3 aliases），朴素算法 O(n×m) 在 Editor 实时场景下迟早卡顿。Aho-Corasick 构建自动机后单次扫描 O(n + 匹配数)，且匹配过程完全确定——同一输入永远得到相同结果。这不再是一个"待定"的选择，而是设计约束。

```rust
/// 在 Fragment 正文中执行确定性实体链接
fn link_in_fragment(
    text: &str,
    automaton: &AhoCorasick,     // 预构建的自动机
    dict: &EntityDictionary,
) -> Vec<Mention> {
    let mut mentions = Vec::new();

    // 1. Aho-Corasick 单次扫描，收集所有候选匹配
    let candidates: Vec<_> = automaton
        .find_iter(text)
        .map(|m| Candidate {
            entity_id: dict.lookup(m.pattern()),
            start: m.start(),
            end: m.end(),
        })
        .collect();

    // 2. 解决重叠：最长匹配优先（§7.4）
    let resolved = resolve_overlaps(candidates);

    // 3. 转换为 Mention
    for m in resolved {
        mentions.push(Mention {
            entity: m.entity_id,
            start: m.start,
            end: m.end,
        });
    }

    mentions
}
```

**自动机构建**：Parser 启动时（或 Entity 词典变更时）一次性构建，后续所有 Fragment 共享同一个自动机。
## 8.4 歧义处理

### 重叠与包含（最长匹配优先）

当两个词条在正文中重叠时，取更长的匹配：

```text
正文："林少侠推开门"
词典：{"林" → c_001, "林少侠" → c_001}
匹配：选 "林少侠"（3 字），不选 "林"（1 字）
```

### 多 Entity 共享同名（歧义 Warning）

当同一个词条映射到多个 Entity 时：

```text
词典：{"林风" → [c_001, c_002]}  # 两个角色都叫"林风"
正文："林风走了"
```

- **v0.1 策略**：无法确定指向哪个，产出 **Warning**（"文本中的'林风'匹配到多个实体"），不生成 mention。
- 作者需通过显式 anchor 消歧（在 frontmatter 标注 `entity: c_001`）。

### 区分大小写

- 中文场景：无大小写问题。
- 英文 / 拼音场景：v0.1 大小写敏感匹配（"Hero" ≠ "hero"）。若需不敏感，留待配置项（Open Question）。

## 8.5 mentions 的产物

Entity Linking 产出的 mentions 是**派生数据**：

- 存入 Location Index（`.novelstudio/cache/`），**不进 StoryIR，不回写 Fragment 文件**。
- 可通过"重新解析"完全重建。

```rust
struct Mention {
    entity: StableId,      // 匹配到的实体
    start: usize,          // 正文中的字符偏移
    end: usize,
}
```

> **不设 MentionRole 枚举。** 隐式匹配的 role 固定为 `mentioned`，没有其他可能值——`appears` / `referenced` 只存在于显式 anchor。Location Index 中隐式 mention 统一记为 `AnchorRole::Mentioned`，无需独立的枚举类型。

# 9. Location Index 构建

Location Index 是 Parser 的**派生产物**（不进 StoryIR，不进 Git），合并显式 anchors 与隐式 mentions 两个来源。

## 9.1 数据来源

| 来源 | 来自 | 可信度 | 含义 |
|:--|:--|:--|:--|
| Fragment.anchors（显式） | StoryIR（作者标注） | 最高 | 实体出场 |
| mentions（隐式匹配） | Phase 4 Entity Linking | 高 | Parser 发现的文本提及 |

```rust
/// Phase 4 的实际实现：Entity Linking 的同时构建 Location Index
fn link_and_index(ir: &StoryIR) -> Result<LocationIndex, ParseError> {
    let dict = build_dictionary(ir);                 // §7.2
    let automaton = build_aho_corasick(&dict);       // §7.3
    let mut index = LocationIndex::new();

    for frag in ir.document.all_fragments() {
        // 1. 显式 anchors（从 IR 读取，直接入索引）
        for anchor in &frag.anchors {
            index.add(anchor.entity, frag.id, anchor.role);
        }

        // 2. 隐式 mentions（Phase 4 实时匹配，不入 IR，直接入索引）
        for mention in automaton.find_all(&frag.text) {
            let entity = dict.resolve(&mention.matched_text);
            match entity {
                Ok(eid) => index.add(eid, frag.id, AnchorRole::Mentioned),
                Err(Ambiguous) => {
                    // 歧义：产 Warning，不入索引（§7.4）
                }
            }
        }
    }

    Ok(index)
}
```

> **mentions 不进 IR**：LocationIndex 是 Parser 的派生产物，与 StoryIR 分离。StoryIR 只含 Source of Truth（anchors），mentions 是可重建的派生数据。

## 9.2 索引结构

```text
LocationIndex:
  c_8A91D4 (林风) → [ f_0001 (appears), f_0002 (mentioned), f_0005 (appears) ]
  i_A7E902 (伞)   → [ f_0001 (mentioned) ]
```

- 按 StableId 索引（BTreeMap，确定序列化）。
- 存于 `.novelstudio/cache/location-index/`，不进 Git。
- 诊断跳转复用此索引（"角色 X 年龄矛盾 → 跳转到 f_0001"）。

# 10. Incremental Parsing（增量解析）

遵循 RFC-0001 §9.1（保存时增量）与 §10.2（两层引用 + Stale）。

## 10.1 文件级 Dirty Tracking

Parser 维护**文件粒度**的 dirty 集合：

```rust
struct ParseCache {
    /// 文件路径 → 最后解析时的内容 hash
    file_hashes: BTreeMap<PathBuf, Hash>,

    /// 判断文件是否需要重新解析
    fn is_dirty(&self, path: &Path, current_content: &str) -> bool {
        let current_hash = hash(current_content);
        self.file_hashes.get(path) != Some(&current_hash)
    }
}
```

## 10.2 影响传播（与 RFC-0001 §10.2 对齐）

当某个文件变化时，Parser 评估影响范围：

| 变化文件 | 影响范围 | 处理 |
|:--|:--|:--|
| `fragments/f_0001.md` | L0：该 Fragment 自身 | 重新解析该文件，更新正文 + anchors + mentions |
| | L1：该 Fragment 锚定的 Entity | 重新对该 Entity 做 Entity Linking（若 alias 变了） |
| | L2+：间接引用 | 标 Stale，不立即处理 |
| `entities/characters/c_001.toml` | L0：该 Entity | 更新 Entity 节点 |
| | L1：正文提及该 Entity 的所有 Fragment | 重新对这些 Fragment 做 Entity Linking |
| | L2+：间接引用 | 标 Stale |
| `structure.toml` | L0：整个 Document Graph | 局部重建受影响的链表与反向索引 |
| | L1：被移动的 Fragment | 更新其 Scene 归属 |

> **structure.toml 的特殊性**：它维护所有序列关系，改动它会触发 Document Graph 的局部重建。但 Parser 只重建"变化的 Chapter / Scene / Fragment"对应的链表段，不全量重建。

## 10.3 增量边界

- **Fragment 正文变化** → 只重解析该 Fragment + 重算其 mentions。不影响其他 Fragment。
- **Entity alias 变化** → 重算所有提及该 Entity 的 Fragment 的 mentions（可能增加或减少匹配）。
- **structure.toml 结构变化** → 重建链表段，但 Fragment 正文不重新读取（正文未变）。

```rust
/// 增量解析入口
fn parse_incremental(
    project_dir: &Path,
    ir: &mut StoryIR,
    cache: &mut ParseCache,
    dirty_files: &HashSet<PathBuf>,
) -> Result<(), ParseError> {
    for file in dirty_files {
        match classify_file(file) {
            FileKind::Structure => {
                rebuild_structure_links(ir, file, cache)?;
            }
            FileKind::Fragment => {
                let frag_id = extract_id_from_path(file);
                reparse_fragment(ir, frag_id, file, cache)?;
                relink_entity_mentions(ir, frag_id)?;
            }
            FileKind::Entity => {
                update_entity(ir, file, cache)?;
                let entity_id = extract_id_from_path(file);
                relink_all_mentions_of(ir, entity_id)?;
            }
            FileKind::Knowledge => {
                // KB 变化不由 Parser 处理，通知 Knowledge Layer
            }
        }
    }
    Ok(())
}
```

# 11. Error Handling（错误处理）

Parser 产出的错误映射为 Diagnostics（RFC-0005），供 Compiler 汇总。

## 11.1 错误分类

| 错误类型 | 级别 | 示例 |
|:--|:--|:--|
| **格式错误** | Error | TOML 语法错误、YAML frontmatter 解析失败 |
| **id 不匹配** | Error | Fragment 文件名与 frontmatter.id 不一致（RFC-0003 §5.3） |
| **引用断裂** | Error | structure.toml 引用了不存在的 Fragment；anchor 引用了不存在的 Symbol |
| **重复 id** | Error | 两个 Entity 文件使用同一 StableId |
| **Symbol 冲突** | Error | 两个 Entity 使用同一 Symbol |
| **链表成环** | Error | 违反 RFC-0002 §3.3 Invariant #6 |
| **空 Scene** | Warning | Scene 的 fragments 列表为空 |
| **歧义匹配** | Warning | 正文中的名字匹配到多个 Entity（§6.4） |
| **无锚点 Fragment** | Warning | Fragment 的 anchors 为空（可能是疏漏） |
| **孤儿 Fragment** | Warning | Fragment 文件存在，但未被 structure.toml 引用 |

## 11.2 错误定位

所有 ParseError 必须携带 Source Location，供 Editor 跳转：

```rust
struct ParseError {
    kind: ParseErrorKind,
    loc: SourceLocation,
}

struct SourceLocation {
    file: PathBuf,
    fragment: Option<StableId>,   // 若涉及 Fragment
    line: Option<u32>,            // 若能确定行号
}

// 对于 Fragment 文件，line 通常可确定（TOML/JSON 行号）
// 对于正文匹配问题，定位到 Fragment 级（块级，不定位到行）
```

# 12. Streaming & Chunked Parsing（流式/分块解析）

遵循 RFC-0001 §10，Parser 必须支持流式解析，避免大文件 OOM。

## 12.1 文件级并行

Fragment 文件相互独立（Phase 3），可并行解析：

```rust
fn parse_fragments_parallel(paths: &[PathBuf]) -> Vec<FragmentContent> {
    paths.par_iter()           // rayon 并行迭代
        .map(|p| parse_fragment_file(p))
        .collect()
}
```

## 12.2 增量加载（懒加载）

百万字小说可能有上千个 Fragment。Editor 若只打开一个 Chapter，Parser 无需解析全部：

```rust
/// 按需解析：只解析指定 Chapter 下的 Fragment
fn parse_chapter_lazy(
    ir: &mut StoryIR,
    chapter_id: StableId,
) -> Result<(), ParseError> {
    for scene in ir.document.scenes_of(chapter_id) {
        for frag_id in ir.document.fragments_of(scene) {
            if !ir.document.is_loaded(frag_id) {
                let path = fragment_path(frag_id);
                let content = parse_fragment_file(&path)?;
                ir.document.fill_fragment(frag_id, content);
            }
        }
    }
    Ok(())
}
```

- 未加载的 Fragment 在 IR 中只有骨架（id + 链表位置），无正文。
- Editor 切换 Chapter 时触发懒加载。
- 全量编译（Compiler）触发全量加载。

## 12.3 内存约束

- 单个 Fragment 文件通常 < 5 KB，单文件解析无 OOM 风险。
- OOM 风险来自"同时加载所有 Fragment 正文"——懒加载解决此问题。
- Entity Linking 的词典常驻内存（Entity 通常 < 300 个，词典 < 1 MB）。

# 13. Relationship to RFCs

| RFC | 关系 |
|:--|:--|
| RFC-0001 | Parser 是数据流第二层；遵守 §10 的增量约束与 §9.1 的增量层级 |
| RFC-0002 | 产出 Story IR（Typed Graph Model）；遵守 §3.3 IR Invariants；链表是内存层表示 |
| RFC-0003 | 解析 Project Format 的文件结构；遵守 §3 单一真相源与 §5 各文件格式 |
| RFC-0004 | Parser 产出的 IR 交给 Compiler 校验；Parser 的错误汇入 Diagnostics |
| RFC-0005 | Parser 产出的 ParseError 映射为 Diagnostics |
| RFC-0007–0009, 0014 | Entity Model 的字段细化不影响 Parser 骨架（Parser 只读通用字段 display_name + aliases） |
| RFC-0010 | AI Runtime 以 Fragment 为单位构建 Prompt（依赖 Parser 已解析的 Fragment） |
| RFC-0015 | Parser 不触碰 Knowledge Base；KB 由 Extraction 独立加载 |

# 14. Open Questions

1. **Entity Linking 的匹配模式**：是否支持正则匹配 / 模糊匹配（如"林风走了"匹配"林风"）？v0.1 只支持精确子串匹配（Aho-Corasick）。模糊匹配可能引入非确定性，需谨慎。（倾向：v0.1 精确匹配，模糊匹配留待配置项。）
2. **Symbol 解析时机**：anchors 中的 Symbol 在 Phase 3（Fragment 解析时）解析——此问题已由 Phase 1.5 的引入解决（SymbolTable 先于 Fragment 构建）。
3. **Paragraph / Dialogue 解析**：v0.1 不解析段落级结构（RFC-0002 §6.1 标注为 v0.2+）。何时引入？需要 Markdown AST 吗？（倾向：等 Editor 有实际需求时再引入。）
4. **懒加载的缓存一致性**：懒加载的 Fragment 被 Editor 修改后，IR 中的缓存如何失效？（与 §10 增量解析对齐。）

# Appendix

> **Parser 是纯确定性的文件→IR 转换器。它读文件、建链表、做词典匹配，但从不用 AI、不做推理、不判合理性。四层可信度——anchors（作者）、mentions（Parser）、assertions（Extraction）、inference（KB）——各司其职，Parser 只负责前两层。**
