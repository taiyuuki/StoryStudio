# 1. Abstract（摘要）

Character 是 Semantic Graph 中最复杂的实体类型。本 RFC 细化 `CharacterNode` 的完整字段定义，涵盖：三重 ID、别名体系、属性模型、关系模型、状态机。

Character 的信息分布在三层，各有不同的可信度与持久化策略（与 RFC-0006 §2.3 的四层可信度模型对齐）：

```text
   Entity 文件 (entities/characters/*.toml)    ← 静态属性（Source of Truth）
   Fragment anchors + mentions                 ← 出场记录（派生）
   Knowledge Base (assertions)                 ← 可验证状态（如 alive/age）
```

------

# 2. Design Principle（设计原则）

## 2.1 静态 vs 动态的分离

Character 的信息分两类，存放在不同位置：

| 信息类别 | 例子 | 存放位置 | 为什么 |
|:--|:--|:--|:--|
| **静态属性** | 名字、种族、外貌、背景 | Entity 文件 | 不会随剧情变化，是角色设定 |
| **动态状态** | 存活、年龄、位置、持有物 | Knowledge Base（Assertions） | 随时间变化，需时序验证 |

> **核心原则：Entity 文件不存动态状态。**
>
> 角色的"是否存活""当前年龄"是随剧情演变的动态状态，存入 Knowledge Base 作为 Assertion（带 valid 窗口），由 Compiler 校验一致性。若存入 Entity 文件，则无法表达"1086 年 17 岁，1088 年 19 岁"的时间维度，也无法被时序规则检查。
>
> 这是 Character Model 最重要的设计决策。

## 2.2 与 RFC-0002 骨架的关系

RFC-0002 §6.2 定义了所有 Entity 共享的骨架（id + symbol + display_name + aliases + attributes）。本 RFC 在此骨架上**扩展 Character 专属字段**，不改骨架本身。

# 3. Character Entity Structure（角色实体结构）

## 3.1 文件格式

```toml
# entities/characters/c_8A91D4.toml

id = "c_8A91D4"
symbol = "hero"
display_name = "林风"

# 别名体系（见 §4）
aliases = ["林少侠", "风哥"]
primary_alias = "林少侠"

# Character 专属静态属性
[profile]
race = "human"
gender = "male"
occupation = "剑客"
birth_year = 1069              # 故事内纪年

# 外貌描述（自由文本，不做结构化）
appearance = "身长七尺，眉目清朗，常着青衫"

# 背景描述
background = "孤儿，自幼被山间隐士收养，习得一身武艺"

# 自定义属性（插件可扩展）
[attributes]
weapon_of_choice = "i_A7E902"  # 引用 Item 的 StableId
faction = "o_5D1C88"           # 引用 Organization 的 StableId
```

## 3.2 Rust 类型

```rust
/// Character 实体的完整定义（扩展 RFC-0002 §6.2 的骨架）
pub struct CharacterNode {
    // —— 骨架字段（所有 Entity 共享）——
    pub id: StableId,
    pub symbol: Option<Symbol>,
    pub display_name: String,

    // —— Character 专属 ——
    pub aliases: Vec<Alias>,
    pub primary_alias: Option<String>,
    pub profile: CharacterProfile,
    pub attributes: BTreeMap<String, AttributeValue>,
}

/// 别名条目——支持区分语境
pub struct Alias {
    pub name: String,
    pub context: AliasContext,
}

pub enum AliasContext {
    /// 通用别名（默认）
    General,
    /// 称谓（如"林少侠"是江湖称谓）
    Title,
    /// 昵称（亲密关系者使用）
    Nickname,
    /// 代号 / 化名
    Codename,
}

/// 角色静态档案
pub struct CharacterProfile {
    pub race: Option<String>,
    pub gender: Option<String>,
    pub occupation: Option<String>,
    pub birth_year: Option<StoryYear>,
    pub appearance: Option<String>,    // 自由文本
    pub background: Option<String>,    // 自由文本
}
```

> **`birth_year` 是静态属性**（出生年不随剧情变化），但"当前年龄"是动态状态（随时间增长），存为 KB Assertion。

# 4. Alias System（别名体系）

## 4.1 为什么别名是核心

中文小说的角色称谓极其复杂：

- 全名："林风"
- 江湖称谓："林少侠"
- 长辈称呼："风儿"
- 敌人蔑称："那小子"
- 化名："李二"（潜入时用）

Parser 的 Entity Linking（RFC-0006 §7）依赖别名词典做匹配。完整的别名体系直接影响实体识别的召回率。

## 4.2 别名与 Entity Linking

Parser 构建 Aho-Corasick 自动机时，将 `display_name` + 所有 `aliases` 入典（RFC-0006 §7.2）：

```text
词典：
  "林风"     → c_8A91D4 (display_name)
  "林少侠"   → c_8A91D4 (alias: Title)
  "风哥"     → c_8A91D4 (alias: General)
  "那小子"   → c_8A91D4 (alias: Codename, 但建议不匹配——见下)
```

## 4.3 匹配策略

并非所有别名都适合自动匹配。过泛的称谓（"那小子""那个人"）会导致大量误匹配：

| 别名类型 | 是否自动匹配 | 理由 |
|:--|:--|:--|
| General / Title / Nickname | ✅ | 专指性强，误匹配率低 |
| Codename | ⚠️ 可配置 | 化名只在特定剧情段有效，全局匹配可能误中 |

```toml
# entities/characters/c_8A91D4.toml

[[aliases_entries]]
name = "林少侠"
context = "title"
matchable = true            # 参与 Entity Linking

[[aliases_entries]]
name = "那小子"
context = "codename"
matchable = false           # 不参与自动匹配（太泛）
```

> `matchable` 字段控制 Parser 是否将该别名纳入 Aho-Corasick 词典。默认 General/Title/Nickname 为 true，Codename 为 false。

## 4.4 别名冲突

两个角色共享同一别名时（都叫"风哥"），Parser 产出歧义 Warning（RFC-0006 §7.4），不自动生成 mention，需作者用显式 anchor 消歧。

# 5. Relationship Model（关系模型）

## 5.1 Semantic Graph 中的 Character 关系

角色与其他实体的关系由 SemanticGraph 的 Edge 表达（RFC-0002 §7.2）。Character 常见的关系类型：

| 关系 | 方向 | 时序性 | 举例 |
|:--|:--|:--|:--|
| `AppearsIn` | Character → Scene | 带时序 | 林风出场于场景 X |
| `Knows` | Character → Character | 带时序 | 林风认识周明 |
| `RelatedTo` | Character → Character | 无时序 | 林风与林雨是兄妹（血缘不变） |
| `Holds` | Character → Item | **带时序** | 林风持有伞（第 3 章获得，第 7 章丢失） |
| `LocatedAt` | Character → Location | **带时序** | 林风在河边（场景内有效） |
| `MemberOf` | Character → Organization | 带时序 | 林风加入青云门 |

## 5.2 关系的时序性

关系是否带 `valid` 窗口（RFC-0002 §7.2），取决于该关系是否会随剧情变化：

- **不变关系**（`RelatedTo` 血缘）：`valid = None`（全时段有效）
- **可变关系**（`Holds`、`LocatedAt`、`MemberOf`）：必须带 `valid` 窗口

```rust
// "林风持有伞"——时序关系
SemanticEdge {
    id: se_001,
    from: c_8A91D4,         // 林风
    to: i_A7E902,           // 伞
    relation: RelationKind::Holds,
    valid: Some(ValidityWindow {
        from: Some(StoryTime::Scene(sc_01_02)),  // 第 1 章第 2 场景获得
        until: Some(StoryTime::Scene(sc_03_01)), // 第 3 章第 1 场景丢失
    }),
    evidence: vec![f_0001, f_0015],  // 支撑此关系的 Fragment
}
```

## 5.3 关系存储位置

| 关系类型 | Source of Truth | 存储格式 |
|:--|:--|:--|
| `AppearsIn` | Fragment anchors | Fragment frontmatter（派生为 SemanticEdge） |
| `Knows` / `RelatedTo` | Semantic Graph | 可存于 Character 文件的 `[relations]` 段 |
| `Holds` / `MemberOf` | Semantic Graph（带时序） | 可存于 KB Assertions（见 §6） |

> `Holds` 和 `MemberOf` 这类带时序的关系，**可以同时作为 SemanticEdge 和 KB Assertion 存在**。v0.1 的策略是：时序关系优先存为 KB Assertion（因为它需要时序验证），SemanticGraph 中的对应 Edge 由 Compiler 从 Assertion 派生。

# 6. Dynamic State（动态状态）

## 6.1 哪些状态存在 Knowledge Base

动态状态存为 Assertion（RFC-0015），带 valid 窗口：

| 状态 | Predicate | 示例 Assertion |
|:--|:--|:--|
| 存活 | `alive` | `subject=c_8A91D4, predicate=alive, object=true, valid=[1069, 1092]` |
| 年龄 | `age` | `subject=c_8A91D4, predicate=age, object=17, valid=[year-1086, year-1088]` |
| 所在地 | `located_at` | `subject=c_8A91D4, predicate=located_at, object=l_riverside, valid=[sc_01_02]` |
| 持有物 | `holds` | `subject=c_8A91D4, predicate=holds, object=i_umbrella, valid=[sc_01_02, sc_03_01]` |
| 身份 | `status` | `subject=c_8A91D4, predicate=status, object=hidden, valid=[sc_05, sc_08]`（潜入状态） |

## 6.2 为什么不存 Entity 文件

```toml
# ❌ 错误做法：在 Entity 文件存动态状态
[profile]
alive = true          # 什么时候 true？全书？死亡后就错了
age = 17              # 1086 年 17 岁，1088 年呢？
```

动态状态的核心特征是**随时间变化**。Entity 文件是静态的设定快照，没有时间维度。存在 KB 中才能：

- 表达"1086 年 alive=true，1092 年 alive=false"
- 被 Compiler 的时序规则检查（dead_character_revived、age_inconsistency）
- 带 Evidence 追溯到具体文本

## 6.3 状态派生

Compiler 从 KB Assertions 派生角色的"当前状态"（用于 Editor 展示）：

```rust
/// 查询角色在某时间点的状态快照
fn character_state_at(
    char_id: StableId,
    time: StoryTime,
    kb: &KnowledgeBase,
) -> CharacterStateSnapshot {
    CharacterStateSnapshot {
        alive: kb.query(char_id, "alive", time),
        age: kb.query(char_id, "age", time),
        located_at: kb.query(char_id, "located_at", time),
        holds: kb.query_all(char_id, "holds", time),
    }
}
```

> 这是**派生查询**，不持久化。Editor 展示"角色当前状态"时实时计算。

# 7. Compiler Rules for Character（角色相关检查规则）

Character Model 为 Compiler（RFC-0004）提供数据基础。以下是依赖 Character 数据的内置规则：

| 规则 ID | Phase | depends_on | 检查内容 |
|:--|:--|:--|:--|
| `dead_character_revived` | Semantic | [Assertion, Entity, Fragment] | 角色死亡后在后续场景出场（RFC-0004 §5.3） |
| `age_inconsistency` | Semantic | [Assertion, Entity] | 年龄不随时间增长 / 倒退 |
| `alias_conflict` | Structure | [Entity] | 两个角色有 matchable 的同名别名 |
| `orphan_character` | Structure | [Entity, Fragment] | 角色从未在任何 Fragment 出场（可能忘了写或该删除） |
| `missing_pov` | Style | [Structure] | Scene 的 pov 引用了不存在的角色 |

这些规则的实现见 RFC-0004 §5，这里只定义 Character 侧的数据契约。

# 8. AI Context（AI 上下文中的角色表示）

AI Runtime（RFC-0010）构建 Prompt 时需要角色的上下文。Character 的上下文由三部分组成：

```text
角色上下文（给 AI 的 Prompt 片段）：
  1. 静态档案：display_name + profile + background（来自 Entity 文件）
  2. 当前状态：alive / age / located_at / holds（来自 KB，按时间点派生）
  3. 近期出场：最近 N 个 Fragment 的出场摘要（来自 Location Index）
```

```rust
/// 构建角色的 AI 上下文
fn build_character_context(
    char_id: StableId,
    ir: &StoryIR,
    kb: &KnowledgeBase,
    loc_idx: &LocationIndex,
    current_time: StoryTime,
) -> String {
    let char = ir.semantic.get_character(char_id);
    let state = character_state_at(char_id, current_time, kb);

    format!(
        "角色：{name}（{aliases}）\n\
         档案：{race}，{occupation}。{background}\n\
         当前状态：{alive}，{age}岁，位于{location}\n\
         持有：{holds}",
        name = char.display_name,
        // ...
    )
}
```

> AI 上下文使用 Symbol + Display Name，不用 StableId（Prompt 里塞哈希无意义，RFC-0002 §4.1）。

# 9. Serialization（序列化）

遵循 RFC-0002 §9 的确定性约束与 RFC-0003 §5.4 的 Entity 文件格式。

```toml
# 完整示例：entities/characters/c_8A91D4.toml

id = "c_8A91D4"
symbol = "hero"
display_name = "林风"
primary_alias = "林少侠"

[[aliases_entries]]
name = "林少侠"
context = "title"
matchable = true

[[aliases_entries]]
name = "风哥"
context = "general"
matchable = true

[[aliases_entries]]
name = "那小子"
context = "codename"
matchable = false

[profile]
race = "human"
gender = "male"
occupation = "剑客"
birth_year = 1069
appearance = "身长七尺，眉目清朗，常着青衫"
background = "孤儿，自幼被山间隐士收养"

[attributes]
weapon_of_choice = "i_A7E902"
faction = "o_5D1C88"
```

- `aliases_entries` 数组按输入顺序输出（不重排，保留作者意图）。
- `[attributes]` 内的键按 BTreeMap 字典序（RFC-0002 §9）。
- `id` 必须等于文件名（RFC-0003 §5.3 同款校验）。

# 11. Open Questions

1. **关系存储位置**：`Knows` / `RelatedTo` 这类无时序关系，存 Character 文件的 `[relations]` 段，还是独立的 relations 文件？（倾向：Character 文件内，就近原则。）
2. **角色成长线**：是否需要结构化表达"角色的成长弧线"（如从怯懦到勇敢的转变）？（倾向：v0.1 不结构化，留作 background 自由文本 + Semantic Validator 分析。）
3. **死亡的精确语义**：`alive=false` 的 valid.until 是无限还是到全书结束？（倾向：无限，角色死后永久 alive=false。回忆场景用独立的 valid 窗口标注。）
4. **别名的历史变化**：角色改名的场景（如结婚后改姓），别名是否带时序？（倾向：v0.1 不支持时序别名，用多个 alias 条目 + 人工判断。）

------

# Appendix

> **静态属性存 Entity 文件，动态状态存 Knowledge Base。这是 Character Model 的核心设计决策——它让角色的设定（不变）与演变（可变）各归其位，时序检查才有据可依。**
