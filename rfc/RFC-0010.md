# 1. Abstract（摘要）

AI Runtime 是 Story Studio 数据流中**唯一允许非确定性的层**。它管理 Agent 的执行、上下文构建、Change 生成与提交——是"AI 生成 → 确定性验证"这条链的编排者。

```text
   作者 / 自动化触发
         │
         ▼
    Task（统一抽象）
         │
    ┌────┴────┐
    │         │
    ▼         ▼
 构建上下文   会话管理（若有状态）
    │
    ▼
 AI Provider（GPT / Claude / Gemini / ...）   ← 非确定
    │
    │ 输出自然语言文本
    ▼
 Parser 解析 → Change 序列                   ← 确定性
    │
    ▼
 Compiler Dry-Run                            ← 确定性验证
    │
    ├─ Error = 0 → 提交（合入 IR）
    └─ Error > 0 → 反馈重试
```

> **AI 写小说，系统验逻辑。** AI 自由地用自然语言创作，系统负责把文本解析为结构、验证一致性、保证提交安全。AI 不碰 Change 的 JSON，不碰 IR 的内部结构。

# 2. Responsibilities（职责边界）

## 2.1 AI Runtime 做什么

- 管理不同 AI Provider 的连接（GPT / Claude / Gemini / DeepSeek / Ollama）
- 接收 Task 请求，构建上下文（角色状态、时间线、已有正文）
- 调用 AI Provider 生成文本
- 用 Parser 将 AI 输出解析为 Fragment + Change
- 调用 Compiler Dry-Run 验证 Change
- 通过则提交，失败则反馈重试

## 2.2 AI Runtime 不做什么

| 不做的事 | 归属 | 理由 |
|:--|:--|:--|
| 直接修改 IR | 无（只通过 Change） | RFC-0001 §6：Agent 只生成 Change |
| 一致性判断 | Compiler | AI 的判断非确定，不可信 |
| 文本解析 | Parser（复用） | 不重复造解析器 |
| 语义质量评估 | Semantic Validator | 主观判断 |
| 训练 / 微调模型 | 无 | 不做 AI Model（RFC-0001 §5） |

## 2.3 确定性边界

```
   AI Runtime 内部：          非确定（AI 生成）
         │
    Dry-Run 通过后
         │
         ▼
   提交到 IR / KB：           确定（已验证的 Change）
```

非确定性**只存在于 AI Runtime 内部**。一旦 Change 通过 Dry-Run 并提交，下游（Compiler / Editor / Export）看到的就是确定性数据。这与 RFC-0001 §9.2、RFC-0015 §7 的隔离模型一致。

# 3. Provider Abstraction（Provider 抽象）

## 3.1 统一接口

所有 AI 模型实现统一的 `AiProvider` trait（RFC-0001 §3.3 AI is Replaceable）：

```rust
#[async_trait]
pub trait AiProvider: Send + Sync {
    /// Provider 标识（如 "openai"、"anthropic"、"ollama"）
    fn id(&self) -> &str;

    /// 发送请求，返回生成的文本
    async fn generate(&self, request: &GenerateRequest) -> Result<GenerateResponse, AiError>;
}

pub struct GenerateRequest {
    /// 系统指令（角色设定、输出格式要求等）
    pub system: String,

    /// 用户消息（任务描述 + 上下文）
    pub messages: Vec<Message>,

    /// 模型参数
    pub model: String,           // 如 "claude-sonnet-4.5"
    pub temperature: f32,
    pub max_tokens: usize,
}

pub struct Message {
    pub role: Role,
    pub content: String,
}

pub enum Role {
    System,
    User,
    Assistant,    // AI 之前的回复（有状态会话用）
}

pub struct GenerateResponse {
    pub text: String,            // AI 生成的文本
    pub usage: TokenUsage,       // token 消耗
}

pub struct TokenUsage {
    pub input_tokens: usize,
    pub output_tokens: usize,
}
```

## 3.2 Provider 注册

```rust
pub struct ProviderRegistry {
    providers: BTreeMap<String, Box<dyn AiProvider>>,
}

impl ProviderRegistry {
    pub fn new() -> Self {
        let mut reg = Self { providers: BTreeMap::new() };

        // reg.register("anthropic", Box::new(AnthropicProvider::new(...)));
        // reg.register("ollama", Box::new(OllamaProvider::new(...)));
        reg
    }

    pub fn register(&mut self, id: &str, provider: Box<dyn AiProvider>) {
        self.providers.insert(id.to_string(), provider);
    }

    pub fn get(&self, id: &str) -> Option<&dyn AiProvider> {
        self.providers.get(id).map(|b| b.as_ref())
    }
}
```

# 4. Task Model（任务模型）

## 4.1 统一 Task 抽象

所有 AI 任务实现统一的 `Task` trait，内部分无状态 / 有状态两种执行模式：

```rust
#[async_trait]
pub trait Task {
    /// 任务类型标识
    fn kind(&self) -> TaskKind;

    /// 执行模式
    fn mode(&self) -> TaskMode;

    /// 构建上下文（调用前）
    fn build_context(&self, ir: &StoryIR, kb: Option<&KnowledgeBase>) -> TaskContext;

    /// 解析 AI 输出为 Change 序列（调用后）
    fn parse_output(&self, ai_output: &str, ir: &StoryIR) -> Result<Vec<Change>, TaskError>;

    /// Dry-Run 失败时的反馈构建
    fn build_feedback(&self, errors: &[Diagnostic]) -> String;
}

pub enum TaskKind {
    /// 续写 / 新增 Fragment（创作）
    WriteFragment,
    /// 补充锚点（维护）
    AddAnchors,
    /// 修改角色属性（编辑）
    UpdateCharacter,
    /// 抽取知识断言（Knowledge Layer）
    ExtractAssertions,
    /// 语义检查（Semantic Validator）
    SemanticCheck,
    /// 自定义（插件）
    Custom(String),
}

pub enum TaskMode {
    /// 无状态单次：一次调用完成
    Stateless,
    /// 有状态会话：多轮对话，可试错回退
    Conversational,
}
```

## 4.2 无状态任务（StatelessTask）

适用于：补锚点、抽取事实、属性修改等**确定性较高**的维护任务。

```rust
pub async fn run_stateless(
    task: &dyn Task,
    provider: &dyn AiProvider,
    ir: &StoryIR,
    kb: Option<&KnowledgeBase>,
) -> Result<TaskResult, TaskError> {
    // 1. 构建上下文
    let ctx = task.build_context(ir, kb);

    // 2. 调用 AI（单次）
    let request = GenerateRequest {
        system: ctx.system_prompt,
        messages: vec![Message::user(ctx.user_prompt)],
        ..ctx.model_config
    };
    let response = provider.generate(&request).await?;

    // 3. 解析输出为 Change
    let changes = task.parse_output(&response.text, ir)?;

    // 4. 返回（Dry-Run 由调用方触发）
    Ok(TaskResult { changes, usage: response.usage })
}
```

## 4.3 有状态会话（ConversationalTask）

适用于：续写章节、构思情节等**需要多轮探讨**的创作任务。

```rust
pub struct Conversation {
    /// 对话历史（多轮）
    messages: Vec<Message>,
    /// 当前 draft IR（AI 的改动累积在此，未提交）
    draft_ir: StoryIR,
    /// 会话的 Scene / Chapter 范围
    scope: StableId,
}

impl Conversation {
    pub async fn send(
        &mut self,
        user_input: &str,
        provider: &dyn AiProvider,
        compiler: &RuleRegistry,

        // 1. 追加用户消息
        self.messages.push(Message::user(user_input));

        // 2. 调用 AI（带上历史）
        let request = GenerateRequest {
            system: self.system_prompt(),
            messages: self.messages.clone(),
            ..self.model_config()

        let response = provider.generate(&request).await?;

        // 3. 解析输出为 Change
        let changes = self.parse_output(&response.text)?;

        // 4. 在 draft_ir 上应用 Change
        for change in &changes {
            self.draft_ir.apply(change)?;

        // 5. 保存 AI 回复到历史
        self.messages.push(Message::assistant(&response.text));

        Ok(ConversationTurn { changes, usage: response.usage })
    }

    /// 提交当前 draft（走 Dry-Run）
    pub fn commit(&self, compiler: &RuleRegistry) -> CommitResult {
        // 将 draft 与原 IR 的 diff 转为 Change 序列，走 Dry-Run
        // ...
    }

    /// 回退到上一轮
    pub fn rollback(&mut self) {
        // 移除最后一轮的 AI 回复 + 对应的 draft 改动
        // ...
    }
}
```

## 5.2 续写 Fragment 的上下文

```rust
impl<'a> ContextBuilder<'a> {
    /// 构建"续写 Fragment"的上下文
    pub fn for_write_fragment(
        &self,
        scene_id: StableId,
    ) -> TaskContext {
        let scene = self.ir.document.get_scene(scene_id);

        // 1. 场景信息（POV、mood、function）
        let scene_info = self.build_scene_info(scene);

        // 2. 前 N 个 Fragment 的正文（提供连贯性）
        let recent_text = self.build_recent_fragments(scene_id, 3);

        // 3. POV 角色的当前状态（RFC-0008 §8）
        let pov_context = scene.pov
            .map(|id| self.build_character_context(id, scene.story_time));

        // 4. 出场角色的简介
        let characters = self.build_character_briefs(scene_id);

        // 5. 当前时间线位置
        let timeline = self.build_timeline_context(scene.story_time);

        // 组装（在 token 预算内裁剪）
        TaskContext {
            system_prompt: format!(
                "你是一位小说作者。请以自然语言续写故事正文。\n\
                 场景：{scene_info}\n{pov}{mood}{function}",
                ...
            ),
            user_prompt: format!(
                "前文：\n{recent}\n\n\
                 角色：{characters}\n\n\
                 时间：{timeline}\n\n\
                 请续写下一个片段。"
            ),
            model_config: ModelConfig::creative(),
        }
    }
}
```

## 5.3 Token 预算管理

```rust
impl<'a> ContextBuilder<'a> {
    /// 在 token 预算内裁剪上下文
    fn fit_budget(&self, sections: Vec<ContextSection>, budget: usize) -> String {
        let mut result = String::new();
        let mut used = 0;

        for section in sections {
            let tokens = estimate_tokens(&section.content);
            if used + tokens > budget {
                // 超预算：截断或跳过低优先级段
                break;
            }
            result.push_str(&section.content);
            used += tokens;
        }
        result
    }
}
```

优先级（高→低）：场景设定 > POV状态 > 近期正文 > 角色简介 > 时间线。

> **上下文使用 Symbol + Display Name，不用 StableId**——Prompt 里塞哈希无意义（RFC-0002 §4.1）。

# 6. Output Pipeline（输出管线）

## 6.1 核心流程：AI 输出文本 → Parser → Change

```text
   AI 输出（自然语言）
         │
         ▼
   分离 Fragment（若 AI 输出多段）
         │
         ▼
   Parser 解析每个 Fragment               ← 复用 RFC-0006
   （提取 anchors、校验格式）
         │
         ▼
   转换为 Change 序列
         │
         ▼
   Compiler Dry-Run                      ← 复用 RFC-0004
         │
   ├─ Passed → 提交
   └─ Failed → 反馈 AI 重试
```

## 6.2 实现

```rust
pub struct OutputPipeline<'a> {
    parser: &'a Parser,          // 复用 RFC-0006 的 Parser
    compiler: &'a RuleRegistry,  // 复用 RFC-0004 的 Compiler
}

impl<'a> OutputPipeline<'a> {
    /// 将 AI 输出处理为已验证的 Change 序列
    pub async fn process(
        &self,
        ai_output: &str,
        target_scene: StableId,
        task: &dyn Task,
        ir: &StoryIR,
        kb: Option<&KnowledgeBase>,
    ) -> Result<PipelineResult, PipelineError> {
        // 1. 用 Parser 解析 AI 输出（把它当作 Fragment 文件内容）
        let parsed = self.parser.parse_fragment_text(ai_output)?;

        // 2. 转换为 Change 序列
        let changes = task.parse_output(ai_output, ir)?;

        // 3. 逐个 Dry-Run（或批量）
        let mut validated = Vec::new();
        let mut all_errors = Vec::new();

        for change in &changes {
            match self.compiler.dry_run(ir, change, kb, &Default::default()) {
                DryRunResult::Passed => validated.push(change.clone()),
                DryRunResult::Failed(errors) => {
                    all_errors.extend(errors);
                }
            }
        }

        if all_errors.is_empty() {
            Ok(PipelineResult { changes: validated })
        } else {
            Err(PipelineError::ValidationFailed { errors: all_errors })
        }
    }
}
```

> **AI 输出走 Parser**——AI 生成的文本与作者手写的文本走同一条解析管线，保证格式一致性。AI 不需要输出 JSON 或 Change 结构，只需输出合格的 Fragment 文本。

## 6.3 为什么 AI 不直接输出 Change JSON

| | AI 输出文本（推荐） | AI 输出 Change JSON |
|:--|:--|:--|
| 创作自由度 | ✅ AI 正常写作 | ❌ AI 要兼顾格式约束 |
| 文笔质量 | ✅ 不受格式干扰 | ❌ 格式要求消耗注意力 |
| 格式可靠性 | ✅ Parser 统一校验 | ❌ AI 可能输出非法 JSON |
| 与作者手写一致 | ✅ 同一管线 | ❌ 两条管线 |
| 适用范围 | 所有创作任务 | 仅结构化操作 |

只有纯结构化操作（移动 Chapter、删除 Fragment）才考虑用 Change JSON，但 v0.1 这些操作由作者在 Editor 直接做，不经过 AI。

# 7. Change Generation（Change 生成）

## 7.1 Change 类型

与 RFC-0002 的节点操作对应：

```rust
pub enum Change {
    // —— Document Graph 操作 ——
    InsertFragment { scene: StableId, after: Option<StableId>, content: FragmentContent },
    UpdateFragment { id: StableId, text: String, anchors: Vec<EntityAnchor> },
    DeleteFragment { id: StableId },
    MoveFragment { id: StableId, to_scene: StableId, after: Option<StableId> },

    // —— 结构操作 ——
    InsertScene { chapter: StableId, after: Option<StableId>, scene: SceneSpec },
    MoveScene { id: StableId, to_chapter: StableId },
    ReorderChapter { id: StableId, after: Option<StableId> },

    // —— Entity 操作 ——
    UpdateCharacter { id: StableId, fields: CharacterUpdate },
    CreateCharacter { character: CharacterNode },
    UpdateLocation { id: StableId, fields: LocationUpdate },
    UpdateItem { id: StableId, fields: ItemUpdate },

    // —— Knowledge Base 操作 ——
    SubmitAssertion { assertion: Assertion },
    UpdateAssertion { id: StableId, fields: AssertionUpdate },
    WithdrawAssertion { id: StableId },

    // —— Symbol 操作 ——
    RenameSymbol { entity: StableId, new_symbol: Symbol },
}
```

## 7.2 Change 的原子性

- 单个 Change 是原子操作——Dry-Run 通过则整体应用，失败则整体拒绝。
- AI 可能一次生成多个 Change（如续写了 3 个 Fragment）。v0.1 策略：**逐个 Dry-Run**，若任一失败则全部不提交（保持原子性），错误反馈给 AI。

# 8. Dry-Run Integration（Dry-Run 集成）

## 8.1 反馈循环

```rust
pub async fn run_with_retry(
    task: &dyn Task,
    provider: &dyn AiProvider,
    ir: &StoryIR,
    kb: Option<&KnowledgeBase>,
    compiler: &RuleRegistry,
    max_retries: usize,
) -> Result<Vec<Change>, TaskError> {
    let mut attempts = 0;
    let mut feedback = String::new();

    loop {
        // 1. 构建上下文（含上次的错误反馈）
        let mut ctx = task.build_context(ir, kb);
        if !feedback.is_empty() {
            ctx.user_prompt.push_str(&format!(
                "\n\n上次尝试存在问题：\n{feedback}\n\n请修正后重试。"
            ));
        }

        // 2. 调用 AI
        let request = GenerateRequest { /* ... */ };
        let response = provider.generate(&request).await?;

        // 3. 解析为 Change
        let changes = match task.parse_output(&response.text, ir) {
            Ok(c) => c,
            Err(e) => {
                attempts += 1;
                feedback = format!("输出解析失败：{e}");
                if attempts >= max_retries { return Err(e); }
                continue;
            }
        };

        // 4. Dry-Run
        let mut all_errors = Vec::new();
        for change in &changes {
            if let DryRunResult::Failed(errors) = compiler.dry_run(ir, change, kb, &Default::default()) {
                all_errors.extend(errors);
            }
        }

        if all_errors.is_empty() {
            return Ok(changes);  // 全部通过
        }

        // 5. 构建反馈
        attempts += 1;
        feedback = task.build_feedback(&all_errors);

        if attempts >= max_retries {
            return Err(TaskError::MaxRetriesExceeded { errors: all_errors });
        }
        // 重试
    }
}
```

## 8.2 重试上限

```rust
const DEFAULT_MAX_RETRIES: usize = 3;
```

- 防止 AI 无限重试消耗 token。
- 达到上限后，将最后的错误返回给作者，由人工决定是否调整指令后重试。

## 8.3 反馈格式

Dry-Run 失败时，错误诊断转换为自然语言反馈给 AI：

```text
上次生成的 Fragment 存在以下问题：

1. [Error] 角色"周明"在场景中出场，但该角色已在第 5 章死亡（断言 a_zhou_dead）。
   请修正：要么这是一个回忆场景（需在 KB 标注），要么避免让已死亡角色出场。

2. [Error] Fragment 的 anchor 引用了不存在的实体 c_XXXXXX。
   请修正：检查实体 ID 是否正确。
```

> 反馈使用自然语言 + 诊断 message，不暴露内部 Diagnostic 结构——AI 只需要理解"哪里错了、怎么改"。

# 9. Extraction as Task（知识抽取作为任务）

RFC-0015 §6 定义的 Extraction 管线，在 AI Runtime 中作为一种特殊 Task 实现：

```rust
pub struct ExtractAssertionsTask {
    /// 要抽取的 Fragment 范围
    target_fragments: Vec<StableId>,
    /// 要抽取的 predicate 类型（如 ["alive", "age", "holds"]）
    predicates: Vec<String>,
}

#[async_trait]
impl Task for ExtractAssertionsTask {
    fn kind(&self) -> TaskKind { TaskKind::ExtractAssertions }
    fn mode(&self) -> TaskMode { TaskMode::Stateless }

    fn build_context(&self, ir: &StoryIR, _: Option<&KnowledgeBase>) -> TaskContext {
        // 提取目标 Fragment 的正文 + 已有相关 Entity 信息
        let fragments_text = self.target_fragments.iter()
            .map(|id| ir.document.get_fragment(*id).text.clone())
            .collect::<Vec<_>>()
            .join("\n---\n");

        TaskContext {
            system_prompt: format!(
                "你是知识抽取器。从以下故事文本中提取可验证的断言。\n\
                 只抽取这些类型的断言：{:?}\n\
                 每条断言必须标注：subject（角色ID）、predicate、object、\
                 时间范围、证据原文。\n\
                 输出 YAML 格式。",
                self.predicates
            ),
            user_prompt: fragments_text,
            model_config: ModelConfig::extraction(),  // 低温度
        }
    }

    fn parse_output(&self, ai_output: &str, _: &StoryIR) -> Result<Vec<Change>, TaskError> {
        // 解析 AI 输出的 YAML 为 SubmitAssertion Change 序列
        let drafts: Vec<AssertionDraft> = serde_yaml::from_str(ai_output)?;
        let changes = drafts.into_iter()
            .map(|d| Change::SubmitAssertion { assertion: d.into() })
            .collect();
        Ok(changes)
    }

    fn build_feedback(&self, errors: &[Diagnostic]) -> String {
        errors.iter()
            .map(|e| format!("- [{}] {}", e.severity, e.message))
            .collect::<Vec<_>>()
            .join("\n")
    }
}
```

> **Extraction 走与 Agent Change 完全相同的管线**：构建上下文 → AI 生成 → 解析为 Change（SubmitAssertion）→ Dry-Run → 提交。这是 RFC-0015 §7 强调的"两条管线同构"。

# 10. Session Management（会话管理）

## 10.1 会话的生命周期

```text
   创建会话（打开一个创作任务）
         │
         ▼
   多轮对话（send / rollback）
         │
    ┌────┴────┐
    │         │
    ▼         ▼
 commit     discard
    │         │
    ▼         ▼
 提交 IR    丢弃 draft
```

## 10.2 Draft IR 的存储

```text
.novelstudio/
└── sessions/
    └── sess_20260711_a3f/
        ├── conversation.json     # 对话历史
        ├── draft-ir.bin          # draft IR 快照
        └── meta.toml             # 会话元信息
```

- 会话状态存于 `.novelstudio/sessions/`，不进 Git。
- 会话可跨 Editor 重启恢复（从 session 目录加载）。
- 提交后 draft 可选保留（用于审计）或删除。

## 10.3 回退（Rollback）

```rust
impl Conversation {
    /// 回退到指定轮次
    pub fn rollback_to(&mut self, turn: usize) {
        // 截断对话历史
        self.messages.truncate(turn * 2);  // 每轮 = user + assistant

        // 重建 draft IR（从原始 IR 重放到该轮的 Change）
        self.draft_ir = self.base_ir.clone();
        for change in self.changes_up_to(turn) {
            self.draft_ir.apply(change).ok();
        }
    }
}
```

> **Draft IR 是可重建的**——从原始 IR + 已应用的 Change 序列重放即可。因此不需要持久化 draft 的中间状态，只需持久化 Change 序列。

# 11. Determinism Boundary（确定性边界）

## 11.1 非确定性的隔离

```
   ┌─────────────── AI Runtime 内部 ───────────────┐
   │                                               │
   │  AI 生成（非确定）                              │
   │      │                                        │
   │      ▼                                        │
   │  Parser 解析（确定）                            │
   │      │                                        │
   │      ▼                                        │
   │  Compiler Dry-Run（确定）                       │
   │      │                                        │
   │      ├─ Passed → 提交                          │
   │      └─ Failed → 反馈重试（回到 AI 生成）         │
   │                                               │
   └──────────────────┬────────────────────────────┘
                      │
                      ▼ 提交后的 Change
              ─────────────────────
              IR / KB（确定，已验证）
              ─────────────────────
```

## 11.2 对称性

| 管线 | 生成（非确定） | 验证（确定） | 提交后 |
|:--|:--|:--|:--|
| Agent Change | AI 生成文本 | Parser + Dry-Run | IR |
| Extraction | AI 生成断言 | Dry-Run | Knowledge Base |

两条管线同构（RFC-0015 §7、RFC-0001 §9.2）。

## 11.3 保证

- **提交的 Change 一定通过 Dry-Run**（Error = 0）。
- **Dry-Run 不通过的 Change 永不进入 IR / KB**。
- AI 的非确定性不影响下游——Compiler / Editor / Export 看到的都是已验证的数据。

# 13. Open Questions

1. **流式输出**：AI Provider 是否支持流式（streaming）输出？Editor 实时展示生成进度？（倾向：是，但 v0.1 可先非流式，流式留 v0.2。）
2. **多 Agent 协作**：多个 Agent 是否能并行处理不同 Scene？（倾向：v0.1 串行，并行需处理 draft IR 冲突。）
3. **Prompt 版本管理**：System Prompt 是否版本化，便于 A/B 测试不同 Prompt？（倾向：是，Prompt 存于 config/，可 Git 追踪。）
4. **成本控制**：是否需要 token 预算上限，防止单次任务消耗过多？（倾向：是，Task 携带 budget，超限中止。）
5. **Semantic Validator 的集成**：Semantic Validator 作为 Task 调用 AI，其产出（Hint/Suggestion）如何回流到 Diagnostics？（倾向：通过 DiagnosticSink，但标注 source 为 SemanticValidator。）

# Appendix

> **AI 写小说，系统验逻辑。AI 用自然语言自由创作，系统用 Parser 解析、用 Compiler 验证。非确定性被关在 AI Runtime 内部——提交后的 Change 永远是已验证的确定性数据。Provider 可替换，Task 可扩展，但"生成→验证→提交"的管线不变。**
