# 1. Abstract（摘要）

Plugin System 让 Story Studio 可被第三方扩展，而不修改核心代码。v0.1 的核心管线（Parser / Compiler / Export）设计已预留了扩展点，本 RFC 定义插件如何接入这些扩展点。

```text
   Plugin 可扩展的维度：
   ├─ Compiler Rule（自定义检查规则）
   ├─ Exporter（自定义导出格式）
   ├─ AI Task（自定义 AI 任务类型）
   ├─ Entity Attribute（自定义实体属性）
   └─ Parser Hook（自定义语法扩展，未来）
```

> **v0.1 不实现插件系统。** 本 RFC 只定义扩展点契约与加载机制的设计，为核心代码预留正确的抽象。

------

# 2. Design Principle（设计原则）

## 2.1 确定性优先

插件不得破坏系统的确定性保证（RFC-0004 §8、RFC-0006 §3）：

- Compiler Rule 插件必须是确定性的（纯函数，无随机 / 网络 / 时间）。
- 插件产出的 Error 同样遵循"Dry-Run 验证"流程。
- AI Task 插件的非确定性被限制在 AI Runtime 内部（RFC-0010 §11）。

## 2.2 权限隔离

插件运行在受限权限下：

| 能力 | 允许 | 说明 |
|:--|:--|:--|
| 读取 IR / KB | ✅ | 只读访问 |
| 注册 Compiler Rule | ✅ | 通过 RuleRegistry.register() |
| 注册 Exporter | ✅ | 通过 ExportRegistry |
| 注册 AI Task | ✅ | 通过 TaskRegistry |
| 直接修改 IR | ❌ | 只能通过 Change |
| 直接写文件 | ❌ | 只能写 `.novelstudio/cache/` |
| 网络访问 | ❌（默认） | 需显式声明权限 |

## 2.3 不破坏铁律

插件遵守 RFC-0001 §8 的铁律：不绕过 Story IR 直接操作文本文件。插件只能通过 Change 机制间接修改 Project。

# 3. Plugin Manifest（插件清单）

每个插件有一个清单文件声明其能力：

```toml
# my-plugin/plugin.toml

[plugin]
name = "foreshadow-tracker"
version = "0.1.0"
author = "Taiyuuki"
description = "追踪伏笔的埋设与回收"
api_version = 1               # Story Studio 插件 API 版本

# 声明的扩展点
[extensions]
compiler_rules = ["ForeshadowRule"]    # 注册的规则
exporters = []                          # 注册的导出器
ai_tasks = []                           # 注册的 AI 任务
entity_attributes = []                  # 自定义属性

# 权限声明
[permissions]
network = false              # 是否需要网络访问
cache_write = true           # 是否需要写缓存
```

# 4. Extension Points（扩展点契约）

## 4.1 Compiler Rule 插件

插件提供的 Rule 实现 RFC-0004 §3.1 的 `Rule` trait：

```rust
// 插件代码示例
pub struct ForeshadowRule;

impl Rule for ForeshadowRule {
    fn id(&self) -> &str { "foreshadow_tracker" }
    fn default_severity(&self) -> Severity { Severity::Hint }
    fn phase(&self) -> RulePhase { RulePhase::Style }
    fn depends_on(&self) -> &[Dependency] {
        &[Dependency::Fragment, Dependency::Entity]
    }
    fn run(&self, ctx: &mut RuleContext) {
        // 扫描所有 function=foreshadow 的 Scene
        // 检查其伏笔是否在后续 Scene 回收
        // 产出 Hint 级诊断
    }
}
```

**约束：**
- 插件 Rule 的最高默认级别是 **Hint**（不可默认 Error）。
- 若作者在 config 中将插件 Rule 提升为 Error，需显式配置。
- 插件 Rule 同样走 Dry-Run 流程。

## 4.2 Exporter 插件

```rust
pub struct JsonExporter;

impl Exporter for JsonExporter {
    fn format(&self) -> ExportFormat { ExportFormat::Custom("json") }
    fn export(&self, ir: &StoryIR, options: &ExportOptions) -> Result<ExportOutput, ExportError> {
        // 自定义导出逻辑
    }
}
```

## 4.3 AI Task 插件

插件可实现 RFC-0010 §4.1 的 `Task` trait，注册自定义任务类型：

```rust
pub struct AnalyzePacingTask;

#[async_trait]
impl Task for AnalyzePacingTask {
    fn kind(&self) -> TaskKind { TaskKind::Custom("analyze_pacing") }
    // ...
}
```

## 4.4 Entity Attribute 插件

插件可注册自定义属性类型，扩展 Entity 的 `[attributes]` 段：

```toml
# 插件声明自定义属性
[entity_attributes]
character.martial_arts = "martial_arts_spec"   # 角色的武功属性
```

这些属性存入 Entity 文件的 `[attributes]`（RFC-0003 §5.4），由插件负责解析与验证。

# 5. Loading Mechanism（加载机制）

## 5.1 插件发现

```text
project/
├── config/
│   └── plugins.toml          # 启用的插件列表
└── .novelstudio/
    └── plugins/
        └── foreshadow-tracker/   # 已安装的插件
            ├── plugin.toml
            └── (插件代码 / WASM)
```

```toml
# config/plugins.toml

[plugins]
foreshadow-tracker = { enabled = true }
weather-consistency = { enabled = true, severity = "warning" }
```

## 5.2 v0.1 的策略

> **v0.1 不支持动态加载插件。** 所有规则 / 导出器 / 任务都是内置的（编译时固定）。

v0.1 的抽象（Rule trait、Exporter trait、Task trait）已为未来插件预留了正确接口。未来引入插件时：

- **方案 A（WASM）**：插件编译为 WASM，运行在沙箱中。安全性最好，但 API 设计复杂。
- **方案 B（动态库）**：插件编译为动态库（.so / .dylib / .dll），运行时加载。性能好，但安全性差。
- **方案 C（脚本）**：插件用脚本语言（如 Lua / Rhai），解释执行。最安全但性能最差。

v0.1 不做选择，待 v0.2 评估。

# 6. Plugin Safety（插件安全）

## 6.1 确定性审计

插件 Rule 注册时，Compiler 验证其确定性：

- Rule 的 `run()` 不能有副作用（纯函数）。
- 不能在 `run()` 中调用随机数、读取系统时间、发起网络请求。
- v0.1 通过代码审查保证；未来用 WASM 沙箱强制。

## 6.2 错误隔离

插件 Rule panic 不应崩溃 Compiler：

```rust
fn run_rule_safely(rule: &dyn Rule, ctx: &mut RuleContext) {
    match std::panic::catch_unwind(|| rule.run(ctx)) {
        Ok(()) => {}
        Err(_) => {
            ctx.report(Diagnostic::error(
                "plugin_error",
                format!("插件规则 {} 执行时崩溃", rule.id()),
                SourceLocation::none(),
            ));
        }
    }
}
```

# 8. Open Questions

1. **插件分发**：插件如何安装？本地路径 / Git 仓库 / 中心仓库？（倾向：v0.2 本地路径 + Git，中心仓库留更远期。）
2. **WASM vs 动态库**：v0.2 选哪种加载方案？（倾向：WASM，安全性优先。）
3. **插件 API 版本**：插件如何声明兼容的 API 版本？核心 API 变更时如何迁移？（倾向：plugin.toml 的 api_version + 版本协商。）
4. **插件间依赖**：插件 A 是否能依赖插件 B？（倾向：v0.2 不支持，插件应独立。）
