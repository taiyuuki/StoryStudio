# 1. Abstract（摘要）

Scene 是 Document Graph 的叙事单元，由 1–N 个 Fragment 组成。RFC-0002 §5.3 已定义了 Scene 的基本结构与"仅属 Document Graph"的归属规则。本 RFC 细化 Scene 的**语义字段**：POV、时间标注、情绪基调、叙事功能。

```text
   Chapter
     └─ Scene（本 RFC）
         ├─ Fragment
         ├─ Fragment
         └─ Fragment
```

Scene 是最"轻"的 Entity Model——它的结构骨架已在 IR 和 Project Format 中定义，这里只补语义层。

------

# 3. POV（视角角色）

## 3.1 定义

POV（Point of View）是 Scene 的叙事视角——这个故事片段是从谁的角度讲述的。

```toml
# structure.toml

[scene.sc_01_02]
title = "河岸"
pov = "c_8A91D4"              # 视角角色的 StableId
fragments = ["f_0003", "f_0004", "f_0005"]
story_time = { year = 1086, month = 3 }
```

## 3.2 POV 的约束

| 规则 ID | Phase | 检查内容 |
|:--|:--|:--|
| `pov_character_exists` | Structure | POV 引用的 Character 存在 |
| `pov_in_scene` | Semantic | POV 角色应该在该 Scene 的某个 Fragment 出场（anchor: appears），否则"视角角色不在场"通常不合理 |
| `pov_consistency` | Style | 同一 Scene 内 POV 不应中途切换（若切换，建议拆为两个 Scene） |

## 3.3 无 POV 的 Scene

并非所有 Scene 都有 POV：

- **全知视角**：`pov = null`，叙述者非角色。
- **群像场景**：`pov = null`，多个角色平分笔墨，无单一视角。

`pov = null` 是合法的，Compiler 不强制要求 POV。

## 3.4 POV 与 AI 上下文

AI Runtime（RFC-0010）生成 Scene 内容时，POV 决定了叙事视角的约束：

```rust
fn build_scene_context(scene: &SceneNode, ir: &StoryIR) -> String {
    match scene.pov {
        Some(pov_id) => {
            let char = ir.semantic.get_character(pov_id);
            format!("本场景视角：{}。以第一人称或紧贴其视角的第三人称叙事。", char.display_name)
        }
        None => "本场景为全知视角。".to_string(),
    }
}
```

# 4. Mood（情绪基调）

## 4.1 定义

Scene 的情绪基调是**可选的语义标注**，帮助 AI 理解场景应有的氛围，也帮助作者规划节奏。

```toml
[scene.sc_01_02]
# ...
mood = "tense"                # 可选
```

## 4.2 预定义值

```rust
pub enum SceneMood {
    Calm,        // 平静
    Tense,       // 紧张
    Joyful,      // 欢快
    Sad,         // 悲伤
    Mysterious,  // 神秘
    Violent,     // 激烈 / 暴力
    Romantic,    // 浪漫
    Horror,      // 恐怖
    Custom(String),  // 自定义（插件可扩展）
}
```

Mood 是**建议性标注**，不产生 Compiler 规则。它服务于：
- AI 生成时的语气引导
- 作者回顾时的节奏可视化（"这本书前 10 章都很 tense，需要调节"）

## 4.3 不做情绪一致性检查

> **Mood 不触发 Compiler 检查。**

判断"场景的实际氛围与标注的 mood 是否一致"是语义判断，属于 Semantic Validator 的职责，不属于确定性 Compiler。Compiler 只验证 mood 字段的格式合法性（是否为合法枚举值）。

# 5. Narrative Function（叙事功能）

## 5.1 定义

Scene 在故事结构中的功能角色，帮助作者把握叙事节奏。

```toml
[scene.sc_01_02]
# ...
function = "rising_action"    # 可选
```

## 5.2 预定义值

```rust
pub enum NarrativeFunction {
    Exposition,     // 交代背景 / 设定
    IncitingIncident, // 触发事件
    RisingAction,   // 上升动作（推进情节）
    Climax,         // 高潮
    FallingAction,  // 下降动作
    Resolution,     // 结局 / 解决
    Transition,     // 过渡（时间 / 地点切换）
    Flashback,      // 回忆 / 倒叙
    Foreshadow,     // 埋伏笔
    Custom(String),
}
```

## 5.3 功能的用途

- **作者规划**：鸟瞰全书结构（"高潮太少""伏笔集中在后半"）。
- **AI 引导**：生成时告知 AI 此场景的叙事目的。
- **节奏统计**：Editor 可展示"本书各叙事功能的分布"。

> `function` 同样不触发 Compiler 检查——它是规划标注，不是正确性约束。

## 5.4 Foreshadow 与伏笔追踪

`function = "foreshadow"` 标注的场景是"埋伏笔"。Semantic Validator 可利用此标注追踪伏笔回收（"第 3 章埋的伏笔，到结尾是否回收"），但这属于 AI 语义判断，不是确定性 Compiler 的职责。

# 6. Scene Relationships（场景间关系）

## 6.1 叙事顺序 vs 时间顺序

Scene 有两种"前后关系"：

| 关系类型 | 来源 | 用途 |
|:--|:--|:--|
| **叙事顺序** | Document Graph 链表 | 阅读顺序（读者看到的顺序） |
| **时间顺序** | Timeline（RFC-0009） | 故事内先后（事件发生的顺序） |

二者可能不同（倒叙）。RFC-0009 §8.1 已详细论述。

## 6.2 Scene 的连接性

Scene 之间应有叙事连贯性。Compiler 可检查（Style Phase）：

| 规则 ID | Phase | 检查内容 |
|:--|:--|:--|
| `scene_geo_jump` | Style | 相邻 Scene 的地理标注跳跃过大，无过渡（"瞬间移动"） |
| `scene_time_jump` | Style | 相邻 Scene 的时间跳跃过大，无标注 |

这些是 Style 级（非阻断），提示作者注意连贯性。

# 7. Complete Scene Structure（完整 Scene 结构）

汇总本 RFC 与已有定义的 Scene 完整字段：

```rust
pub struct SceneNode {
    // —— 结构字段（RFC-0002）——
    pub id: StableId,
    pub symbol: Option<Symbol>,
    pub title: Option<String>,
    pub chapter: StableId,           // 所属 Chapter
    pub prev: Option<StableId>,      // 链表（内存层）
    pub next: Option<StableId>,

    // —— 时间字段（RFC-0009）——
    pub story_time: Option<StoryCalendar>,

    // —— 语义字段（本 RFC）——
    pub pov: Option<StableId>,       // 视角角色
    pub mood: Option<SceneMood>,     // 情绪基调
    pub function: Option<NarrativeFunction>, // 叙事功能
}
```

```toml
# structure.toml 中的完整 Scene 示例

[scene.sc_01_02]
title = "河岸"
pov = "c_8A91D4"
story_time = { year = 1086, month = 3 }
mood = "tense"
function = "rising_action"
fragments = ["f_0003", "f_0004", "f_0005"]
```

> `fragments` 数组是顺序的 SoT（RFC-0003 §5.2），不是 Scene 的"属性"而是"拥有的关系"。

# 9. Open Questions

1. **Scene 的 summary**：是否需要为 Scene 存一个摘要字段（供 AI 快速回顾"这个场景讲了什么"）？（倾向：是，但摘要应由 AI 生成并标注 extracted_by，存为派生数据而非手写。）
2. **Fragment 级别的 mood**：情绪是否需要精确到 Fragment？（倾向：否，Scene 级足够。Fragment 太碎，标注成本高。）
3. **多 POV Scene**：一个 Scene 内中途切换视角的情况，是允许（用 Fragment 标注 POV）还是禁止？（倾向：v0.1 Scene 级单一 POV，切换视角建议拆 Scene。）
4. **Scene 的字数统计**：是否需要自动统计 Scene 字数并作为字段？（倾向：作为派生数据，不持久化。）

------

# Appendix

> **Scene 是叙事单元，由 Fragment 组成。它的结构骨架早已定义，本 RFC 只补语义——POV 决定谁在看，mood 决定什么感觉，function 决定为什么存在。这三者引导 AI，但不约束确定性检查。**
